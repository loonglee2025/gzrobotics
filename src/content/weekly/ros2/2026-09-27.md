## 总判断

本周是 **ROSCon Global 2026 周（9/22–24，多伦多）**，官方例行节奏整体让位于会议：ROS PMC 周二例会、Waffle 例会、ROS-ffice hours 全部取消 [1]；「ROS News of the Week」本期缺席（最新一期仍停在 9/14），PMC 纪要也停在 9/15 [1]。因此本周的信号几乎全部来自会场内外两条线：**会场内**——Qualcomm 宣布收购 PickNik（MoveIt 维护方），这是本周唯一的生态级事件 [2]；**会场外**——rosdistro 冻结解除后的 release 洪峰，以及一批在会议期间照常合入的基础设施与安全提交。

最值得优先关注的四件事：其一，**中间件核心维护方被芯片厂商收编**——Qualcomm 收购 PickNik，MoveIt 保持开源、许可证不变、硬件中立，但「谁的算力跑 VLA/VLM」已经直接写进了操纵栈的归属问题 [2]；其二，**可复现安装终于有官方答案**——`snapshot repository` 文档落地，`snapshots.ros.org` 按 sync 日期打快照，解决「一次 sync 把你换到没测过的版本」这个长期痛点，仅限 LTS + Ubuntu [3][4]；其三，**治理侧收口**——上次预告的 scoped committer 名单正式写入 `Governance.rst`（4 人入册）[5]；其四，**Fast-DDS 一次修掉三个 DATA_FRAG 路径的 CVE**，且修复尚未进入任何 release [6]。

数量化的「官方节奏」只有一处：rosdistro 在 9/24–9/27 共 172 次提交、其中 159 次 bloom，覆盖 52 个包、5 条发行版线，是典型的会后解冻洪峰 [7]。

## 本周关键信号

### 1. ROSCon 收官 + 会后 release 洪峰：Nav2 的 Lyrical 版本如期落地

**发生了什么：** ROSCon Global 2026 于 9/22–24 在 Sheraton Centre Toronto 举办并收官，官方已公布下一届为 **ROSCon Global 2027，2027 年 10 月 12–14 日，波兰克拉科夫**；演讲视频预计两周后上线 [8][9]。同期官方渠道明确「因为绝大多数贡献者都在 ROSCon，本周不安排任何会议」，ROS PMC 例会、Waffle 例会、ROS-ffice hours 均取消，下周一恢复 [1]。

会场之外，rosdistro 在 9/21–9/27 共 **172 次提交**（9/24 43 次、9/25 39 次、9/27 13 次为主），其中 **159 次为 bloom release，覆盖 52 个包**；按发行版分布：Lyrical 41、Jazzy 38、Rolling 29、Kilted 26、Humble 25。上一期预告的「rosdistro 冻结解除后的 release 洪峰」和「Nav2 的 Lyrical release 会后放行」同时兑现——**`navigation2: 1.5.2-2` 已于 9/21 进入 `lyrical/distribution.yaml`** [7]。

**为什么值得关注：** 两点。其一，上一期判断的「稳定版节奏本身已成稀缺资源」有了下半场：冻结期 vs 解冻期的提交分布差异极大（一周 172 次 vs 全周冻结），说明发行版流水线的产能对会议日历高度敏感——这正是「Rethinking Rolling Syncs」要解决的问题。其二，对生产团队而言，**Lyrical 的导航栈现在补齐了**：上期因保守决策被压在会后发布的 Nav2，本周随解冻入线，Lyrical 用户可以开始规划导航相关升级窗口。

**影响层面：** 发行版节奏 / 生产部署计划 / 社区日历

**下一步盯什么：** 10 月起的常规同步恢复节奏；Lyrical 本轮 sync 的回归报告；9/28 Community Meeting #64 是否会透露会后基础设施议程 [10]。

### 2. Qualcomm 收购 PickNik：MoveIt 维护方进入芯片厂商体系

**发生了什么：** 9/23 于 ROSCon 期间官宣，**Qualcomm Technologies 收购 PickNik Inc.**，由 PickNik 创始人 Dave Coleman 主笔对外说明 [2]。文中的数据勾勒出 MoveIt 的体量：15 年历史、40 个仓库、6,700 stars、4,400 forks、**560+ 贡献者**，两篇 MoveIt 论文合计被引 1,700+。官方承诺的「不变项」很具体：

- MoveIt 1 与 MoveIt 2 **保持开源、许可证不变、社区驱动路线图**；
- MoveIt 保持**硬件无关**；
- PickNik 客户支持延续；
- 继续支持 **MoveIt 与 ROS 的开源开发**；
- Qualcomm 与 PickNik 同为 **OSRA 创始成员**，Qualcomm 将继续投资 ROS 与 MoveIt。

Coleman 给出的收购逻辑值得原文记下：**「这些强大的 AI 模型需要实时、在功耗预算内跑在机器人本体上，而不是数据中心或网络另一端」**，因此机器人最难的问题「不再是纯软件问题，而是软硬件联合设计问题」。文中点名 Qualcomm 近年的开源动作：收购 Arduino、Modular、Edge Impulse、Foundries.io，以及 Dragonwing 平台。

**为什么值得关注：** 这是 2026 年机器人中间件生态最具结构性的一条：**操纵栈的核心维护方从独立咨询公司进入移动 SoC 厂商体内**。三层含义：其一，技术方向上，「混合 AI 系统」（AI 模型 + 传统确定性规划/碰撞检测）被明确确立为 MoveIt 的下一段路线，与 ROS 2 长期依赖的实时/确定性叙事并不冲突，而是分工；其二，产业上，物理 AI 的算力下沉趋势现在直接映射到了 ROS 生态的关键节点上——本周 NVIDIA 侧也有对应动作（Isaac ROS 5.0 与 cuMotion 与 MoveIt 2 栈的集成）[11]；其三，治理上，「社区驱动路线图」这句承诺在母公司资源倾斜下能否维持原有的 RFC/PMC 节奏，是长期观测点。

**影响层面：** 生态治理 / 维护带宽 / 商业化与开源边界

**下一步盯什么：** MoveIt 路线图与 PMC/OSRA 的接口是否变化；Qualcomm 对 ROS 上游（rclcpp/rclpy/rosidl 等）的贡献是否加码；PickNik 原有的开源维护者角色（如 MoveIt 2 的 CI/发布）是否会重构。

### 4. 「sync 突袭」有官方解：snapshot repository 文档落地

**发生了什么：** 9/22 合入 `Add page for the snapshot repository (#7191)`，新增 211 行文档页，并同步在安装页与自定义 rosdistro 页加入指引入口 [3][4]。文档开篇就点明问题：**「主 ROS apt 仓库只保存每个包的最新版本，所以一次 sync 可能把你的系统换到比你上次测试更新的包上」**；sync 发生时旧版本会从主仓库移除、构建失败的包会被删掉。解决方式是 `snapshots.ros.org`：它**保留每次 sync 刚结束时的主仓库副本**，安装快照即得到一组固定版本，直到你主动切换。关键约束：

- **仅 LTS 发行版 + Ubuntu** 提供快照；快照按 sync 日期命名（如 `2026-08-07`），发行版 EOL 时打一个 `final` 快照；
- 快照仓库**使用独立的签名密钥**（指纹 `4B63 CF8F DE49 746E 98FA  01DD AD19 BAB3 CBF1 25EA`），与主仓库的 `ros2-apt-source` 密钥不同；
- 明确警告：**快照不包括 bugfix 与安全更新**，需周期性跟进升级 [4]。

实测盘点（本人核对 [13]）：站点自 2019 年的 `ardent` 起即存在快照，ROS 1 与 ROS 2 并存；**Jazzy 最新快照 `2026-09-11`，Humble 最新 `2026-08-07`**，与各自最近的 sync 节奏对应。同时发现一个运维坑：**`https://snapshots.ros.org` 的 TLS 证书主机名不匹配**，`curl`/Python 默认校验下直接失败（文档内链接使用的是 `http://`），在 CI 镜像构建里直接取快照会踩到。

**为什么值得关注：** 这是本周最贴近生产环境的一条。ROS 2 的 apt 主仓库语义是「只保留最新」，团队长期靠 `apt-mark hold`、私有镜像或整镜像打包来对抗 sync；官方快照仓把这件事变成**一等公民**：容器镜像可以按 `humble` + `2026-08-07` 精确复现，导航/操纵这类多包强耦合栈终于有了可断言的基线。对验证流程的意义同样大——上期提到的「三条 sync 叠加导致验证队列变长」，现在可以用「固定快照做回归、再择时切 sync」的方式拆开。

**影响层面：** 生产部署 / CI 可复现性 / 依赖治理

**下一步盯什么：** 快照生成频率能否跟上 sync（Jazzy 最近快照 9/11，需确认 9/18 sync 后是否补上）；证书主机名是否修复；LTS 之外的发行版（Lyrical/Kilted）是否会纳入——目前文档口径是仅 LTS。

### 5. 安全：Fast-DDS 单次提交修掉三个 DATA_FRAG 路径 CVE

**发生了什么：** 9/22，eProsima 以**单个 squash 提交**（私有分支协审后合并）修复三个 DATA_FRAG 分片路径问题，提交信息直接引用三个 GHSA 编号 [6]：

- `GHSA-w92j-25c7-68qx`：**拒绝**分片大小、样本大小、子消息内分片数或起始序号为 **0** 的 DATA_FRAG 子消息；
- `GHSA-33xc-m88x-3cp8`：在 StatelessReader 的 DATA_FRAG 路径上复用 pending change buffer 前，**校验缓冲区容量是否容纳新的分片结构**；
- `GHSA-f5r6-qvhq-mx93`：计算单分片样本所需 payload 大小时，**为 fragment index 预留空间**。

同一周 Fast-DDS 还有两条可靠性修复：9/23 修 **volatile reader 在初始定位 GAP 之后失步**（#6542，涉及「限制 GAP 处理到 HB 声明值」「每次 GAP 前发 HB」「跳过已从历史中移除的 change 的 GAP」「修复 DataSharing GAP 接收」等一串改动）；9/21 修 **UDP 打开输入通道时的内存泄漏**（#6540）[14][15]。

**需要如实标注的边界：** 三点。其一，**三个 GHSA 编号在 GitHub Advisory Database 中尚未公开**（逐条查询均为 404），因此目前无法给出官方 CVSS 与影响版本区间——这些 ID 来自提交信息本身。其二，**修复尚未进入任何发布版本**：Fast-DDS 最新 release 仍是 `v2.14.7`（9/8）与 3.x 线 `v3.6.2`（7/2）。其三，DATA_FRAG 是**远程可分片触发的解析路径**，属于典型的中间件攻击面，但本次未给出可控的复现条件。

**为什么值得关注：** ROS 2 默认 RMW 仍是 Fast DDS，DDS 的解析路径直接暴露在机器人网络的组播域里，这类「一个 `0` 没校验」的问题在跨网段/多厂商混布场景下风险放大。更重要的是流程信号：**先私有分支隔离修复、再 squash 公开、且不与功能提交混在一起**——这是把安全问题当工程纪律处理，而不是靠发布说明追认。对使用 Humble/Jazzy 的团队，需要盯的是修复进入各发行版所依赖的 Fast-DDS 版本号，以及是否需要临时打补丁。

**影响层面：** 安全 / 中间件 / 网络边界

**下一步盯什么：** `v2.14.x`/`v3.6.x` 后续 release 是否包含这三个修复；GHSA 正式公开时的 CVSS 与受影响版本区间；Humbe/Jazzy 侧 `ros-humble-fastrtps` 类包的跟进时间。

### 6. `shared_buffer_backend`：rosidl::Buffer 的 CPU 共享内存后端出现

**发生了什么：** 9/26，社区发布实验性项目 `shared_buffer_backend`——`rosidl::Buffer` 的 **CPU 共享内存后端**（前身叫 `memfd`），目标是让图像这类**变长大 payload** 在端点可共享内存时**不经过常规消息路径搬运字节**，且 **Python 节点也能零拷贝消费** [16]。作者对既有方案的边界描述很干脆：intra-process 通信要求生产者消费者在同一 C++ 进程（Python 推理节点或需要故障隔离时不便）；Fast DDS Data-sharing 要求 **bounded** 主题类型，其完整零拷贝路径还要求 **plain** 类型；基于预分配定长数组的方案是另一个方向的折衷。本项目落在 **Lyrical 引入的 `rosidl::Buffer` 抽象**这一层。

发布者侧改动很小：

```cpp
sensor_msgs::msg::Image image;
image.data = shared_buffer::allocate_buffer(byte_count);  // 先确定 byte_count
publisher->publish(std::move(image));
```

Python 订阅侧直接拿到只读视图喂 NumPy，不再拷一次 payload。

作者自述的对照实验（V4L2 相机 640×480、MJPEG→bgr8、标称 30 Hz、Fast DDS）：**普通 CPU 缓冲路径**下，独立 C++ 订阅端**长时间无法稳定在 30 Hz**，出现整秒 0 条、随后 1–15 Hz 抖动的区间；**启用 `shared_buffer` 后**，C++ 与 **Python** 订阅端在启动后都**稳定在 30 Hz 附近**。作者明确声明：这不是受控基准、也未定位普通路径波动的根因、不应被读成通用的 Fast DDS 性能结论。另有配套动作：`rosidl_typesupport_fastrtps` **#164 已合入**，把 buffer 路径的热日志改为每进程只打一次（本次实验靠覆盖日志级别绕开）[17]。

**为什么值得关注：** 这条与本周的 `rosidl_buffer_backends`（含 CUDA 后端）生态形成互补——**buffer-backend 机制正在从 GPU 独占走向 CPU 侧落地**，而这正是「相机发布者 → 多进程 → Python 推理」这种真实部署布局的痛点所在。它也把两个长期问题摆上明面：其一，**generic subscription 目前不提供 buffer-backend 选择**（作者因此改用具体的 `sensor_msgs::msg::Image` 订阅），意味着工具链与通用抽象层还需要跟上；其二，中间件厂商各自提供零拷贝路径（Data-sharing / Zenoh / 自定义 SHM）与 ROS 层的统一抽象之间如何分工。对做高带宽感知链路的团队，这是本周最值得动手实测的一条。

**影响层面：** 中间件 / 感知数据通路 / 语言互操作（Python 推理节点）

**下一步盯什么：** 是否进入 rosdistro、是否与官方 `rosidl_buffer_backends` 的接口收敛；generic subscription / `ros2 topic` 工具系是否补齐 backend 选择；作者提到的「普通路径波动根因」是否有后续定位结论。

### 7. rclrs 0.8.0 + buildfarm 学会 vendor Rust crate：Rust 客户端进入常规构建路径

**发生了什么：** 两条互相咬合的进展。

**客户端侧：** 9/23 发布 **`rclrs` v0.8.0**（作者自嘲「Conference-Driven Development」，赶在 ROSCon 前落地）[18]。要点：**首次支持 ROS 2 Lyrical**，绑定为 Humble/Jazzy/Kilted/Lyrical/Rolling 全线重新生成；**ROS 消息包改由 `ros-env` 访问**（保证 rclrs、应用与生成消息使用同一套消息定义，`use ros_env::*;`）；action 侧新增 `ActionClientState::server_is_available`、action server task 不再要求 `Sync`、**参数回调**支持；`TopicEndpointInfo` 暴露 QoS profile；破坏性变更集中在 `ros-env` 迁移与参数回调 API。仓库侧同日 3 个提交，含 `feat!: take the ROS shim interfaces from ros-env` [19]。

**基础设施侧：** 同一周 ros_buildfarm 连续三个提交把 Rust 依赖纳入常规构建：9/23 `Install dh-cargo for sourcedeb builds (#1139)`、9/24 `Vendor crate dependencies in sourcejobs (#1144)`、9/24 `Remove crates supplied by ROS packages before vendoring (#1147)` [20][21]。也就是说，sourcedeb 构建现在会**自动 vendor crate 依赖**，并避免把已由 ROS 包提供的 crate 重复 vendor。同期 ros2/ros2 侧：`Add ninja and sccache in a buildfarm-only environment (#1854)`、`Add nanobind (#1856)` [22][23]。

**为什么值得关注：** Rust 客户端从「能跑 demo」走向「能进 buildfarm 的常规路径」——**sourcedeb 阶段能 vendor crate 依赖，是任何非 C++/Python 语言随发行版同步的前置条件**。这条链路和两周前的 scoped committer 名单（CI 基建）、本周的 `dh-cargo` 一起，说明构建基建正在为多语言绑定铺路。`ninja`+`sccache` 只作用于 buildfarm 环境、`nanobind` 的引入，则指向两件事：**构建吞吐**与**绑定层换代**（pybind11 → nanobind 方向的迁移预期）。rclrs 侧 `ros-env` 的破坏性迁移，本质是在解决「消息定义一致性」这个跨语言长期问题。

**影响层面：** 构建基建 / 语言绑定 / 构建吞吐

**下一步盯什么：** rclrs 0.8.0 是否随 Lyrical 进入官方 apt 源；nanobind 在 rclpy/tf 相关绑定上的实际迁移节奏；buildfarm 的 crate vendoring 是否扩展到 Rust 之外的生态（如更多 vendor 类包）。

## 核心框架更新

## 工程化观察

1. **会后 release 洪峰的分布值得记一笔**：159 次 bloom 中 Lyrical 41、Jazzy 38、Rolling 29、Kilted 26、Humble 25——**四条线几乎是均摊的**，说明社区维护者已普遍按「多发行版同步发布」的方式组织（mola、mavros、mrpt3、fields2cover、mapviz 等都是五线齐发）。对下游团队的含义：落后一条发行版不再等于落后一个功能周期，而是落后一个「发布批次」。
2. **rosdep 的 RHEL 侧继续补洞**：9/25 `Add RHEL mappings for five existing rosdep keys (#54176)`、9/24 `Add Fedora and RHEL mappings for qtpositioning5-dev` [36]。这是上期「RHEL 升 Rolling Tier 1」在依赖元数据层面的落地动作——平台层级调整真正生效，靠的是这类一行行 rosdep 映射。
3. **REP 链接整体迁移到 `reps.openrobotics.org`**（9/25）[37]：REP 文档站点从之前的路径迁出，外部脚本/文档中的旧链接需要更新；结合 `docs.ros.org` 的发行版列表可知，当前开发发行版为 **Makoa Mata-mata（`makoa`，2027 年 5 月）**，最新已发布发行版为 **Lyrical Luth（2026 年 5 月）**[38]。
4. **Rolling 持续清理**：`Remove acado_vendor from Rolling`（9/25）、`Remove qml_ros2_plugin from rolling`（9/24）。Rolling 的「未维护包出清」节奏保持稳定，使用这些包的项目需要注意上游迁移。
5. **文档侧的两个小改动对冲了大的运维痛点**：`snapshot repository` 页（可复现安装）与 `ros2 action info --verbose` 补全——后者让 action 的 5 个底层服务/主题在命令行可见，是排障时最缺的一块可观测性。
6. **快照站的证书问题需要提级**：`https://snapshots.ros.org` 的 TLS 证书主机名不匹配（`curl`/`urllib` 默认校验直接失败），而文档正文给出的链接是 `http://`。在 CI 里 `curl` 快照索引会立即踩坑；建议团队在脚本中显式处理（临时 `-k` 或使用 `http`），并等官方修复。

## 前沿议题

- **算力下沉与「谁的机器人 AI」**：本周三件事指向同一方向——Qualcomm 收购 PickNik 时明确说「模型要在本体上、功耗预算内实时跑」[2]；NVIDIA 的 Isaac ROS 5.0 与 cuMotion 与 MoveIt 2 集成，把碰撞感知规划接到 GPU 侧 [11]；ROS 2 社区本周讨论的正是 **perception/AI 任务该跑在本体、边缘服务器还是云上**，以及这种放置是否会**动态变化**、有没有人「上了云又撤回来」[39]。三者的共同点是：**推理放置正在从「架构偏好」变成「可观测的运行时约束」**——延迟与本地算力争用已经是真实故障源，但目前 ROS 2 里缺少描述这种放置的标准抽象。
- **云侧部署的社区组织化**：ROSCon 会场上的 **k8s / KubeEdge × ROS 2** 圆桌已开跟进帖，组织者（Tomoya Fujita，TriOrb）表示返日（东京）后将在 **10 月**安排线上跟进会议，且明确「ROS 是开源的，任何人都可以加入」[40]。这条相对冷门，但它把「机器人负载进 Kubernetes」从零散试水推向有固定节奏的社区议题——与本周讨论的推理放置问题是同一问题的部署侧。
- **executor 与并发主线未停**：Nav2 在 costmap 发布前先自旋 executor（#6549）[28]；rclrs 的 action server task 不再要求 `Sync`、新增参数回调 [18]。客户端库一侧的执行模型（events executor 入 PMC、rclpy asyncio executor 死锁）在 ROSCon 会场的专场之后，仍需看后续合入节奏。
- **Zenoh 两条线仍在推进**：gz-transport 启用 Zenoh 共享内存（#842）[31]；而稳定版侧，上期提到的 **Jazzy「针对 Zenoh 回归的快速跟进 sync」本周未出现在 rosdistro 的 52 个包中**，仍未落地。
- **中间件零拷贝的「第四种做法」**：DDS Data-sharing（有类型约束）、intra-process（有进程约束）、预分配定长数组（有灵活性代价），加上本周的 `rosidl::Buffer` + CPU 共享内存 [16]。值得思考的是：**这一层抽象该由 ROS 定义还是由各家中间件定义**，以及它会怎样反过来影响消息类型系统的设计（bounded vs plain vs 变长）。
