## 总判断

ROSCon 后的第一个完整工作周，官方节奏全面恢复，而且带着明确的「收口」姿态：ROS PMC 与 Gazebo PMC 双双复会，**REP-158（OpenUSD 仿真资产互操作规范）经两 PMC 联合投票正式接受** [1][2]——上期预告的投票结果如期兑现；「ROS News of the Week」复刊，官方确认了 ROSCon 期间的四件大事（Intrinsic Open Core 开源、Qualcomm 收购 PickNik、RHEL 升 Tier 1、Isaac ROS 5.0）[3]。

本周最值得优先关注的四件事：其一，**REP-158 落地**——仿真资产的单位、材质、光照约定第一次有了跨仿真器的官方规范文本，Gazebo/Isaac Sim/MuJoCo 之间的资产搬运从此有章可循 [2]；其二，**Fast-DDS 安全修复进入「常态化流水线」模式**——上周三个 DATA_FRAG CVE 之后，本周又有两个私有评审的 GHSA 修复合入 master，五个编号全部未公开、全部未进 release [4][5]；其三，**10/5 双 sync 预备**——Lyrical（307 包待同步、3 个回归）与 Jazzy（472 包、零回归）同时进入冻结，下周一将是会后最大的一次包推送 [6][7]；其四，**PMC 复会抛出两个结构性议题**：CI/CD 需求文档（承认基础设施「有机生长而非设计」）与 macOS 黄金路径上 Pixi vs 传统 curated 平台的路线之争 [8]。

数量化的「官方节奏」：rosdistro 本周 122 次提交、115 次 bloom、覆盖 28 个包，五条发行版线几乎均摊（Lyrical 26、Humble 24、Rolling 23、Jazzy 22、Kilted 20）；同时出现 **4 次版本回滚**（roboplan、mrpt_ros_bridge ×2、gtsam），是上周解冻洪峰的质量账单 [9]。

## 本周关键信号

### 1. REP-158 正式接受：仿真资产互操作有了官方规范

**发生了什么：** 9/28 Gazebo PMC 纪要确认：**「正式决定：接受 REP-158《OpenUSD Conventions for Simulation Asset Interoperability in Open Source Robotics》，这是与 ROS PMC 的联合投票，最终结果将在两个 PMC 正式记录后公布」** [1]。规范文本已上线 reps.openrobotics.org，核心约定包括：资产必须使用 MKS 单位制（`metersPerUnit`/`kilogramsPerUnit`/`timeCodesPerSecond` 显式置 1.0，上游 CAD 毫米等单位在 ETL 管线中烘焙进几何与物理）；自发光材质仅用于指示灯类效果，主照明必须共址布置标准 `UsdLux` 光源 [2]。这正是上期「下周优先跟踪」中 REP 158 投票结果的兑现。

**为什么值得关注：** 仿真资产格式碎片化是机器人仿真的长期隐形成本——同一个机器人在 Gazebo、Isaac Sim、MuJoCo 里各要一套资产。REP-158 选择的是「约定优先于格式」的路线：不发明新格式，而是给 USD 在开源机器人场景下的使用立规矩。这与 Gazebo PMC 同场讨论的「从 Gazebo 起步、经格式转换器导出到其他仿真器」的定位互为表里 [1]——当 MuJoCo 在 ROSCon 上势头强劲时，Gazebo 阵营的应对不是对抗而是把自己做成互操作枢纽。对资产管线团队的实际意义：单位烘焙与光照约定可以直接写进资产验收 checklist。

**影响层面：** 仿真生态 / 资产管线 / 跨仿真器互操作

**下一步盯什么：** 两个 PMC 正式记录后的公告文本；各仿真器（Isaac Sim、Gazebo、Webots）对 REP-158 的资产侧适配；`urdfdom` 闭环运动学讨论（ros/urdfdom#267）与 REP-158 的边界划分 [1]。

### 2. Fast-DDS：又有两个私有评审 GHSA 修复合入，五个 CVE 全部悬而未发

**发生了什么：** 继上周单次提交修复三个 DATA_FRAG 路径 CVE 之后，本周 master 上又合入两个同样模式的修复：**9/28 `Fix GHSA-wfcj-cv96-9wj9`、10/1 `Fix GHSA-g355-8h7f-6w8v`**——均为「私有分支评审后 squash 合入」，提交信息不含任何技术细节 [4][5]。同周的正常功能提交包括 `Set max ASIO buffers based on IOV_MAX`（#6554）与 `Custom security policy`（#6550）[10]。**边界如实标注：五个 GHSA 编号（上周三个加本周两个）在 GitHub Advisory Database 中查询仍为 404，均未公开；Fast-DDS 最新 release 仍停留在 v2.14.7（9/8）与 v3.6.2（7/2），即全部五个修复尚未进入任何发布版本** [11]。

**为什么值得关注：** 上周的判断「把安全问题当工程纪律处理」本周得到强化——这不是一次性清账，而是**成建制的私有评审修复流水线**：两周一共五个 GHSA 级别修复，节奏稳定、格式统一（同一作者 Carlos Ferreira González、同一评审人）。对下游的含义分两层：短期看，Humble/Jazzy 用户必须盯修复进入 `ros-*-fastrtps` 包的时间点，必要时自行 backport；长期看，eProsima 显然在消化一批积压的安全审计结果，DATA_FRAG/RTPS 解析路径的加固还没结束，使用 Fast DDS 暴露在不信任网络的团队应把这当作持续风险项管理。

**影响层面：** 安全 / 中间件 / 发布节奏

**下一步盯什么：** 五个 GHSA 的公开时间、CVSS 与影响版本区间；`v2.14.x`/`v3.6.x` 下一个 release 是否打包这批修复；Jazzy 10/5 sync 中 fastrtps 相关包的版本号变化 [7]。

### 3. 10/5 双 sync 预备：Lyrical 307 包待同步，Jazzy 零回归

**发生了什么：** 10/2，两条发行版线同时发布 sync 预备公告并进入冻结：**Lyrical** 计划 10/5 同步，**307 个包待同步、3 个回归**，即日起 hold 新的 rosdistro release PR [6]；**Jazzy** 同样计划 10/5（按新加坡时区周一），**472 个包就绪、零回归**，冻结范围是「除非修复已报告回归，否则全部 hold」[7]。Jazzy 帖下出现了典型的末班车请求：社区成员询问 `ros2cli#1321` 能否赶上——该修复针对 `ros2 interface show` 显示错误消息定义甚至崩溃的问题，对应的 suffix match 修复（#1315）本周已在 master 合入 [12]。

**为什么值得关注：** 这是 ROSCon 冻结-解冻周期后的第一次常规双 sync，也是检验上期「快照仓库」叙事的第一个实战窗口：**snapshots.ros.org 上 Lyrical 已有 9/18 sync 对应的快照、Humble 已有 9/14 快照**，如果 10/5 sync 后快照按节奏补齐，「固定快照做回归、择时切 sync」的工作流就真正闭环了 [13]。另一个值得记录的细节：Lyrical 并非 LTS，但快照站实际已为其生成快照——与官方文档「仅 LTS + Ubuntu」的口径存在偏差，对 Lyrical 用户是事实利好 [13]。

**影响层面：** 发行版节奏 / 生产部署计划

**下一步盯什么：** 10/5 双 sync 是否如期落地、Lyrical 的 3 个回归是何包；sync 后 snapshots.ros.org 是否当天补快照；Jazzy 的 Zenoh 回归跟进（连续两周未见）是否随本轮进入。

### 4. PMC 复会：CI/CD 需求文档 + macOS 路线之争 + ARM64 RPM 请求

**发生了什么：** 9/29 ROS PMC 会后首会，议题密度明显超标 [8]：

- **CI/CD 需求文档**：clalancette 牵头，源于 ROSCon 上「我们到底想从 CI/CD 要什么」的讨论。官方原话值得记下：「我们的基础设施是有机生长而非设计出来的，而且太慢了」。文档刻意只做需求清单、不做选型，跨 ROS 与 Infrastructure 两个 PMC 征求意见；配套的 CI/CD SIG 提案已提交 TGC 做资助决策——理由是「没有资助挂钩，过载的 PMC 不会有人站出来组 SIG」。
- **macOS 黄金路径之争**：不要求 macOS 升 Tier 1，但要一条「基本能用」的官方路径。mjcarroll 倾向标准化到 Pixi；cottsay 抛出核心矛盾——**Pixi 是滚动生态，而 ROS 的工作流、工具链和发行模型都建立在稳定、精选、打安全补丁的地基上**（CMake 4 是现成例子）。集中式 `pixi.lock` 在核心包可行但无法扩展到发行版级别；折衷方案是版本区间而非精确钉版。andrew_symington 报告 macOS 上的 Bazel 全量构建（含 Qt）已相当干净。
- **Red Hat 请求 ARM64 RPM 包**：Red Hat 正在一批 ARM 开发板上启用 ROS，需要 Lyrical 与 Rolling 的 ARM64 RPM。buildfarm 目前完全不产出 ARM64 RPM，cottsay 估算**每个发行版约 1500 个新增构建任务，Rolling+Lyrical 合计约 3000**——本质是资源分配问题，下一步是与 buildfarm 团队算成本、与 Red Hat 谈投资。缺失包（Pinocchio、部分 Nav2 包）的解法是直接追上游 [8]。
- **PMC 维护边界**：当天收到一个针对非 PMC 维护仓库的安全报告，PMC 明确「社区维护包的问题应直接找维护者，我们只是基础设施」，承认此处缺乏文档与流程。

**为什么值得关注：** 四个议题指向同一件事：**ROSCon 之后的 ROS 官方正在把「会上的共识」转化为「可资助、可问责的工程项」**。CI/CD 文档 + SIG 资助挂钩的模式，与 8 月 TGC 批准的 25 万美元基建/文档资金（Cargo-in-buildfarm 的进度本周也有了非正式跟踪 issue ros_buildfarm#1157）是同一套治理逻辑 [14][15]。ARM64 RPM 请求则是 RHEL 升 Tier 1 的直接后续——平台支持的承诺最终都要折算成 buildfarm 的任务数和预算。macOS 之争本质是「滚动依赖 vs 稳定依赖」的路线分歧，与本周 Conan 工作流帖（把 ROS 装进 conanfile 当普通 C++ 依赖消费）形成有趣对照：社区正在从多个方向试探「ROS 作为库」的可行性 [16]。

**影响层面：** 基础设施 / 治理 / 平台支持

**下一步盯什么：** CI/CD 需求文档的公开链接与评论期；CI/CD SIG 的 TGC 资助结果；ARM64 RPM 的成本评估结论；PMC 维护边界文档化。

### 5. Intrinsic Open Core 开源：「新一代 ROS 发行版的第一个」

**发生了什么：** 本周「ROS News of the Week」正式确认 ROSCon 期间的重磅发布：**Intrinsic 开源 Intrinsic Core**，OSRA 官方博客称之为「**新一代 ROS 发行版中的第一个**」（the first of a new generation of ROS distributions），Forbes 的标题更直接——「Google is giving away the Android of robotics」；源码已在 github.com/intrinsic-ai/intrinsic-core 公开 [3][17]。同期新闻确认：ROSCon Global 2027 定档波兰克拉科夫（2027 年 10 月 12–14 日），演讲视频预计两周内上线 [3]。

**为什么值得关注：** 「发行版」这个词在这里是关键：Intrinsic Core 不是又一个栈或工具包，而是**一个带商业实体背书的 ROS 衍生发行版**——与上周的 Isaac ROS 5.0（NVIDIA 的 ROS 发行版）并置，「vendor 发行版」正在成为一个正式品类。加上 Qualcomm 收编 MoveIt 维护方 PickNik，三周内 ROS 生态的三个关键位置（操纵栈维护方、GPU 感知栈、应用开发平台）分别被 Qualcomm、NVIDIA、Google 系力量占位。对使用者的实际意义在于分流：核心 ROS 的治理仍走 OSRA/PMC 路线，但「开箱即用的生产级体验」越来越多地由厂商发行版承接——选型时「跟上游 Rolling 还是跟厂商发行版」会成为新的架构决策点。

**影响层面：** 生态格局 / 商业化与开源边界 / 发行版定义

**下一步盯什么：** Intrinsic Core 的仓库结构中与上游 ROS 的分叉程度；其贡献回流上游的节奏（andrew_symington 已在 PMC 代表 Intrinsic）；厂商发行版之间（Isaac ROS vs Intrinsic Core）的互操作姿态。

### 6. events executor 主线推进：EventsCBGExecutor 加入 worker queue

**发生了什么：** 10/1，rclcpp 合入 `feat(EventsCBGExecutor): Added worker queue`（#3277）[18]。同周 rclcpp 还有：action client goal handle 新增 `GoalStatusCode` 枚举与 `get_status_code()`（#3292）、组件容器生成的 main 在移除节点前检查 executor 关联（#3287）。rclpy 侧修复了 `Executor.__del__` 在 SIGINT guard condition 已终结时的容错（#1734）[19]。

**为什么值得关注：** 上期提到「executor 与并发主线在 ROSCon 专场之后需看合入节奏」，本周就是答案的第一部分：**events executor 从实验性调度器向生产可用的执行模型继续补构件**——worker queue 是支撑并发回调组（callback group）事件分发的基础设施。值得注意的配套信号：ROS PMC 纪要的 ROSCon 复盘里记录了一位听众在 skye.galaxy 的 executor 演讲后主动提出「让 executor 更快」的想法 [8]；ros2cli 本周为 `ros2 component standalone` 新增 `--executor-type` 与 `--isolated` 参数（#1310），executor 的选择正在进入命令行工具层 [20]。执行模型的可观测性与可配置性在同步补齐。

**影响层面：** 客户端库 / 执行模型 / 实时性

**下一步盯什么：** EventsCBGExecutor 相对默认 executor 的基准数据；ROSCon executor 专场视频上线后的设计细节；`--executor-type` 是否推广到 launch 系统。

### 7. Nav2 高强度修复周：AMCL 连修两个内存安全级问题

**发生了什么：** Nav2 本周 14 个提交，密度与性质都不寻常 [21]：

- **AMCL 二连修**：修复 k-d 树聚类遍历中的**栈溢出**（#6464）与 k-d 树**整数溢出**（#6451）——定位算法核心数据结构上的内存安全级问题；
- **参数边界校验**：`Validate parameter bounds to prevent invalid allocations (Bugs 1–9 in #6428)`（#6566）——一次性修掉 9 个「畸形参数导致非法内存分配」的 bug；
- **TF 时效性**：BT 与 navigators 增加 stale TF 检查（#6527）、costmap 与行为树的 staleness 检查（#6496）——承接上周 costmap 发布前自旋 executor 的时序主线；
- 其余：planner 抢占的 goal 传播修复（#6586）、DWB 速度缓存动态限速（#6590）、AMCL 在收到首帧地图前安全处理全局定位请求（#6579）、Hybrid A* 保留分数航向（#6545）等。

**为什么值得关注：** 这批修复的共性是**「恶意或畸形输入 → 崩溃/溢出」**：栈溢出、整数溢出、非法分配，全是 fuzzing 或代码审计的典型产出。Nav2 1.5.2 上周刚进 Lyrical，本周就集中修这一类问题，说明导航栈正在被系统地做鲁棒性审计（#6428 的多 bug 编号方式暗示存在一次集中的漏洞梳理）。对把 Nav2 部署在开放网络或接受外部目标点输入的团队，这些修复值得评估 backport 到自维护分支。

**影响层面：** 导航栈 / 鲁棒性与安全 / LTS 维护

**下一步盯什么：** #6428 全系列是否还有后续 bug；这批修复进入各发行版 sync 的时间（Jazzy 10/5 sync 是否包含）；Nav2 下一个 Lyrical 版本。

## 核心框架更新

- **`launch`：修复十年老问题 SIGTERM 处理（#712）**，并发布 `3.10.2`；同时补充信号处理文档（#1025）、明确 log action 的 `level` 属性为必填（#1024）[22]。SIGTERM 路径的修复直接影响容器编排（k8s preStop、systemd stop）下的进程退出行为。
- **`ros2cli` 一周 8 提交，主题是「可用性对齐」**：`--log-level`/`--level` 别名统一（#1308）、`--count` 别名推广到 list/find/nodes（#1312）、`--filter` 别名（#1313）、整数参数校验避免裸 ValueError（#1296）、`ros2 component standalone` 新增 `--executor-type`/`--isolated`（#1310）、`interface show` suffix match 修复（#1315）[12][20]。
- **`rosbag2`**：按大小分割 bag 时计入缓存消息体积（#2496）——分割决策不再低估实际写入量 [23]。
- **`rosidl`**：生成的 C 头文件正确处理注释分隔符（#995）。
- **旧式 `ament_export_*` 清理扩散**：`rcl`（#1342）、`rosbag2`（#2519）、`geometry2`（#996）、`rviz`（#1889）跟随上周 `rosidl` 的步伐，继续减少导出变量对下游的隐式耦合。
- **`ros2_documentation`**：Lyrical 文档注明 `rmw_zenoh_cpp` 的 Buffer 支持（#7209）——与上周 shared_buffer_backend / rosidl::Buffer 主线衔接；RPM 安装说明扩展到 Fedora（#7230），RHEL 升 Tier 1 的文档侧跟进 [24]。
- **Fast-DDS**：除两个 GHSA 修复外，`Set max ASIO buffers based on IOV_MAX`（#6554）修复大消息 scatter-gather 场景 [10]。

## 工程化观察

1. **回滚是洪峰的对价**：本周 rosdistro 出现 4 次版本回滚（roboplan、mrpt_ros_bridge ×2、gtsam）[9]。上周 159 次 bloom 的解冻洪峰不可能零成本——`gtsam 4.3.1` 上周刚五线齐发，本周就被回退到 `4.3.0-5`。对维护者的提示：bloom 前的多发行版构建验证仍是人肉防线；对用户的提示：sync 后 48 小时内的 apt upgrade 值得在 staging 环境先跑一轮。
2. **「ROS 作为库」的探索多点开花**：Conan 团队发布 ros-conan recipes——把 ROS Kilted 声明进 conanfile、像普通 C++ 依赖一样消费（Linux/macOS/Windows 三平台）[16]；PMC 同周辩论 Pixi vs curated 平台与 macOS Bazel 全量构建的可行性 [8]。三条路线的共同诉求是把 ROS 从「系统级发行版」变成「可嵌入现有工程体系的依赖集」——这是 RHEL Tier 1、快照仓库之后同一条去摩擦化曲线的延续。
3. **快照站口径与现实偏差**：官方文档称快照「仅 LTS + Ubuntu」，但实际 Lyrical（非 LTS）已有 9/18 快照、Humble 有 9/14 快照；Jazzy 最新仍是 9/11（9/18 若有 sync 则未补快照）[13]。文档口径、实际覆盖、补齐节奏三者需要分别跟踪。证书主机名问题本周未见修复。
4. **CI 成本意识抬头**：Gazebo PMC 拟启用「新贡献者 PR 需手动批准才跑 CI」（防批量/自动化 PR 拥堵队列），并在评估用依赖图智能跳过无关构建（release-tools#1558）[1]；ROS 侧的 CI/CD 需求文档直接承认「太慢」[8]。构建资源正在从「默认无限」变成「需要治理的资产」——ARM64 RPM 的 3000 任务估算会把这件事推向预算层面。
5. **OpenEmbedded 社区会议 #64 如期召开**（9/28），议程包括 Layer Audit、Superflore 传递依赖、SDK 文档、OEROS 容器镜像、**Edge AI 支持**、bitbake-setup 配置片段 [29]——Yocto 路线的 ROS 部署继续组织化，与上周 k8s/KubeEdge 圆桌形成「机器人部署形态」的两条平行线。

## 前沿议题

- **仿真器格局的重排**：Gazebo PMC 纪要罕见地正面讨论「MuJoCo 在 ROSCon 的势头」（包括 mujoco_ros2_control 的直接使用与新渲染器），应对策略是明确价值主张——易用性、不强制 GPU、HIL 与集成测试、混合运动学/动力学模式、Fuel 集成、以及「从 Gazebo 起步再经格式转换导出」的枢纽定位 [1]。叠加 REP-158 的接受，仿真层的竞争叙事正在从「谁替谁」转向「资产与资产的互操作」。
- **零拷贝传感器通路的合流**：Gazebo PMC 讨论用 rcl_buffer 把仿真传感器数据零拷贝交给 ROS（ros_gz_pointcloud 为首选），mjcarroll 进一步畅想 GPU/CUDA 渲染的传感器数据直接进入 ROS 节点 [1]。这与上周 shared_buffer_backend（CPU 共享内存后端）、本周文档侧注明 rmw_zenoh_cpp Buffer 支持（#7209）构成同一条线的三个落点——buffer 抽象正在从消息层向仿真器与 RMW 两侧同时渗透 [24]。
- **治理的「资助挂钩」模式成型**：CI/CD SIG 提案明说「没有资助就不会有 SIG」；TGC 的 25 万美元资金已开始产出可跟踪的工程项（Cargo-in-buildfarm #1157）[8][15]。OSRA 的会费模式正在从「维持运转」升级为「定向投资」，这会是观察社区治理演化的长期样本。
- **年度调查启动**：Open Robotics 首次年度开发者调查开放（截止 11/30，抽奖 50 件官方周边），官方明确「我们不做遥测，调查是获取用户反馈的最佳机制」[30]。对依赖官方路线图的团队，这是低成本影响优先级排序的渠道。
