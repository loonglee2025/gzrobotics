## 总判断

本周是 **ROSCon Global 2026（9/22–24 Toronto）开幕前的最后冲刺周**，上周预告的「会前收口」全部兑现，节奏之密集为近期罕见。最值得优先关注的三件事：其一，**发行版三线齐发**——Humble（9/14，77 新包 + 687 更新 + patch release）、Kilted（9/17，257 包）、Lyrical（9/18，336 包）在一周内完成 sync，PMC 为此下达了全周 rosdistro PR 冻结令，Jazzy 还排着一趟针对 Zenoh 回归的快速跟进 sync；其二，**治理组合拳继续落地**——RHEL 正式升入 Rolling Tier 1、Fedora 降 Tier 3 的投票通过，上周预告的 scoped committer 投票如期发出（六人入选，覆盖 tf2/launch/rclpy/CI 基建等关键仓库），REP 158（OpenUSD）进入 ROS + Gazebo 双 PMC 联合投票；其三，**Gazebo 官宣弃用 armhf 32 位二进制包**（9/21 生效），同时 gz-sim 合入 EnTT 版 ECM 架构重构。代码层面，Nav2 合入 lifecycle manager 合并大重构，rclpy asyncio executor 被发现死锁——executor 这条主线在 ROSCon 前夜仍在升温。

## 本周关键信号

### 1. 发行版「三线齐发」：Humble/Kilted/Lyrical 一周内完成 sync，rosdistro 全周冻结

**发生了什么：** 上周「会前最后窗口」的判断本周完全兑现 [1][2][3][4]：

- **Humble（9/14）**：sync + patch release 15（`release-humble-20260914`），77 个新包 + 687 个更新——包括 ros2_control 2.54.x、BehaviorTree.CPP 4.10、Crazyflie 1.0.7、NoDL 2.0.3 首次进入 Humble 官方源 [1]；
- **Kilted（9/17）**：257 个包，无回归一次通过；过程中 peci1 发现 rmw_zenoh 0.6.8（含关键 bugfix #1039）因构建时序差点错过 sync，christophebedard 澄清了「SYNC 列表要求新版本已在 testing 仓」的机制 [2]；
- **Lyrical（9/18）**：336 个包。sloretz 合并了 MoveIt 的 release PR（含 #3851 controller spawner 参数文件修复），但**明确把 Nav2 的 release PR 压到 ROSCon 之后**——会前不引入导航栈变更的保守决策 [3]；
- **Jazzy**：PMC 纪要确认还有一趟「针对 Zenoh 回归的快速跟进 sync」在排队 [4]；
- PMC 对 rosdistro 下达**全周 PR 冻结令**（9/15–9/22），三条 sync 短兵相接是官方给出的理由 [4]。

**为什么值得关注：** 一周三条 sync + 一次冻结令，说明「发行版节奏」本身已经成为需要 PMC 级协调的稀缺资源——这正是两周前「Rethinking Rolling Syncs」自动化方案要解决的痛点在稳定版侧的镜像。对生产团队的直接含义：**下周一开工，三条线的 apt 源全是新的**，上周 Jazzy 882 包大 sync 的验证工作还没做完的团队，现在验证队列又加长了；Lyrical 用户注意 Nav2 不在本次 sync 中，导航相关修复要等会后。

**影响层面：** 发行版节奏 / 生产部署计划

**下一步盯什么：** Jazzy Zenoh 回归跟进 sync 是否在 ROSCon 期间落地；Lyrical sync 后的回归报告；Nav2 的 Lyrical release 会后何时放行。

### 2. 平台层级调整落地：RHEL 升 Rolling Tier 1，Fedora 降 Tier 3

**发生了什么：** 9/15 PMC 纪要确认投票通过 [4]：**RHEL 成为 Rolling 的 Tier 1 平台，Fedora 降至 Tier 3**。文档已同步更新。上周纪要中的细节本周值得复述：Fedora 包由 Fedora Robotics SIG 维护，Tier 3 意味着无 CI 强制要求，包会随 Rolling sync 自动同步，PMC 只承担记账与文档层面的工作。

**为什么值得关注：** 这是 REP 2000 平台矩阵多年来最实质的一次调整，信号意义大于技术意义：**ROS 官方资源向企业级 Linux（RHEL）倾斜**，承认桌面滚动发行版（Fedora）不适合作为机器人中间件的一级支持目标。对企业用户的含义很直接——RHEL 从「社区移植」变为「一等公民」，RHEL 上跑 ROS 2 Rolling 从此有官方 CI 背书；对 Fedora 用户则意味着回归响应不再有保证。

**影响层面：** 平台支持矩阵 / 企业采用

**下一步盯什么：** REP 2000 文档的正式更新页面；RHEL Tier 1 的 CI 覆盖何时体现在 buildfarm 状态页；此举是否为 M-turtle 时代 RHEL 进入稳定版 Tier 1 铺路。

### 4. REP 158（OpenUSD）进入双 PMC 联合投票：法定人数机制首次被摆上台面

**发生了什么：** REP 158（机器人 OpenUSD 约定）从 Draft 推进到投票阶段，与上周 SIG PAI 的更新衔接 [4][5]：ROS PMC 大部分票已投；因 Gazebo PMC 同为该 REP 的署名方，mjcarroll 亲自出席 9/14 Gazebo PMC 会议发起动议，Gazebo 侧投票 9/18 截止。通过后 REP 158 进入 **Accepted**（而非 Final）状态，作者完成实现后才可 Finalize。mjcarroll 还特意点破流程细节：跨 PMC 投票的法定人数是各 PMC 成员的 50%、简单多数决——**理论上两个 PMC 合计 25% 的成员即可通过一项 REP**。

**为什么值得关注：** 两件事。其一，OpenUSD 作为 NVIDIA 主导的仿真/场景描述标准，进入 REP 流程意味着 ROS-Gazebo 生态对 USD 的互操作从「厂商插件」上升为「官方约定」——这是具身智能数据管线（仿真→训练→部署）标准化的关键一块。其二，「25% 即可通过」被 PMC 主席自己公开点出，说明 REP 治理的参与度问题已被官方意识到，未来可能出现法定人数规则的修订讨论。

**影响层面：** 标准制定 / 仿真与数据互操作

**下一步盯什么：** 9/18 投票结果公告（截至周日未见，可能在 ROSCon 上宣布）；Accepted 之后的实现主体是谁（NVIDIA？Intrinsic？）。

### 5. Gazebo 弃用 armhf + EnTT 版 ECM 合入：一边砍包袱一边换引擎

**发生了什么：** Gazebo 本周一减一增两个架构级动作 [6][5]：

- **弃用 armhf（32 位 ARM）二进制包**（9/15 官宣，jrivero）：9/21 起不再为任何在支持期内的 Gazebo 版本（Fortress/Harmonic/Ionic/Jetty）发布 armhf .deb，已发布包保留但不再更新，源码编译不保证。理由坦率：树莓派/Jetson/ARM 云实例早已全面 64 位，上游（DART、Fedora）在撤，而 armhf 构建占 buildfarm 产能、拖慢发布 [6]；
- **gz-sim 合入 #3447「ECM Implementation with Entt」**（9/15）：实体组件管理器迁移到 EnTT——这是 gz-sim 核心数据结构的架构级重构，配套的 Python 绑定暴露（#3957）和 `Server::Ecm` 更名 `EcmScope`（#3964）已在推进；
- 其他值得记录：gz-sensors #655 相机渲染直写复用 image message 内存，高分辨率 RGB 相机性能提升约 15%；gz-transport 完成 Zenoh 1.8 集成第二部分（最低版本升至 1.7.2），修复了进程内 pub/sub 叠加远程订阅者导致的消息重复（#961/#965）；MuJoCo 物理后端合入接触可视化（gz-physics#1055）与关节速度指令（#1004）；Homebrew 7.0.0 破坏了 homebrew-zenoh tap 和 gz-rendering/gz-gui 测试沙箱，macOS 侧正在救火；新的 Gazebo Release Dashboard 有望被官方收编。

**为什么值得关注：** armhf 弃用与上周 M-turtle「less is more」路线图完全同频——官方在主动缩小支持面以换取维护质量，这是健康的信号，依赖 32 位 ARM 的存量用户需要尽快给出迁移计划。EnTT 迁移则是 gz-sim 多年技术债中最重的一块，ECM 性能与 Python 可编程性都会因此改善，仿真重度用户（RL 训练管线）应关注后续基准数据。

**影响层面：** 仿真基础设施 / 平台支持面

**下一步盯什么：** EnTT 版 ECM 的性能对比（团队正为 ROSCon 演讲做 Jetty vs main 的 profiling）；armhf 弃用的社区反馈期（10 天）有无反弹；Gazebo M 命名投票结果（9/18 截止，待公布）。

### 6. rclpy asyncio executor 死锁浮现 + rclcpp ABI 检查完善：executor 与质量门双线推进

**发生了什么：** 两条与「核心框架质量」直接相关的进展 [4]：

- **rclpy asyncio executor 发现死锁**：buildfarm 上 rclpy 的 async node/service/client 测试持续 120 秒超时（rclpy#1719），PMC 纪要披露 Nadav Elkabets 在准备 ROSCon 演讲时**发现了 asyncio executor 的一个死锁**——这正是他获选 rclpy scoped committer 的直接背景；
- **rclcpp #3276**（9/18）：上周合入的 ABI 兼容性检查（#3262）本周补上了自动发布评论与标签的环节，门禁从「检查」走向「可读的通知」；
- 另有 rclcpp#3273：`benchmark_executor` 在 Ubuntu Resolute 上持续超时，skye.galaxy 怀疑卡在多线程 executor，与 jmachowinski 一起做定性排查——两位新 PMC 委员的第一项协同工作恰好就在 executor 性能上；
- rosidl #993 修复 action 字段类型校验；launch #1003 拒绝非法 GroupAction 布尔属性；rosbag2 CI 切换到 Ubuntu Resolute 基础镜像（#2502）。

**为什么值得关注：** executor 主线的剧本越来越清晰：新 PMC 委员（skye.galaxy、jmachowinski）+ 新 rclpy committer（Nadav）+ 一个刚被发现的 asyncio 死锁 + 多线程 executor 性能疑点——所有线索都指向 ROSCon 的 async/executor 专场演讲。对用户的现实提醒：**如果你的系统重度使用 rclpy 异步执行器，rclpy#1719 值得订阅**，死锁修复大概率在会后随 Lyrical/Rolling 更新落地。

**影响层面：** 核心框架 / 正确性与性能

**下一步盯什么：** Nadav 的死锁修复 PR；rclcpp#3273 的定性结论（是挂起还是纯慢）；ROSCon async/executor 专场的内容。

### 7. Nav2 合入 lifecycle manager 合并大重构 + 持续 costmap 修复

**发生了什么：** Nav2 本周 17 个 commit，核心是一项架构变更加一串正确性修复 [7]：

- **#6410「Combine lifecycle managers」**（9/15）：合并 lifecycle manager——这是 Nav2 进程内生命周期管理的结构性简化；
- 正确性修复延续 tsan 清扫线：#6436（controller server 复用防过期 tf 查询）、#6452（校验 costmap 消息数据尺寸，#6430 的 Bug 2）、#6510（新订阅时强制全量 costmap 发布）、#6516（rolling static layer 中 NO_INFORMATION 错误压制其他代价）、#6525（陡峭 footprint 边缘漏清障单元）；
- MPPI 控制器两个状态管理修复：#6531（reset 时刷新噪声分布）、#6537（优化迭代间清空代价缓存）；
- 另有 #6512（Smac Hybrid 在 costmap 分辨率变化后的搜索状态修复）、#6513（AxisGoalChecker 径向容差参数）；
- 发行侧：**Nav2 1.5.2（9/16，Jazzy 线）发布**，但 Lyrical 的 Nav2 release 被 sloretz 压到会后（见信号 1）。

**为什么值得关注：** 上周的 tsan 并发清扫本周进入「平台期后的深水区」——从显式 data race 转向状态一致性（MPPI 迭代间状态、costmap 订阅时机、tf 过期）这类更隐蔽的正确性问题。#6410 的 lifecycle manager 合并则预示着 Nav2 在精简运行时组件数量，与全社区「做减法」的基调一致。生产用户注意：**1.5.2 已进 Jazzy，但 Lyrical 用户本周拿不到 Nav2 更新**。

**影响层面：** 生态项目 / 架构演进与正确性

**下一步盯什么：** #6410 合并后的行为回归报告；Nav2 Lyrical release 会后的放行时间；MPPI 状态修复是否解决社区报告的漂移类问题。

## 前沿议题

1. **嵌入式 ROS 2 的路线之争悄然升温**
   fj-blanco 的 Zephyr 原生 Cyclone DDS 栈（ESP32-S3 直连 RTPS，无 agent）+ 进行中的 rmw_zenoh_pico Zephyr 移植 + micro-ROS 传统的 XRCE-DDS agent 架构——MCU 侧第一次出现三条可对照的技术路线。作者明确目标是「同一硬件上对比嵌入式 RMW 路径」，这个基准一旦发布，将直接影响资源受限平台的选型。

2. **ISO 21423 与车队互操作的开源化**
   InOrbit 把 ORO 作为 ISO 21423 参考实现开源（支持 ROS 2 + Open-RMF），加上 Discourse 上 Open-RMF 下一代空间约束设计的讨论——车队管理层正在重演单机层曾经历的「标准 + 开源参考实现」双轮驱动。多机/ fleet 系统的架构师应读一遍 ORO 的抽象划分。

3. **Executor 问题成为 ROSCon 前的暗线**
   asyncio executor 死锁（Nadav）、多线程 executor benchmark 疑点（skye.galaxy + jmachowinski）、events executor 推广（上周）——三条线在三位新任治理成员手中交汇。PMC 纪要点名 ROSCon 的 async node / logging / executor 专场为 PMC 重点关注场次，executor 架构的下一步走向大概率在会上显形。

4. **仿真数据标准的合流前夜**
   REP 158（OpenUSD）双 PMC 投票 + gz-sim EnTT 重构 + MuJoCo 后端能力补齐——「USD 做场景描述、gz-sim 做仿真、MuJoCo 做接触物理」的具身智能训练管线各层都在本周动了一格。ROSCon 的 Physical AI 场次值得重点关注。
