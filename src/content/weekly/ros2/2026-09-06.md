## 总判断

本周 ROS 2 的主旋律是**「ROSCon 前最后冲刺：Lyrical 冻结同步落地、治理层换届投票启动、以及『依赖版本钉死』这一老大难问题第一次被拿到 PMC 桌面上寻求体系化解法」**。最值得关注的三件事：其一，**Lyrical 本周 freeze + sync**（9/1 PMC 纪要明确），同时 Humble sync 排期下周、Jazzy 正在清理回归、Rolling 同步自动化 PR 进入评审——四条发行线同时在动，是 ROSCon 前典型的发布管理高峰；其二，**PMC 换届选举选票已发出**（skye.galaxy、jmachowinski、andrew_symington 拟任委员，nuclearsandwich、audrow 转 emeritus），且第二批 committer 将首次采用「scoped access」限定范围写权限——上周预告的治理变革本周进入执行阶段，Bazel 工作组则明确推迟到 andrew_symington 正式入委之后；其三，**rmw_fastrtps#906 的依赖钉版本讨论**触发了 cottsay 提出的更重要方案：启用 package format 3 中早已存在但基本无人使用的**版本兼容标志**，把「构建时依赖版本」传导进下游 Debian/RPM 包约束，从体系上杜绝「只更新一个包、整个栈 ABI 崩掉」的事故。工程侧，SIG Physical AI 开始定期向 PMC 汇报，其 WG1 的零拷贝 rosidl 概念已跑出 proof of life（4MB 图像、Fast DDS 共享内存、约 1 kHz / 1 ms）。

### 2. rmw_fastrtps#906 引出体系性方案：用 package format 3 的版本兼容标志杜绝「局部升级炸全栈」

**发生了什么：** MiguelCompany 在 PMC 提出 rmw_fastrtps#906——**钉死依赖版本**。动机很具体：某个共享包发生 ABI break 后，只更新了 `rmw_fastrtps` 的用户会发现整个栈在脚下崩掉。讨论迅速升级：

- cottsay 指出钉版本造成「两处需同步维护」，而现有发布自动化不会更新这些 pin，catkin_pkg prepare-release 也不会，「在几百个包的发布季会非常痛苦」；
- clalancette 建议改用「大于等于」约束而非等号，并指出这是**全栈问题**，不是 Fast DDS 特有；
- **cottsay 提出更优的通用路径：package format 3 已有版本兼容标志（version compatibility flag）但基本没被使用**。若正确打通，包的依赖可以被锁定到「构建时的版本」，并强制传导到下游 Debian/RPM 包约束中——「局部更新搞坏系统」将变得不可能。cottsay 主动提出与 MiguelCompany 合作把这件事做成体系方案。

**为什么值得关注：** 这是 ROS 2 二进制分发模型的深层缺陷第一次被 PMC 级人物认领：apt 世界里 ROS 包之间只有「依赖名」没有「ABI 代际」约束，任何一次 sync 的不完整更新都可能产生运行时崩溃。若 version compatibility flag 方案落地，影响面是整个 buildfarm 的打包逻辑与所有发行版的升级安全性——比上周的 ABI 自动检查原型（tomoyafujita）更进一步：一个管「防出错」，一个管「错了也炸不了」。

**影响层面：** 工程化 / 分发与打包体系 / ABI 稳定性

**下一步盯什么：** cottsay 与 MiguelCompany 的协作产出形态（REP？buildfarm 改动？）；version compatibility flag 在 Debian 打包链路的实际传导验证；与 ABI 检查原型（帖子 57477）是否合流为「ROS 2 ABI 治理」组合拳。

### 6. 诊断体系大讨论：ros2_medkit 解释「为什么不扩展 /diagnostics」——状态流 ≠ 故障模型

**发生了什么：** ros2_medkit 团队（9/4）发布长文，正面回答「为什么不扩展 diagnostic_msgs / diagnostic_updater / aggregator」这个被问了一年（包括 ROSCon 审稿人）的问题。核心论点：**status 是信息，fault 是可查询、可操作的模型，后者无法通过给前者加字段得到**。具体论证：

- REP 107 体系是「实时状态流」：aggregator 按 name 只保留最新一条、覆盖式更新，rqt 只缓存 30 帧——**没有「故障」这个东西的身份**：不知何时开始、复发几次、是否仍活跃、谁确认过；
- 很多故障源根本不是 ROS 节点（电机驱动里的 MCU、独立固件的传感器），driver 静默时 aggregator 只能说 STALE；
- 「它还活跃吗？确认它、改它背后的配置、把当时的录包给我」——这些操作需要一个**独立于 ROS graph、持有带地址与动词的故障记录的服务**。ros2_medkit 的实现：`Fault` 消息（fault_code、AUTOSAR DEM 式防抖生命周期 PREFAILED→CONFIRMED→HEALED→CLEARED、occurrence_count）、确认时自动抓 freeze frame（16 个话题）+ 写 MCAP ring buffer（故障前 5s 后 1s）、SQLite 持久化、挂到 SOVD（ISO 17978）实体树、全套 REST/SSE API 不需要加入 DDS graph；
- `/diagnostics` 仍是输入：bridge 把 OK/WARN/ERROR/STALE 映射为 PASSED/故障事件，现有 diagnostic_updater 节点零改动即可获得故障码、生命周期与历史。

**为什么值得关注：** 这是连续第四周「可观测性/可运维」主线的延续（ros2probe→ros2_pulse→官方拟删旧 topic statistics→本周故障管理），但层次不同：前几周解决「看得见」，本周解决「看得见之后如何形成可操作的运维闭环」。AUTOSAR DEM 防抖 + SOVD 实体树 + REST 外暴露的组合，明显是汽车行业诊断方法论向 ROS 的移植——与 ROS-Industrial 渗透率提升的大背景同频。作者抛给社区的问题（「fault record 是否应成为共享 ROS 消息」）可能演化为新的 REP 级讨论。

**影响层面：** 工程化 / 诊断与运维体系 / 生产部署

**下一步盯什么：** ROSCon 上该议题的 talk 与社区反馈；fault 记录标准化的呼声是否成形；ros2_medkit 与官方诊断栈的边界讨论结果。

### 7. ROS 2 安装入口之争：一条命令安装 apt 路径的提案引发信任边界讨论

**发生了什么：** MrBearing 提案为 apt 安装路径提供「一条命令安装器」（9/3 帖为回应质疑的第二轮论述）。质疑点是 `curl | sh` 反模式；作者的反驳相当扎实：

- 现状的信任边界本来就是「从项目控制的 URL 经 HTTPS 下载 .deb 并 sudo dpkg -i」——脚本并不扩大它，且脚本可读；
- 历史事故清单：2019 安全事件轮换 key、2021 apt-key→signed-by 迁移、**2021-05 key 过期（官方 Docker 镜像与 setup-ros 在假期周末全红）**、**2025-06-01 key 再次过期引入 ros-apt-source**——每次事故都是全社区的 Dockerfile/CI/Ansible 副本同时坏，然后各自修；
- 真正诉求是「**一个有人维护的单一入口**，让文档、Dockerfile、CI 都指向它」：可选形态包括 ros2-apt-source .deb 的无版本稳定 URL（peci1 此前已要求）、把 ros2-apt-source 推进 Ubuntu 官方源（`sudo apt install ros2-apt-source`，最干净但工作量最大）、或 ros2/ros-infrastructure org 下托管的「下载-阅读-运行」脚本。

**为什么值得关注：** 这接上了上周「ROS 融入主流软件工程工具链」（ros-conan、Bazel WG、Windows CI）的主线——安装入口是新人体验与 CI 稳定性的第一道关。2021/2025 两次 key 事故的「全社区同时坏、各自修」模式，本质是缺少单一维护入口的结构性后果。作者明确表示希望 PMC 认领所有权——这与本周 rosdistro 内容准则讨论（emersonknapp：「我们要么立政策，要么承认没有」）同属「社区基础设施的权责清晰化」趋势。

**影响层面：** 工程化 / 安装与分发入口 / 新人体验

**下一步盯什么：** PMC 是否认领该入口；无版本稳定 URL 与「进 Ubuntu 源」两条路径的可行性结论；ROSCon 基础设施话题中的相关讨论。

## 工程化观察

- **回归风险**：本周最大单点是 Nav2 #6435（costmap 并发）——已修复，随下次 sync 落地前，使用 Rolling/Lyrical 源码构建的团队应确认是否包含。rclcpp #3243 的参数范围收紧可能在升级后暴露「一直就错但没人管」的参数声明。rosbag2 #2476 的 SequentialReader API break 仅影响 Rolling 上的子类实现者。
- **平台迁移前奏密集**：MoveIt2 修 Ubuntu 26.04 clang 构建、Gazebo 弃 FreeImage 并对齐 Resolute、Homebrew/Gazebo 弃 macOS Intel（ROS 2 侧尚无对应公告，需继续盯）、Windows 多播 socket 耗尽回归——四条线共同说明 **2027 周期的平台基线迁移已实质启动**，维护多平台 CI 的团队现在就该盘点对 Ubuntu 26.04 与 macOS 架构的依赖。
- **「权责清晰化」成为横向主题**：rosdistro 内容准则（mjcarroll 起草中）、ROS 2 安装单一入口提案、scoped access committer 权限、version compatibility flag——四件看似无关的事共享同一个方向：把过去靠惯例运转的环节变成有人认领、有文字可依的制度。对下游用户的直接收益是可预期的稳定性。
- **可观测性连续第四周有新货**：ros2_medkit（故障管理闭环）+ fastdds_transport_viz（传输层可见性）。判断不变：社区主线已从「功能可用」转到「可观测、可运维」，且开始触及「标准化」（fault record 是否该成共享消息）。
