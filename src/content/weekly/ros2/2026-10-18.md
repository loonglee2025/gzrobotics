## 总判断

ROSCon 之后的第三个工作周，官方主线从「清账与摊平」转向**两条并行的深水区**：一条是把内存拷贝从消息容器层彻底解开（`rosidl::Buffer` 后端化 + `rmw_fastrtps` 的 buffer-aware 订阅路径），另一条是把 Gazebo 的开发平台生命周期按硬日期收口（Homebrew 断供、维护者审计、EOL 排期）。

上期留下的两个悬而未决的问题本周同时闭环：**10/12 Humble sync 如期落地**（40 个新包、446 个更新），且 `snapshots.ros.org` 上 `humble/2026-10-12` 快照已经出现——同时补出的还有 `jazzy/2026-10-05` 与 `lyrical/2026-10-05`。也就是说上期判断的「固定快照做回归这条工作流本周没有闭环」，本周已恢复可用 [1][2]。

本期的技术重点是那件还没被广泛讨论的事：**ROS 2 正在把「非 CPU 内存」变成消息的一等存储后端**。核心侧 `rosidl` 已在 rolling 与 lyrical 两条发行线里发布 `rosidl_buffer` / `rosidl_buffer_backend` / `rosidl_buffer_backend_registry` / `rosidl_buffer_py`，配套的 `rosidl_buffer_backends`（`cuda_buffer`、`tensor_msgs` 的 `ExperimentalTensor`、`torch_conversions`、`libtorch_vendor`）已以 0.1.2-1 进 apt；文档侧 rolling 已上线「About / Using / GPU Buffer Transport / 写一个 backend」四篇。而**本周最密集的提交发生在 RMW 侧**：`rmw_fastrtps` 一周合并 4 个 buffer-aware 相关 PR、仍有 8 个 open，`rmw_implementation` 补了 3 个针对性测试 [3][4][5][6]。

安全侧出现了一次容易误读的时间差：Fast-DDS 的两个 GHSA 修复（`GHSA-hhx6-8qfx-8c23`、`GHSA-5fgv-8wxq-3f69`）**作者日期是 10/02 与 10/08，但真正进 master 的 committer 日期都是 10/14**——按推送节奏算，它们属于本周。累计已确认编号至少 9 个，全部在 GitHub Advisory 数据库中仍是 404，最新 release 仍是 v2.14.7（09-08）[7][8][9]。

治理侧则继续「静默」：**ROS PMC 纪要仍停在 9/29**，10/6 与 10/13 两周均缺席，`ROS Meetings for Week of …` 也停在 9/21。10/14 的 Open Robotics HQ 帖给出解释——TGC 会议排在「下周」，纪要将后补；ROSCon 善后、季度切换与年末六场区域 ROSCon 的协调吃掉了官方带宽 [10][11]。所以这一期判断治理信号的正确姿势是：**以 Gazebo PMC 与各工作组会议为准，把 ROS PMC 的缺口当作已知延迟而非停摆**。

需要如实标注的边界有三处：`snapshots.ros.org` 的 `kilted/` 与 `rolling/` 目录本次抓取均返回 404（尚不能区分是路径变更还是未启用）；`rmw_fastrtps_cpp → rmw_fastdds_cpp` 改名本周**没有启动**（PR 列表里没有相关条目）；ros2_control 本周**没有 6.13**，rolling/lyrical 仍是 6.12.0。另外 `snapshots.ros.org` 的 TLS 证书主机名不匹配问题依旧存在，取索引只能用 `http://`。

## 本周关键信号

### 1. Humble 10/12 sync 落地 + 快照补齐：上期两个未闭环问题同时关闭

**发生了什么：** 10/12 官方发布 Humble 同步公告，tag 为 `humble/2026-10-12`，口径是 **40 个新包、446 个更新**（amd64）；新增清单以 `easynav 0.5.0` 一族为主体（导航栈新实现，Humble 首次进入），另有 `as2-platform-mavlink` 等 [1][2]。同一周内 `snapshots.ros.org` 补出了 **`humble/2026-10-12`**、以及上期缺失的 **`jazzy/2026-10-05`** 与 **`lyrical/2026-10-05`** 快照 [12]。rosdistro 侧本周 91 次提交、79 次 bloom、30 个包，五条发行线的分布接近均摊（rolling 16、lyrical 16、jazzy 17、humble 18、kilted 12）。

**为什么值得关注：** 上期报告明确写了两条「未闭环」：Humble sync 是否如期、10/5 之后快照是否补出。本周两条都关掉了，这意味着「用固定快照做可复现回归」这条工程流程重新可用——对需要长时间对齐版本矩阵的团队（尤其还在 Humble 产线上跑的生产系统）是实质性改善。另一方面，Humble 作为 2022 年的 LTS 仍在以「40 新 + 446 更新」的规模接收同步，说明生态对它的投入没有随新发行版上线而退潮。

**影响层面：** 发行节奏 / 生产环境可复现性 / Humble 生态活跃度

**下一步盯什么：** 下一轮 rolling/lyrical/kilted/jazzy 的 sync 排期（本周只有 Humble 一条线）；`kilted/`、`rolling/` 快照目录 404 是路径变更还是未启用。

### 2. `rosidl::Buffer` 后端化：GPU 零拷贝通道从文档走进 RMW 主路径

**发生了什么：** 核心侧能力已经就位且已发行：`rosildi` 在 rolling/lyrical 里带上了 `rosidl_buffer`、`rosidl_buffer_backend`、`rosidl_buffer_backend_registry`、`rosidl_buffer_py`；`rosidl_buffer_backends` 以 **0.1.2-1** 同时出现在 rolling 与 lyrical 的 rosdistro 中（包：`cuda_buffer`、`cuda_buffer_backend`、`cuda_buffer_backend_msgs`、`tensor_msgs`、`torch_conversions`、`libtorch_vendor`）[3][6]。文档形态也齐了：rolling 上有「About rosidl::Buffer backends」「Using rosidl::Buffer backends」「Transporting GPU buffers」「Writing a Buffer Backend」四篇，明确写了**默认行为完全不变**（`Buffer<T>` 隐式转换为 `std::vector<T>&`，老代码不用改），只有订阅端显式设置 `acceptable_buffer_backends` 才会走非 CPU 路径，且**当前只有 `rmw_fastrtps_cpp` 实现了协商**，其它 RMW 会静默回落 CPU [13][14]。

本周的推进集中在 RMW 的实现细节上。`rmw_fastrtps` 合并了 4 个：`#927` 上报 buffer-aware CPU 通道的消息主发布者 GID、`#934` 在 buffer-aware take 路径上遵守 `ignore_local_publications`、`#936` 为 buffer-aware 订阅支持 `rmw_take_sequence`、`#924` 移除旧式 `ament_export_*` 调用 [15]。仍有 8 个 open 且在 10/19 仍在更新：`#949` 为 buffer-aware 类型上报 deadline/liveliness 事件、`#951` 修正新消息计数、`#930` 修 `rmw_wait` 的伪 QoS 事件唤醒、`#944` 在 loaned/dynamic take 路径也遵守 `ignore_local_publications`、`#946` 对未知 `acceptable_buffer_backends` 名称报错、`#938` 为 participant 内共享的加速 buffer topic 做引用计数、`#942` 让离场的 buffer-aware 订阅被遗忘以免挡住传统订阅 [16]。`rmw_implementation` 同步补了三个「带 `uint8[]` 字段的消息类型」的针对性测试（`take_sequence`、`ignore_local_publications`、`publisher_gid`）[5]。社区侧，rosdistro 在 10/16 把第三方脚本 `memfd_buffer_backend` 改名为 `shmem_buffer_backend`（仓库 `dskkato/shmem_buffer_backend`，source-only），是往官方命名收敛的动作 [17][18]。

**为什么值得关注：** ROS 2 此前有两条减拷贝路径——intra-process（同进程传 `unique_ptr`）与 loaned messages（RMW 管内存做共享内存传输）——但都解决不了「数据本来就在 GPU 上」的情况：相机直出、点云、推理框架产出的张量，拷回 `std::vector<uint8_t>` 再发出去，等于把加速器的意义抹掉一半。`rosidl::Buffer` 是从**容器层**解决这件事，`.msg` 里仍写 `uint8[]`，存储换成 vendor 后端（CUDA VMM IPC 跨容器共享、Qualcomm HTP 的 dma-buf），配套 `tensor_msgs/ExperimentalTensor` + DLPack 的 `torch_conversions` 桥给出「张量怎么走 ROS 2」的标准答案 [6]。对做感知/VLA/多相机管线的团队，这是数量级级别的数据面变化；对普通用户则是一条**零迁移成本**的旁路。

**影响层面：** 消息层 / RMW 分层 / 数据面性能 / Physical AI 管线

**下一步盯什么：** buffer-aware 路径上的 QoS 语义是否等价补齐（`#949`/`#930`/`#951`）；accelerated buffer topic 在 participant 内共享的引用计数正确性（`#938`）；回落行为是否可观测——目前「静默回落 CPU」没有对用户暴露诊断项；`rmw_zenoh` 有 loader 但支持到哪一步还需单独核实。

### 3. Fast-DDS 两个 GHSA 修复本周才真正进 master，累计 9 个编号仍全部未公开

**发生了什么：** 本周 master 上有两个「私有评审后 squash 合并」的安全提交落地：`980f1926`「Avoid RTPS statistics submessage missmatch」（修复 `GHSA-hhx6-8qfx-8c23`）与 `a2c44e78`「Fix GHSA-5fgv-8wxq-3f69」。**关键细节是时间差**：两者的 author 日期分别是 10/02 与 10/08（上两期报告的窗口内），但 committer 日期均为 **2026-10-14**——即它们本周才被合入主干。同期还有 `edc0ed58` 把 fastcdr 升到 2.3.7 [7]。**边界如实标注**：本周抽查的 7 个 GHSA 编号（含上期 5 个与本期的 2 个）在 GitHub Advisory Database 中**全部仍为 404**；Fast-DDS 最新 release 仍为 **v2.14.7（2026-09-08）**；rosdistro 里 jazzy 的 `fastrtps` 仍是 `2.14.7-1`，即**下游拿不到任何一个已修版本** [8][9]。窗口外的 10/19 另有三个功能性修复（TCP 默认配置改进、UDP send timeout 修正、payload pool 空指针竞态）。

**为什么值得关注：** 这条线已经持续一个多月，节奏始终是「同一批人 + 私有评审 + squash」，说明是成建制的安全审计清账而非零散应急。对下游的直接含义没变，但**叙述要点需要修正**：如果只看 author 日期，会误以为本周没有安全动作；按合入日期看，本周实际上是清账周。此外这次修的是 RTPS 统计子消息的匹配逻辑（解析路径），与上两周的 AES-GCM-GMAC、TCP/TLS 一起，覆盖了「解析—加密—会话」三层。

**影响层面：** 中间件安全 / 跨网段与多机器人部署 / 供应链

**下一步盯什么：** 是否出 2.14.8（或 3.x）打包这 9 个修复；Advisory 何时公开（当前 `<3` 的安全公告都还是影子状态，运维无法据此评估风险面）；rosdistro 何时 bloom 新版本到各发行线。

### 4. ros2_control 下游迁移出现分野：mujoco 已迁完，webots 仍停滞；gz_ros2_control 高强度加固

**发生了什么：** 上期点名的两个下游本周给出了不同答案：**`mujoco_ros2_control` 已合并「Migrate to the new Command/StateInterface API」（`#296`，10/14）**，迁移路径完成；而 **`webots_ros2` 的「Migrate webots_ros2_control to the modern Handle export API」（`#1059`）自 9/9 起仍然 open**，本周该仓唯一提交是给 CI 加超时 [19][20]。ros2_control 本体本周 5 个提交，无新版本（rolling/lyrical 仍 6.12.0，ros2_controllers 6.10.0）；`ros2_controllers` 3 个修复里值得注意的是 `#2692`——JointTrajectoryController 在 `on_activate` 里先清空有序接口再重排，属于典型的「激活态二次触发」缺陷 [21]。真正高强度的动作在 `gz_ros2_control`：**一周 8 个提交**，包含「Fixes several crashes」、硬件初始化加可选超时、校验 `update_rate` 并去重参数处理、unit test 补 `GazeboSimSystem` 并修空组件下的 `read()`、include-what-you-use 与导出现代化 [22]；同时社区发起 RFC，要重组 `gz_ros2_control` 的集成测试架构（目标：从「进程/话题存在」升级为「校验关节位置/速度/力矩的实际响应」，合并重复的仿真启动，统一 Rolling 到 Humble 的语义），对应 issue `#964` [23][24]。

**为什么值得关注：** 6.12 的破坏性删除（`Handle` 原始指针构造、按值返回的 export 接口）让下游出现**明确的分野**：跟着走的（mujoco）拿到了新 API 的好处，没跟的（webots）就停在旧栈上——而 webots_ros2 是教学与轻量仿真的主力，它的停滞意味着「同一个自研 controller 在不同发行版要分支」的问题会继续存在一段时间。gz_ros2_control 的这批提交则是另一个信号：**仿真侧的控制插件正在被当作生产组件对待**（崩溃修复 + 参数校验 + 超时 + 单测），这与 Gazebo PMC 本周的测试网络、Thruster 稳定性回移是同一股风。

**影响层面：** 硬件抽象 / 控制器生态 / 仿真桥 / 发行版兼容

**下一步盯什么：** `webots_ros2#1059` 是否会在这个季度内落地；ros2_control 6.13 与 ros2_controllers 6.11 的节奏；gz_ros2_control RFC 的结论是否会带来 CI 时长与覆盖率的可量化变化。

### 5. Gazebo PMC 10/12：Homebrew 断供时间表与维护者审计——治理层面的硬日期

**发生了什么：** 10/12 Gazebo PMC 纪要给出了一串**带日期的生命周期决定**：Ionic 于 **2026 年 12 月** EOL；因 Homebrew 计划在 **2027-01-10** 移除 FreeImage（`homebrew-simulation#3298`），**Harmonic 与 Fortress 的 Homebrew 支持将在同日终止**（PR `#3598`/`#3597`）；Homebrew 的 Qt5 支持将在 **2027 年 5 月**移除，官方将起草公告。治理流程上有两个变化：预发布版本不再要求逐 PR review，改为**提前公告 + 最多 24 小时等待窗口**后合并；跨多包/多阶段的 backport 建议**等所有相关改动进 main 且下游 CI 跑完**再回移。基础设施侧：新的 macOS Tahoe runner（`mac-six.tahoe`）上线并开始 bottling，Python 3.15 引起的 formula 测试失败正在修，`gz-sim#4047` 在所有测试套件里统一设置 `GZ_IP` 以避免意外的组播行为。技术侧本周 `gz-physics` 有 8 个提交集中修 bullet-featherstone 的运动学模式（非基座 link 速度、动态 link 的 kinematic joint 锁定、position limits、多 link 模型），与纪要里「kinematics mode improvements」完全对应 [25][26]。组织侧：批准 Cherrie Lu 为 mentee committer，Luca Della Vedova 的 mentee PMC 投票进行中，维护者审计 Phase 2 截止 10/16 [25]。

**为什么值得关注：** 对 macOS 上做 ROS 2 + Gazebo 开发的团队，这不再是模糊的「未来会不支持」，而是**两个具体日期**：2027-01-10（Harmonic/Fortress 的 Homebrew 支持终止）与 2027-05（Qt5 移除）。仿真器作为开发环境的可获取性，比仿真器本身的 API 变更更快地影响团队排期。而「预发布不再逐 PR review、backport 等下游 CI」这两条流程调整，直接对应过去一段时间里「上游动了、下游炸了」的常见事故形态。

**影响层面：** 开发环境 / 仿真生态 / 发布流程 / 下游 CI 约定

**下一步盯什么：** Harmonic/Fortress 的 Homebrew 官方公告文本；维护者审计 Phase 2 的最终分配结果（谁主责哪些包，直接决定响应速度）；Python 3.15 与 Ubuntu resolute 的构建尾巴是否清完。

### 7. 两个「安静但真实」的缺陷修复：执行器定时器 use-after-free 与 ros2cli 的回环客户端

**发生了什么：** `rclcpp#3315`「Fix use-after-free of removed timers in EventsCBGExecutor」10/16 合入——事件驱动的回调组执行器在定时器被移除后仍会访问已释放对象，这是会随机表现为崩溃的**正确性缺陷**，不是性能或 API 问题 [28]。同周 `rclcpp#3278` 保证异常不逃逸析构函数、`#3322` 让 `function_traits` 支持 `noexcept` 可调用对象 [29][30]。`ros2cli#1241`「Accept loopback clients in LocalXMLRPCServer」10/16 合入，修的是 `ros2` CLI 的本地 XMLRPC 服务在只监听回环的环境下无法接受连接的问题（容器化与受限网络下常见） [31]。`rclpy#1666` 修了「立即 shutdown」的 flaky 测试，`rosbag2` 两次清理弃用 API（`argparse.FileType`、`Invoke`） [32][33]。

**为什么值得关注：** 这类提交不会被写进任何公告，但决定「系统会不会偶发崩溃」。执行器 use-after-free 属于最难复现、最容易在客户的长时间运行场景里冒出来的一类问题；`ros2cli` 的回环监听则直接影响容器/远程开发工作流。判断核心框架健康度，这类修复的密度比新特性更可靠。

**影响层面：** 客户端库 / CLI 工具 / 运行时稳定性

**下一步盯什么：** 是否有 backport 到 jazzy/lyrical（本次看到的都是 Rolling 主线提交）；执行器相关是否还有同源问题（`EventsCBGExecutor` 的移除时序模型整体是否被复审）。

## 工程化观察

**一、本周的执行模式是「路径可选 + 逐条补测」。** `rmw_fastrtps` 每合并一条 buffer-aware 路径，`rmw_implementation` 就补一条「带 `uint8[]` 字段」的测试（`#294`/`#296`/`#297` 三个几乎同构的 PR）。这是新特性在成熟 RMW 里落地的最可靠形态：先让路径可选、默认不启用，再用针对性测试把每条路径钉住。反过来看，open 的那 8 个 PR 全是「某条路径还没对齐语义」（QoS 事件、计数、loaned、dirty-list 生命周期）——说明真正的成本在语义一致性，不在传输本身。

**二、清理型提交仍是主线，但重心从「删功能」转到「删旧式写法」。** 本周 `rmw_fastrtps#924` 移除 `ament_export_include_directories`/`ament_export_libraries`，`rosbag2` 两次清 `argparse.FileType` 与 `Invoke`，`ros2_control#3696` 做 include-what-you-use，`gz_ros2_control#980` 统一 `package.xml` 元数据与现代 CMake 导出。上期是删用户可见功能（topic statistics、`rmw_fastrtps_dynamic_cpp`，后者已在 Makoa 发行说明中记为「Changes since the Lyrical」条目 [42]），本周是删内部旧约定——影响面小，但对「自己维护下游包」的团队意味着轮子更少、坑更浅。

**三、发行量回落但分布更均匀。** rosdistro 91 提交（上期 200）、79 bloom、30 个包、五条线 12–18 之间；本周只有 Humble 一次 sync。对比上期的「双 sync + 五线均摊」，本周是「单 sync + 五线均摊」，说明常规维护模式下每天都在向所有活跃发行线推进，sync 只是阀门。

**四、平台迁移的尾巴始终存在，且集中在测试基础设施。** 本周可见的尾巴：macOS Tahoe runner 上线并 bottling、Python 3.15 引致的 formula 失败、Ubuntu resolute（Lyrical）构建、`euslisp/jskeus` 的 resolute key 修复、rosdep 检查 `*-updates`/`*-security` 套件、以及 `gz-sim#4047` 统一 `GZ_IP`。这些条目单看都是琐事，合起来说明 ROS 2 的成本中心正在从「写功能」转向「维持 N 个平台的构建与测试可信」。

## 前沿议题

**1. 张量成为 ROS 2 的一等公民。** `tensor_msgs/ExperimentalTensor` + `torch_conversions`（DLPack 导入/导出）+ `libtorch_vendor` + CUDA/Qualcomm 后端，把「模型推理的在环数据」纳入 pub/sub 数据面 [6]。这条线的意义不在于零拷贝本身，而在于**ROS 2 开始承认「消息的存储介质」是接口的一部分**：一旦 backend descriptor 上了 wire，跨设备（GPU/CPU/NPU）的订阅协商就要被写进契约。这会重新定义「topic 兼容性」的判据。

**2. 任务规划层正在重新起势。** PlanSys2 换 Kairos（支持 PDDL 2.1/3、负前提、析取、条件效果、派生谓词、timed initial literals、偏好、object fluents，PDDL+ 在路上）与 STN-based BT builder（真正的时序语义、允许「一个动作在另一个动作期间发生」）[37][38]。这跟「LLM 做高层规划、PDDL 做可验证落地」的路线是同一个方向上的两端——LLM 侧需要的就是这种「能被形式化验证的执行层」。

**3. OTA 是否是已解决问题？社区的答案是「不是」。** 10/18 的讨论帖里，作者自建了基于容器 + GitHub Releases + 健康检查回滚的更新器，坦承「更新器无法更新自己」「A/B 各有取舍」；回复里既有指向另一条「车队固件更新怎么不砖机」的旧帖，也有商业产品方直言 OTA 是「真实机器人上岗的第一道瓶颈」 [43]。对生产团队这是明确的信号：**部署侧的空白仍然存在**，而 ROS 2 官方并没有对应的项目。

**4. AI 辅助运维的工具链在成形。** DDS Monitor Pro 预告 MCP 集成（让 AI 直接检查 ROS 2 系统状态）、ros2_pulse 把探测数据接到 Prometheus/Grafana [34]。两者共同点是：**把「观测」从 CLI 短命令搬到可持续的数据平面**，这在多人协作与远程运维场景里是刚需。
