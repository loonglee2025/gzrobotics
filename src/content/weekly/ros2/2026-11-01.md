## 总判断

本周的核心事件是一件「还没定下来的标准」：**REP-0157 从设计文档走进了 PMC 议程**。10/27 的 ROS PMC 会议上，这份题为 *Minimal Overhead Messaging Support Using Runtime Agnostic Memory Layouts* 的草案被正式讨论，并因内容过多决定在 11/4 单独开会 [1]。它的野心是把 `rosidl` 从「每种语言一套内存表示」改成「语言无关的连续内存布局 + 语言特定的视图（view）」，从而让零拷贝第一次有可能跨语言、跨进程、跨加速器成立——草案里那句自我诊断很直白：*截至 2026 年初，支持零拷贝的中间件无法跨越语言边界，因为不存在共同的运行时表示；而且变长成员的内存布局是非局部的，因此即便在同一语言内适用范围也极窄，窄到连 `std_msgs/msg/Header` 这样的标准消息都不合格* [2]。同一周，这条线的第二层——`rmw_fastrtps` 的 `acceptable_buffer_backends`（GPU/加速器内存后端）通道——把上期悬着的四个 open PR 全部合入，同时暴露出十几个新 issue [3][4][5][6]。也就是说：**标准层在画图纸，实现层正在做验收，而验收单上写满了缺陷**。

第二条主线是**「谁在写代码」被正式摆到治理桌上**。10/20 的 ROS PMC 纪要记录了两件事：`AGENTS.md` 从 `rclcpp` 移交给 `ros2/ros2` 以便全组织统一（issue #1887），以及「新增一个 GitHub Action 强制 PR 模板、不合规的提交直接挡掉」[7][8]。Gazebo PMC 同周的议题更硬：buildfarm 被外部贡献淹没，于是开始讨论「是否对每个外部贡献自动跑 CI」「维护者是否应有更高优先级」「如果一个 PR 里带恶意二进制怎么办」[9]。而现实是——本周合入的提交里 AI 署名已经是常态：`Assisted-by: OpenAI Codex (GPT-6.1 Sol)`、`Co-authored-by: Claude Opus 5.5`、`Assisted by: Gemini`、`AI-assisted-by: OpenAI Codex (GPT-5.6 Sol)` 各出现在不同仓库的关键修复里 [10][11][12]。治理在讨论「怎么管」，代码已经在用。

第三条是**「无效输入得到有效数值」这个缺陷家族的集中爆发**，且这次集中在导航栈这一层。`nav2_mppi_controller` 修了一个倒车专用配置（`vx_max == 0`）下绝对限速计算把 `vx_max` 除以基准速度得到 `inf`、进而让 `vx_max=NaN`、`vx_min`/`vy`/`wz` 全部变成无穷大的缺陷 [13]；`nav2_costmap_2d` 修了「足迹各边的致命代价在聚合时被吞掉」[14]；`nav2_amcl` 修了读数少于 `max_beams` 时步长为 0、循环永不前进的死锁 [15]。这三条都不是崩溃，而是**机器人在错误的状态下继续运动**——上期讲的是中间件层的静默失败，本周它下移到了运动规划层。

发行层面本周异常安静，但安静本身是信号：**零 sync 公告、零新增快照、Kilted 11 月 EOL 进入倒计时、Lyrical 的 sync 因 API 破坏被官方推迟到 10/27–11/3** [8][16]。rosdistro 提交量从上周的 232 次 / 74 个包回落到 128 次 / 31 个包，同时 `ecl` 与依赖它的 `kobuki` 系列被从 Rolling 中整体移除 [17]——ROS 1 时代那一层嵌入式抽象的最后一块二进制支持，随这次 PR 一起消失。

上期七个待跟踪项，本周闭环三个：`rmw_fastrtps` 的 `#955`/`#958`/`#960` 全部合入（`#953` 仍 open，因为它等的是 `#952`）；TGC 的 ROS 代表、3 名新 committer、M-turtle ROSboss 三个投票已发出；`webots_ros2#1059` 第三次停在 open，且自 9/9 起再无更新 [18]。仍未闭环的是 Fast-DDS 的安全版本——本周又合入一个 GHSA 修复，但**最新 release 依然是 v2.14.7（09-08），这是连续第五期下游拿不到补丁** [19][20]。

## 本周关键信号

### 1. REP-0157：`rosidl` 要被重写成「语言无关内存布局 + 语言特定视图」

**发生了什么：** 10/27 的 ROS PMC 会议专门讨论了 REP-0157，因覆盖面太大，PMC 决定在 **11 月 4 日 9:30 PST** 单开一场会，会前材料是 REP 草案与 ROSCon 2026 的演讲《Breaking through the zero-copy bottleneck with REP-0157》[1]。翻草案本身，它的结构比 Discourse 通告里那句「向后兼容、支持 C/C++/Python」复杂得多 [2]：

- **核心主张**：`rosidl` 消息不再是「语言特定的数据结构」，而是**语言无关连续内存布局上的语言特定视图（view）**，写（发布）有时有界、读（订阅）无界。
- **三个新抽象**：`views`（语言习惯的访问接口，可拥有内存也可仅引用）、`storage`（按消息布局组织的、语言特定的存储描述符）、`shapes`（约束每个变长成员尺寸的「形状」，用于外部托管内存时的分配）。每个成员的内存块被包成 `rosidl_memory_t {void* address; int attributes;}`——`attributes` 用来标注这块内存属于哪个**设备**、哪个内存**区段**、允许什么操作，这正是异构计算（GPU/加速器）真正需要的元信息。
- **只改一个 rmw API**：`shapes` 在构造时通过 publisher/subscription 的 options 传入，RMW 据此判断「有界消息」并据此做 loan 或校验。
- **尺寸显式编码在内存表示里**（shapes 不上线传输），参考实现选择了**二进制兼容的序列化格式**——即 XCDR 既是线格式也是内存格式。

**为什么值得关注：** 草案的动机段落是这十年来对 `rosidl` 最尖锐的一次自我批评：`rosidl` 是 ROS 2 最老的子系统之一，2013 年的初始研究，C 与 C++ 生成器从 Alpha 1 起就各有一套运行时表示；即便后来陆续加了消息 loan、共享内存传输、进程内通信、type adaptation/negotiation，这些「零拷贝」都只是**窄形式**——因为设计前提就不允许通用形式。这句话解释了一个长期被归因于「实现不给力」的现象：**为什么 `rclcpp` 的进程内通信被公认是关键使能者，而跨进程的零拷贝却始终只有少数传感器消息能用**。如果 REP-0157 落地，「跨语言零拷贝」这个从 2016 年就写在路线图上但从未实现的能力第一次有了规范路径，而它同时是 GPU/加速器内存通道（见信号 2）能否从「单语言特异实现」变成「通用机制」的前提。

需要纠正一处容易被误读的地方：**通告里说的「向后兼容」是有限度的**。草案 *Backwards Compatibility* 一节写得很清楚——为了保证「拥有型视图」与「引用型视图」接口一致，必须放弃标准库类型；C++ 与 Python 可以靠 inline namespace / import 技巧做软迁移，**而 C 语言没有这些特性，这次重设计必然破坏 C 的 API 兼容性**，只能用「线格式兼容」来保证新旧代码共存的渐进路径 [2]。评估迁移成本时，这条差异比任何特性列表都重要。

**影响层面：** 消息层规范 / 零拷贝数据面 / 异构计算 / 客户端库 API

**下一步盯什么：** 11/4 专门会议的结论（是否进入 PMC 投票、是否有明确的目标发行版）；`rosidl_memory_t` 的通用分配 API 在草案里还标着 TBD，这一项不定，backends 侧就无法通用；C 语言迁移路径是否给出「旧 API 保留多久」的时间表。

### 2. buffer backends 进入验收期：上期四个 open PR 全合并，同时开出十几张缺陷单

**发生了什么：** 上期报告的「下一步盯什么」里点的四个 PR，本周**全部合入**：`#955` 在 buffer-aware 路径之前先校验 `rmw_take_with_info` 参数（10/26）、`#958` 让 buffer-aware 发布失败返回错误（10/28）、`#960` 修 participant 初始化期间的 buffer 发现（10/29）、`#951` 让 buffer-aware 订阅报告正确的「新消息数」（10/29），另加一个 `#930` 修 `rmw_wait` 里虚假的 QoS 事件唤醒 [3][4][5][6][21]。`rmw_zenoh` 侧同步跟进：`#1089` 让 buffer-aware 路径的发布错误处理与基础路径一致 [22]。

但更值得看的是**这一周新开的 issue**，它们把这条通道的真实成熟度摊开了（仓库 `ros2/rosidl_buffer_backends`，23 star，已含 `cuda_buffer`、`cuda_buffer_py`、Qualcomm 实现与 `torch_conversions`）[23]：

- `#947` **内部 buffer 通道的 topic 出现在 ROS 图里**——为实现加速通道而建的中间 topic，用户用 `ros2 topic list` 就能看见 [24]；
- `#948`/`#949` **buffer-aware 消息类型不上报 deadline 与 liveliness QoS 事件** [25]；
- `#952`/`#953` `wait_for_all_acked` 对 buffer-aware 类型**在消息真正被确认前就返回 true**，且不等 buffer 通道的 DataWriter [26]；
- `#961`/`#962` backends 收到的是**加速通道的 GID 而非发布者的 GID** [27]；
- `#963`/`#964` `rmw_serialize` 把**尺寸估算值当成了序列化长度**返回 [28]；
- `#965`/`#966` 对接受非 CPU 后端的订阅做序列化 take：`rmw_fastrtps_cpp` 上**忙等死循环**，`rmw_zenoh_cpp` 上**返回描述符字节**——同一 API 两个实现两种错误行为 [29]；
- `#937`/`#938`/`#939`/`#942` 一类 bookkeeping 缺陷：加速订阅先于同进程发布者销毁时报「Failed to delete participant」；退出的 buffer-aware 订阅者不从列表里移除，导致**后来的普通订阅者收不到消息** [24]。

同期 `rosidl_buffer_backends` 一周三个 CUDA 修复：`#26` 没有可用 CUDA 设备时不要 abort、`#27` 创建读事件时不带 IPC 标志、`#29` 让 CUDA IPC dispatcher 随最后一个 manager 一起停 [30]。

**为什么值得关注：** 这组 issue 的性质高度一致：**它们全都在「加速路径」与「基础路径」之间制造语义差**。QoS 事件不上报、`wait_for_all_acked` 说谎、GID 给错、序列化长度给错、内部 topic 泄漏到用户可见的图里——对上层的算法工程师来说，这些都不是「功能少一点」，而是**同一套 API 在两种消息类型下行为不同**，而差异只在负载或拓扑变化时才暴露。上期把 `#946`（未知 backend 名显式报错）理解为「把静默失败改成显式错误」，本周这批 issue 说明那只是第一层：显式报错的前提是**路径本身语义正确**，而加速路径现在还没有。对任何打算在 Rolling 上试 `cuda_buffer` 的团队，本周的信息量是「能用，但不要相信它的 QoS 语义」。

**影响层面：** RMW 分层 / GPU 零拷贝 / QoS 语义一致性 / ROS 图可观测性

**下一步盯什么：** `#947`（内部 topic 泄漏）与 `#948`（QoS 事件）谁先被修——前者影响所有用户的观感，后者影响依赖 deadline 做看门狗的系统；`#965` 两个实现的行为分歧最终按哪一边对齐；`#953` 是否本周合入（它是上期名单里唯一剩下的）。

### 3. 同一个「显式失败」纪律延伸到共享内存：一段非异常的错误把恢复路径彻底绕开

**发生了什么：** Fast-DDS 本周三个提交，其中两个是同一条线的上下游。`#6598`（Michael Carroll）修的是一个**故障不是 C++ 异常、因而恢复代码永远跑不到**的问题：`check_sanity()` 只校验了分配器，空闲块遍历沿偏移指针走却不检查是否越界；`open_port_internal` 随后调用 `find<PortNode>()`，沿命名索引继续走更多偏移指针。**一个进程被突然杀掉留下的不一致段**会让这次遍历直接 fault——而 fault 不是异常，`open_port_internal` 里的恢复逻辑因此永远不会执行 [31]。修法是加一个带边界检查的遍历（`tree_sanity.hpp`），在解引用前验证每个节点在段内、对齐、父子链一致，同时检查 `construct_func` 的返回（此前创建失败被忽略、段却被标成已初始化，调用方拿到一个 segment manager 为空的段，首次使用即 fault）。`#6559` 修的是性能：打开一个**健康**的共享内存端口默认要等 333 ms，因为健康检查只在监听者的计数变化后才认它活着，而空闲监听者每 `port_wait_timeout_ms` 才刷新一次（正好是 `healthy_check_timeout_ms / 3`）；改成主动请求心跳后从 333 ms 降到约 1 ms [32]。第三个提交是安全修复 `e31068a3`（GHSA-w75r-338m-pc5x，反序列化字符串时检查空终止符），**author 日期 10/08、committer 10/28** [19]。

**为什么值得关注：** `#6598` 这个案例值得单独记一笔，因为它暴露的是**错误处理模型本身的漏洞**：代码作者写了恢复逻辑，也写了边界假设，但两者之间隔着一个「假定只会抛出异常」的错误模型——而指针越界产生的是 SIGSEGV。这类缺陷在共享内存、mmap、zero-copy 这些直接操作裸内存的子系统里是系统性风险，且**用异常测试用例永远测不出来**。把它和上期的「静默失败改显式错误」并置看，这一周的进展是：显式错误的**返回值层**基本补齐了，接下来是**故障域层**（什么算可恢复、什么必须让进程退出）。

**影响层面：** 中间件可靠性 / 共享内存与裸内存安全 / 安全发行节奏

**下一步盯什么：** GHSA-w75r-338m-pc5x 至今仍是 **404（未公开）** [19]，而 Fast-DDS 最新 release 仍是 **v2.14.7，2026-09-08** [20]——这意味着下游连两个月前的问题都还没拿到修复版本，这条线已是连续第五期无闭环。GHSA 何时公开、2.14.8 或 3.x 何时打包这五个安全提交，是本报告里最该催的一项。

### 4. 构建时间被当成一等工程问题：`rosidl` 上 PCH、ccache 能命中 PCH、CI 学会跳过无关文件

**发生了什么：** 本周有三个互不相干但指向同一目标的提交。`rosidl#988`（William Woodall）给三个生成目标加上 `target_precompile_headers`——`rosidl_typesupport_introspection_cpp`、`rosidl_typesupport_introspection_c`、`rosidl_generator_c` [10]；`rviz#1911` 给 GCC 加 `-fpch-preprocess`，因为**不加这个参数 ccache 根本无法缓存用到 PCH 的编译单元** [33]；Gazebo 侧的 `release-tools#1558`/`#1575` 让 Jenkins 在 PR 只改 Markdown、GitHub workflow、Bazel 元数据、LICENSE 或 `package.xml` 时跳 Linux/macOS CI，通过 PR 描述里的 `SKIP_CI_FOR_IGNORED_FILES` 触发 [9]。此外 `ros2cli#1248` 加了颜色输出工具与测试、`moveit2#3937` 把 pre-commit 的 Python 钉到 3.14、`ros2_control#3726` 与 `ros2_controllers#2723` 各有一次 pre-commit 钩子版本升级 [34]。

**为什么值得关注：** 这几件事单看都是「小优化」，合起来是一条明确的判断：**ROS 2 生态开始把「编译等待」当作配额来管理，而不是当作不可避免的税**。`rosidl` 生成的 typesupport 是几乎所有 ROS 2 包编译时的公共瓶颈（每个包都要包含一堆生成的 introspection 头），给它上 PCH 的收益是乘性的；而 `rviz#1911` 这个细节更说明问题——**PCH 与 ccache 默认互相抵消**，加 PCH 而不加 `-fpch-preprocess` 会让增量编译的收益归零，这类「优化互相打架」的坑只有在真的测过构建时间后才会被发现。加上 Gazebo 的 `SKIP_CI_FOR_IGNORED_FILES`（这是本周 Gazebo PMC 讨论「buildfarm 被淹没」的直接产物），可以看到**外围设施的成本压力正在反向塑造核心库的构建方式**。

**影响层面：** 构建性能 / 开发者体验 / CI 成本

**下一步盯什么：** PCH 是否推广到 `rosidl_generator_py`（Python 侧才是慢的主战场）；`rmw`/`rclcpp` 是否跟进；`SKIP_CI_FOR_IGNORED_FILES` 会不会被误用成「跳过本该跑的 CI」（与信号 5 的门禁问题相邻）。

### 5. AI 参与贡献进入治理层：`AGENTS.md` 上收到组织级，PR 模板变成硬门禁

**发生了什么：** 10/20 的 ROS PMC 纪要里，`@mjcarroll` 提出用 `AGENTS.md` 统一 AI agent 的行为规范，原本是针对 `rclcpp` 的 PR（`rclcpp#3366`），现在**移到 `ros2/ros2` 以便统一管理**（issue #1887）；同时「新增一个 GitHub Action 强制执行 PR 模板，不符合模板的提交直接被挡」。issue 正文列出的 agent 行为要点很具体：**没有人类构建、测试并读过 diff 之前不许开 PR；绝不允许声称做过没跑过的验证；必须用 PR 模板；必须遵守 sign-off 与披露规则** [7][8]。Gazebo PMC 同周从另一个角度碰到同一问题：buildfarm 被外部贡献「stormed」，讨论要不要对每个外部贡献自动触发 CI、维护者是否应有更高优先级、以及**如果一个 PR 里带恶意二进制怎么办** [9]。与之形成对照的是本周的代码：`nav2_mppi_controller#6707` 署 `Co-authored-by: Claude Opus 5.5`，`nav2_costmap_2d#6678` 署 `Co-Authored-By: Claude Opus 5.5`，`rmw_fastrtps#951`/`#958` 署 `Co-authored-by: Claude Opus 5.5`，`gz-sim#4140` 署 `Assisted-by: OpenAI Codex (GPT-6.1 Sol)`，`gz-sim#4101`/`#4077` 署 `Assisted by: Gemini`，`rclpy#1752` 署 `Co-authored-by: Claude Fable 5.1`；而 `ros2_documentation#7297`（subordinate nodes 教程）在 PR 描述里专门回答了「是否使用生成式 AI」并列出本地验证清单 [10][11][12][35]。

### 6. `rclpy` 跨进程异步与生命周期：两个「只在多节点/多进程下才出现」的修复

**发生了什么：** `rclpy#1723`（Nadav Elkabets）改的是 `AsyncNode` 的唤醒机制：`#1496` 曾允许把 Python 函数注册为 RMW 回调，pybind 在调用前从 **DDS 线程获取 GIL**——这在同进程节点间能用，**跨进程则很快死锁**。新实现模仿 `asyncio` 自身的跨线程唤醒方式（`loop.call_soon_threadsafe` 写一个字节到 socket），**为每个实体加一对 wakeup socketpair**；作者报告在高负载下延迟显著改善，原因是极端负载时 asyncio 事件循环可能长时间持有 GIL、把等待 GIL 的 RMW 线程饿死。同时删除了 `set_on_new_*_callback` 的 pybind 绑定（因为无法避免与 Python 回调死锁），改为 `set_on_new_*_wakeup` [12]。另一个 `rclpy#1752`（Tomoya Fujita）修的是关停时的清理**跳过每隔一个节点**：`BaseNode.destroy_node()` 调用 `Context.untrack_node()` 从 `__node_weak_ref_list` 删除节点，而 `_cleanup()` 正在遍历同一个列表，删除导致后续元素前移，于是**每第二个被追踪的节点都被跳过，其 `rcl_node_t` 在关停后仍然存活**；修法是遍历快照并在之后清空列表 [36]。

**为什么值得关注：** `#1723` 是这个季度 `rclpy` 方向上最重要的一次架构调整，因为它承认了**「RMW 回调里碰 GIL」这条路走不通**，并改用一个与 GIL 无关的唤醒原语。对写 Python 异步 ROS 2 的人，含义是：`AsyncNode` 从「同进程实验品」变成了**可用在多进程拓扑上的东西**；而删掉 `set_on_new_*_callback` 绑定是一次 API 收缩，任何直接依赖它的代码必须改。`#1752` 则是那种「看上去只是泄漏」、实际会让**关停后的资源（共享内存段、端口、participant）留在系统里**的缺陷——在容器反复启停的部署里它会表现为「重启后莫名资源不足」，这类问题用单元测试几乎不可能发现，只有遍历式清理这种结构性缺陷才会暴露。

**影响层面：** Python 客户端库 / 异步编程模型 / 进程生命周期与资源回收

**下一步盯什么：** `AsyncNode` 在多进程高负载下的基准是否能复现作者的延迟改善；`set_on_new_*_callback` 的移除是否回移到 Jazzy（会破坏现有用户）；`#1752` 是否回移——它以 `Claude Fable 5.1` 协作完成，值得留意同类「迭代中修改集合」的清理路径是否还有别处。

### 7. 导航栈的安全类缺陷：无效参数得到有效数值，机器人继续运动

**发生了什么：** `navigation2` 本周 10 次提交里至少四件是「不会崩溃但会让机器人做错事」的：`#6707` 在绝对限速模式下 `Optimizer::setSpeedLimit()` 用基准 `vx_max` 做除数，**倒车专用配置（`vx_max == 0`）使比值变成 `inf`，于是 `vx_max` 成 `NaN`、`vx_min`/`vy`/`wz` 全部无穷大**；修法是 `vx_max` 非零时用 `vx_max`、否则用 `|vx_min|` 作参考速度，两者都为零则拒绝更新并保留当前约束 [13]。`#6691` 修 costmap 足迹各边的**致命代价在聚合时被吞掉**，改为逐边检查致命代价后再聚合，收尾边与 Python 检查器同步 [14]。`#6711` 修 AMCL 束模型在**读数少于 `max_beams` 时步长为 0、循环永不前进**的挂起，改用与 LikelihoodFieldModel 相同的守卫 [15]。`#6700` 修 MPPI 动态参数更新**写入已经销毁的局部变量**，并把 motion model 参数改为静态（运行时改直接拒绝，因为优化器不会重载运动模型）[37]。另外 `#6678` 修 costmap 实际发布频率低于设定值——抖动让「严格大于一个周期」的判断反复落空，2 Hz 的设定在 5 Hz 更新下实际只有 1.67 Hz，非整数倍周期永远向上取整 [11]；`#6696` 修碰撞检测关闭时 graceful controller 崩溃、`#6685` 只校验能到达目标的模拟轨迹 [38]。

**为什么值得关注：** 这四条的共同形态是**「配置合法但语义无效」**：倒车专用机器人把 `vx_max` 设成 0 完全合法；足迹边缘的致命代价在数学上就是「取最大值」，聚合时被判成 unknown 并不违反任何类型约束；短扫描是真实激光雷达在近距遮挡下的常态。它们都不触发异常、不写错误日志，**只是让速度指令变成一个数学上合法、物理上荒谬的值**——在 costmap 那条里则是让避障代价消失。上期判断「静默失败正在被系统性地改成显式错误」是以中间件为中心的观察；本周可以补一条：**这个纪律在应用层的推进速度明显慢于框架层**，而应用层的静默失败代价更高，因为它直接作用在执行器上。

**影响层面：** 运动规划与避障 / 控制安全边界 / 参数校验

**下一步盯什么：** MPPI 的限速逻辑是否被抽成一个带单测的独立函数（`#6707` 已加两个单测，但同类「除以基准」的写法在其它 critic 里是否还有）；`#6700`「motion model 参数运行时不可改」是否需要写进文档——这类「运行时拒绝」如果不写文档，用户会以为是 bug。

## 工程化观察

**1. 「零拷贝」这个词在 ROS 2 里已经被用了十年，但它一直没有定义。** REP-0157 的价值不在于提出了多少新概念，而在于它终于把「零拷贝」拆成了可验收的三件事：内存布局语言无关（storage/shape）、尺寸可约束（bounded on write）、跨语言视图一致（view）。对照本周 buffer backends 的十几张缺陷单可以看到，**过去十年所谓的零拷贝每次都只实现了其中一件**：消息 loan 只解决「不复制」，共享内存传输只解决「同机」，type adaptation 只解决「单一语言」。任何团队在做「我们的链路是零拷贝」的技术判断时，建议按这三件事分别核对，而不是按功能名核对。

**2. 缺陷的形态正在从「崩溃」转向「语义错误」，而后者更难发现。** 本周最有代表性的四条缺陷——`wait_for_all_acked` 在消息未确认时返回 true、`rmw_serialize` 返回估算而非实际长度、buffer backends 拿到错误的 GID、costmap 吞掉致命代价——全都是「函数返回了合法类型的值，但语义是错的」。这类缺陷的共性是**接口签名不变、单测不易覆盖、在低负载下不复现**。`rosbag2#2545` 提供了一个反向样本：那三个 xfail 里有一个是 `future.get()` 在 `wait_for()` 超时后照样阻塞，于是「丢失的响应」表现为 60 秒 ctest 超时且没有任何诊断信息——**测试框架本身也在制造语义错误**。一个可操作的工程习惯：任何 `get()` / `value()` / `wait_*()` 之后，先确认「失败时这里返回什么」，而不是「成功时返回什么」。

**3. AI 参与已经把「署名」变成一行必须读的信息。** 本周 8 个以上关键提交带 AI 协作署名，覆盖 rclpy、rmw_fastrtps、nav2、gz-sim、docs 五个仓库；`ros2_documentation#7297` 甚至在 PR 模板里专门回答「是否使用生成式 AI」并列出 `sphinx-lint`/`codespell`/`sphinx-build -W`/`pytest` 四项本地验证结果 [35]。同一周 PMC 决定用 `AGENTS.md` 与 PR 模板 Action 来约束这件事 [7][8]。这意味着**读 PR 的方式要改**：diff 仍然可信，但「作者声称验证过」这个信号的价值在下降，PR 描述里的验证清单（跑了什么、在哪跑）变成主要依据。对内部的代码评审流程，建议直接采纳 `AGENTS.md` 那四条：人类先构建/测试/读 diff 才开 PR、不声称未跑过的验证、用模板、sign-off 与披露。

**4. 发行侧的「API 破坏」正在变成硬约束。** Lyrical 因 API 破坏推迟 sync 1–2 周 [8]，`ros2_control` 的 `is_limited()` 从返回引用改成返回值并明确写进 release notes [52]，`rclpy` 删除 `set_on_new_*_callback` 绑定 [12]，`ecl`/`kobuki` 因无二进制被整体移出 Rolling [17]。四件事都在说同一个趋势：**维护者现在愿意为「正确性」付出一次 API 破坏的代价，并把成本转移给下游**。对自己维护的包，最实用的准备是——**把「我依赖的 API 是否在 rolling 上仍存在」变成 CI 的一步**，而不是等 sync 之后 apt 升级失败。

**5. ROS 1 时代的抽象层正式退场。** `ecl` 从 Rolling 消失的方式很说明问题：移除理由不是「不维护了」，而是「在 rolling 的任何平台上都没有当前版本的二进制」——它是在构建矩阵里**自然死亡**的，跟着走的还有 `kobuki_core`、`kobuki_velocity_smoother`。对仍在使用 kobuki/ecl 的团队（教学与入门场景里不少），含义是**必须换基线，且新基线只能选已 EOL 之外的四条线** [17]。

**6. 组织侧的两件杂事，都是「收尾」的形态。** 本周 HQ 的周记（对应 10/19 那周，10/27 才发）只写了三件事：困扰数月的**审计接近完成**、本地 ROSCon 的排期（西班牙已结束、意大利下周、比利时 11/25–26、印度与土耳其 12 月初）、以及因 OSRA 成员咨询而做的**商标执法**——「我们不喜欢告诉别人不能在产品名里用 ROS，但不保护就会失去商标」[58]。这三件事对技术选型没有直接影响，但对判断组织精力分配有用：审计算是长期占用管理带宽的事项，它一结束，PMC/治理类议题（如信号 5 的 `AGENTS.md`、Bazel WG）推进会快一些。同期新闻帖把项目负责人交接、Robotheca（475 个可构建开源的机器人目录）、Robostack monorepo 一并列出 [59]。

## 前沿议题

**REP-0157 的三个待解问题。** 草案本身留了明显空白：`rosidl_memory_t` 的通用（反）分配 API 标着 **TBD**——而这一项恰恰决定 backends 能否通用（现在每个 backend 自己管分配，语义就不统一）；`shapes` 不上线传输，靠「内存表示里编码尺寸」来推断，这意味着**内存表示必须与线格式二进制兼容**（草案选了 XCDR 这条路），那么对齐、填充、字节序的处理就成了性能与兼容性的交汇处；C 语言没有 inline namespace，必然破坏 API，草案只给出「线格式兼容 + 新旧代码共存」的渐进路径，没有时间表 [2]。11/4 的会议如果能在这三点上给出方向，REP 才有可能离开 Draft。

**异构内存后端会不会标准化。** `rosidl_buffer_backends` 已经有 CUDA（含 Python 绑定）与 Qualcomm 两家的实现，`torch_conversions` 也在里面 [23]。但本周的 issue 显示，「后端」这一层的语义契约还很不完整：谁分配、谁释放、GID 用谁的、QoS 事件算谁的、序列化返回什么。REP-0157 若定义了 `rosidl_memory_t` 的统一语义，这些问题会一次性收敛；若没有，就会出现「每个 backend 一套行为」的分裂。

**`ros2_control` 的非实时数据通道。** 本周 `nnarain` 提出一个真实且长期被绕开的缺口：硬件设备的**字符串型命令/状态接口**（固件版本、校验和、序列号、诊断字符串）目前在 `ros2_control` 里没有原生支持，只能用 `control_msgs/GenericHardwareStatus` 勉强覆盖一部分，或用旁路 topic（issue `ros2_control#3491`）[60]。他同时点出了关键张力：字符串不是实时安全的，但**这些数据走的是和其他状态一样的通路**。这是一个「要么在实时框架里开一个非实时通道、要么承认它属于旁路」的设计选择，附带的另一个观察是 `ros2_control` 里 handle 的生命周期问题（`Best practices for accessing non-controls information alongside ros2_control` 这个 2024 年的帖子本周被重新关联）。

**降级链路里的传输层 QoS。** `Zenoh + RaptorQ` 的公开原型把问题讲得很具体：室外地面机器人在树荫、建筑、起伏地形下持续丢包 15–30%，可靠重传会触发**队头阻塞**——紧急指令被进度图之类的批量数据堵死。原型用 RFC 6330 喷泉码把一个资产切成交织的源块，收端凑够任意足够多的 droplet 即可比特精确重建（演示里 158.5 KB → 36 KB 压缩、111 个 droplet、3.82 秒广播、零重传）；同时用令牌桶把地图流限到 128 kbps（`Priority.DATA_LOW` + `CongestionControl.DROP`），高优先级命令走 `Priority.DATA_HIGH` + `CongestionControl.BLOCK` 并带 Ed25519 签名 [61]。这条线值得跟的原因不是「又用一个新协议」，而是它示范了**在同一条 Zenoh 会话里用优先级 + 拥塞策略把两类流量隔开**——这是 ROS 2 的 QoS 模型目前表达不了的东西。

**subordinate nodes 终于有权威文档了。** `create_sub_node()` 这个 API 存在多年但从未进官方文档，本周合入的概念页把它讲清楚了：子节点**共享父节点的 context、日志、参数、时钟、定时器**，但在 ROS 图里有**自己独立的身份**（独立的名字与命名空间）；教程对比了 subordinate nodes / composable nodes / standalone nodes 三种选择，并给出「相对 sub-namespace 如何解析成有效命名空间」的完整例子 [35]。对做多传感器模块化封装的团队，这解决了「一个驱动里挂多个逻辑节点」时长期靠口口相传的经验问题。
