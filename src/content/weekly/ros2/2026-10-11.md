## 总判断

ROSCon 之后的第二个工作周，官方节奏从「共识落地」转入「清账与摊平」。三件事同时在收敛：**发行节奏**（10/5 Jazzy/Lyrical 双 sync 落地，10/12 Humble 已预告冻结，rosdistro 一周 200 次提交、185 次 bloom，五条发行线接近均摊）、**核心分层**（`rmw_fastrtps_dynamic_cpp` 从 rcl/ros2cli/rosbag2 一并移除，topic statistics 整条链路下线，ros2_control 一周连发 6.11/6.12 并删掉已弃用的 Handle/export API）、**构建与依赖**（rclcpp 去掉旧式 `ament_export_*`，Nav2 用窄化 include + 目标导出削减构建依赖并加规则防回潮）。

两条值得单独拎出来的结构性动作：其一是 **Gazebo PMC 10/05 抛出的 `rosdistro-extension`**——让 ROS 发行版直接从源码或二进制消费 Gazebo 包，可能取代 `gz_*_vendor` 包，这与会后已接受的 REP-158（资产互操作）是同一件事的两面：格式上互通、发行上互认 [1][2]。其二是 **Fast-DDS 继续以私有评审流水线修安全**：本周新增 5 个 GHSA 编号（AES-GCM-GMAC ×3、TCP/TLS ×2），修复类别首次从解析路径扩展到加密与会话传输层，但**三周累计 7 个已确认编号的修复全部未公开、未进入任何 release** [3][4][5]。

需要如实修正上期的一处乐观判断：**10/5 sync 之后 snapshots.ros.org 并没有补出新快照**（最新仍为 Jazzy 2026-09-11、Lyrical 2026-09-18、Humble 2026-09-14），「固定快照做回归」的工作流本周没有闭环 [6]。另外，**ROS PMC 本周没有新纪要**（最新仍停在上期已覆盖的 9/29），官方频道这一周的治理信号主要来自 Gazebo PMC 与社区会议 [2]。

数量化的生态盘面：10 月是区域 ROSCon 的密集月——中国上海 10/16–17、英国爱丁堡 10/21–23、新加坡 10/23–26（已售罄）、西班牙瓦伦西亚 10/27–28；OSRA 10/6 发布 ROSCon Global 2026 结案博客，确认这是史上最大一届（1000+ 现场、40+ 国家、325+ 公司、58 赞助商、2000+ 直播观众），2027 年定档波兰克拉科夫 [2][7]。

## 本周关键信号

### 1. 核心仓库集体「做减法」：`rmw_fastrtps_dynamic_cpp` 与 topic statistics 双双下线

**发生了什么：** 两条独立的清理线在本周同时落进 Rolling：

- **RMW 收敛**：10/5 合入 `rmw_fastrtps` #923——删除 `rmw_fastrtps_dynamic_cpp`，并把 `rmw_fastrtps_shared_cpp` 合并进 `rmw_fastrtps_cpp`；理由是 dynamic 实现自 ROS 2 Crystal 起就是 Tier 2、新特性只落进 `rmw_fastrtps_cpp`，而共享实现包引入过 ABI 破坏 [8]。上游追踪 issue 明确三步走：**删 dynamic → 合并 shared → 把 `rmw_fastrtps_cpp` 改名为 `rmw_fastdds_cpp`**，动机只有一句「Less is more!」[9]。本周连带删除发生在外围：rcl #1349、ros2cli #1331、rosbag2 #2523 [10][11][12]；CI 任务与 buildfarm 配置的删除仍未完成 [9]。
- **topic statistics 下线**：10/5 rclcpp #3203「移除半成品统计实现，替换成可由第三方包实现的接口」，官方在 PR 里明确标注**这是 user-facing 行为变更——我们在删一个已有功能**，理由是近期 bug 报告显示几乎无人使用 [13]。配套清理：ros2 #1878 移除 `libstatistics_collector`、rclcpp #3316 把它从质量声明里删掉、ros2_documentation #7245 删除 topic statistics 文档 [14][15]。

**为什么值得关注：** 这是 ROS 2 核心层少见的「成体系删功能」而非加功能。对使用方的实际影响分两层：一是任何依赖 `rmw_fastrtps_dynamic_cpp` 的配置（老教程、动态类型/自省型实验）在 Rolling 上会直接失效，且这不是弃用警告而是移除；二是 topic statistics 移除后，`ros2 topic hz` 一类依赖统计的行为要等第三方包按新接口补位——而接口已经开放，属于「官方退位、生态补位」的典型动作。长期看，RMW 从 4 个实现收敛到 1 个 Fast-DDS 包（Zenoh、CycloneDDS 作为生态实现并行存在），中间件层的心智负担在下降。

**影响层面：** 核心框架 / RMW 分层 / 用户可见行为

**下一步盯什么：** `rmw_fastrtps_cpp → rmw_fastdds_cpp` 改名时 `rmw_implementation` 的默认名与旧环境变量告警如何处理；buildfarm/CI 里的 dynamic 任务何时清干净；是否有社区包承接 statistics 接口。

### 2. ros2_control 一周连发 6.11.0 / 6.12.0，弃用 API 正式删除（破坏性）

**发生了什么：** 10/5 发布 6.11.0、10/7 发布 6.12.0（rolling 与 lyrical 同步进 rosdistro；ros2_controllers 6.10.0 同行）[16]。核心动作是 #3610「Remove deprecated methods from Rolling and Lyrical」：删除 raw-pointer 形式的 `Handle` 构造，以及按值返回的 `on_export_state_interfaces()` / `on_export_reference_interfaces()`，替代物为返回 `SharedPtr` 的 `on_export_state_interfaces_list()` / `on_export_reference_interfaces_list()`；**其中 `on_export_reference_interfaces_list()` 是纯虚函数，意味着每个 chainable controller 都必须实现它，哪怕不导出任何 reference interface** [17]。官方同周更新迁移文档（migration.rst +154/−26）[18]，并于 10/8 在论坛发布破坏性变更公告 [19]。

**为什么值得关注：** ros2_control 是硬件抽象层的骨架，任何自研 `hardware_interface`、自研 controller、以及基于它的仿真桥都会受影响。更关键的是**删除只发生在 Rolling 与 Lyrical，Humble/Jazzy/Kilted 保留旧栈**——同一套自研控制器代码从本周起必须按发行版分支。下游迁移已经在跑：mujoco_ros2_control 的迁移 PR 已合并，而 **webots_ros2 的迁移 PR 自 9/9 起仍然 open**，是本周最需要自查的下游 [20][21]。

**影响层面：** 硬件抽象 / 控制器生态 / 发行版兼容

**下一步盯什么：** webots_ros2_control 迁移何时落地；6.12.0 的 changelog 与是否跟出 6.12.1；Kilted/Humble 的迁移时间表是否与 Lyrical 对齐。

### 3. Gazebo PMC 10/05：`rosdistro-extension` 想让 ROS 直接消费 Gazebo 包

**发生了什么：** 10/5 Gazebo PMC 纪要中演示了 `rosdistro-extension` 项目——它扩展 ROS 的发行元数据索引与 Python 库，使 ROS 发行版既能以**源码导入**方式消费 Gazebo 包（ROS 从源码重建上游包，例如 Rolling 直接吃 Gazebo Jetty），也能以**二进制导入**方式消费，**可能取代 ROS 中的 Gazebo vendor 包**，从而简化发布维护；待解问题是 CMake shim 与上游 CI 测试的责任归属 [1]。同场其他决定：Gazebo M 版正式定名 **Mosaic**；gazebo-tooling 将自动化 Homebrew 发布流程中的 build bottle 步骤（带防重复护栏）；gz-sim 增加 macOS 上 WindowServer/Metal 检测（macOS 不再需要 XQuartz）；gz-transport 为 Jetty 准备 Zenoh backport 与两处 ABI 兼容修复；sdformat 有一个支持 URDF 1.1 capsules 的 PR 待评审 [1]。

**为什么值得关注：** `gz_*_vendor` 包是 ROS 与 Gazebo 之间最别扭的一层——版本绑死、补丁传递慢、改名/ABI 问题要两边同步。若 rosdistro-extension 落地，Gazebo 上游版本可以直接进入 ROS 发行元数据，Gazebo 将以「发行版级」身份参与 ROS 的发行模型，vendor 包这一层可能整体消失。这与上期 REP-158 的路径完全一致：先在格式上定义互操作（单位、光照、ROS 接口 schema），再在发行上互相承认。对下游资产/仿真团队而言，需要开始关注「我依赖的是 vendor 包还是上游包」这个问题。

**影响层面：** 仿真生态 / 发行元数据 / 依赖策略

**下一步盯什么：** rosdistro-extension 的规范与 PR 进展；`gz_sim_vendor`（本周 rolling 刚更新到 0.5.4）等 vendor 包是否停止更新；CMake shim 与上游 CI 的解法。

### 4. Fast-DDS 再修 5 个 GHSA（加密 + 传输层），仍全部未公开、未发布

**发生了什么：** 两个「私有分支评审后 squash 合入」的提交在 10/5 进入 master：`Fix several security advisories in AES-GCM-GMAC`（对应 GHSA-f6cw-h682-xw3p、GHSA-mg54-9fm8-xvf3、GHSA-j4xc-fjx8-wfg4）与 `Fix Several TCP TLS CVEs`（对应 GHSA-6pwr-vh77-2x8m、GHSA-58x7-8g6g-mpp8）[3][4]。**边界如实标注**：这 5 个编号（连同前两周的 2 个）在 GitHub Advisory Database 中查询**全部仍为 404**；Fast-DDS 最新 release 仍是 v2.14.7（2026-09-08），即三周累计 7 个已确认编号的修复**没有任何一个进入发布版本**；本周 rosdistro 侧也没有 `fastrtps`/`fastdds` 的 bloom 提交，只有 `fastcdr 2.3.7` 进了 rolling/lyrical/kilted（10/9）[5][16]。

**为什么值得关注：** 修复类别首次从 DATA_FRAG/RTPS 解析路径扩展到 **AES-GCM-GMAC（加密会话语义）与 TCP/TLS 传输**——也就是「建立可信通道」的那部分代码，而这恰好是跨公网、多机器人、需要安全通信的部署最依赖的路径。节奏上仍是同一批人、同样的私有评审 + squash 格式，说明这是成建制的安全审计清账，而不是零散应急；但对下游的直接含义没有变化：**暴露在不信任网络中的 Fast DDS 用户，当前拿不到任何已修版本**。

**影响层面：** 安全 / 中间件 / 发布节奏

**下一步盯什么：** 5 个新编号的公开时间与影响版本区间；下一个 Fast-DDS release（v2.14.8 / v3.6.x）是否打包这批修复；Humble/Jazzy 的 `ros-*-fastrtps` 包是否 backport。

### 5. 10/5 双 sync 落地，10/12 Humble 冻结预告

**发生了什么：** 10/5 Jazzy sync 以 `jazzy/2026-10-05` 标签落地，官方口径是 **190 个新包 + 312 个更新**，兑现了上期预告的「472 包就绪、零回归」[22]；Lyrical 同批推进（10/5 晚间发出 Lyrical 新包公告）[23]。随后 10/8 官方发出 `Preparing for Humble sync 2026-10-12` 并冻结新 release PR [24]（该帖正文本周因抓取限制未能取到包计数与回归数，边界如实标注）。本周 rosdistro 累计 **200 次提交、185 次 bloom**，bloom 的发行版分布为 rolling 48 / lyrical 39 / jazzy 38 / kilted 33 / humble 27，涉及唯一包数 rolling 42、lyrical 33、jazzy 32、kilted 27、humble 24 [16]。

**为什么值得关注：** 两周内三条发行线完成全量同步，说明冻结-解冻积压正被系统消化。更要紧的是**每次 sync 都会让「APT 环境」与「容器/镜像内的二进制」产生漂移**——不升级的环境跑的是旧包，而 sync 内容本周已经包含 ros2_control 6.12.0、easynav 0.5.0、rmw_zenoh 全五线重发等实际变更 [16]。对生产团队，sync 日是「要么跟、要么钉住」的决策点，而不是通知日。

**影响层面：** 发行版节奏 / 生产部署计划

**下一步盯什么：** 10/12 Humble sync 是否如期、有无回归；snapshots.ros.org 是否补出 10/5 快照；下一轮 sync 轮到哪条线。

### 6. 三条生态线同时强化：Zenoh 全五线重发、EasyNav 0.5.0、Nav2 可靠性批次

**发生了什么：**

- **rmw_zenoh 一次性铺满五条线**：rolling 0.14.0 / lyrical 0.10.7 / kilted 0.6.9 / jazzy 0.2.12 / humble 0.1.11（均为 10/7）[16]。0.14.0 的内容包括底层 zenoh 升级到 1.10.1、去掉不必要的 getter 锁、package.xml 改用 SPDX 标识 Apache-2.0；10/8 还合入 #994「删除实体时在应用线程上关闭它们」[25]。
- **EasyNav 0.5.0** 覆盖 Humble / Jazzy / Kilted / Lyrical，并同时提供两条安装路径：APT（下次 sync 后可用）与 **Pixi（立即可用，且支持 Rolling，不要求系统预装 ROS 2）**；官方强调它与 Nav2 可互操作、提供可直接运行的 PlayGrounds [26]。
- **Nav2 一周 26 次提交**，主体是围绕 TF 时效（staleness）检查铺开的加固——costmap 各层、collision monitor、docking、route、AMCL 初始位姿校验；工程侧还有 #6558 用窄化 include + 目标导出削减构建依赖，并加了一条 Semgrep 规则防止「大 include」回潮 [27][28]。

**为什么值得关注：** 三条线指向同一趋势——**导航/定位栈的竞争点正从「功能有多少」转向「失效模式处理得多干净」**（TF 过期、空点云、重定位竞态、地图切换时序）；而 Zenoh 的跨五线重发说明 DDS 之外的第二条中间件路线已进入常规维护节奏，不再是实验特性。

**影响层面：** 导航栈 / 中间件 / 构建依赖

**下一步盯什么：** Zenoh 版本升级是否引入新回归（Jazzy 侧此前有回归记录）；Nav2 staleness 批次是否伴随参数默认值改动；EasyNav 与 Nav2 的职责边界。

### 7. 生态与治理：ROSCon Global 结案、Open-RMF 开 Office Hours、官方工作组写进治理页

**发生了什么：** OSRA 10/6 发布 ROSCon Global 2026 结案博客，把收官数据与期间的重磅发布一次列全：1000+ 现场与会者、40+ 国家、325+ 公司、45+ 大学、58 赞助商、46 展商、2000+ 直播观众，2027 年定档克拉科夫（10/12–14）；其中**两条此前未进周报**——**Cognex 收购 RealSense**、**Inorbit.ai 发布 ISO 21423 的首个参考实现 OpenRobOps** [7]。Open-RMF 项目新增例行 Office Hours，线下地点为 **Intrinsic 新加坡办公室**，线上可视频接入 [29]。ros2_documentation 本周把「Official Working Group」章节补进 Governance 页面（#7173，跟进 osra-policies-and-procedures #16）；同时把 NVIDIA Isaac ROS 加进了 adopters 名单 [30][31]。

**为什么值得关注：** 三条都关乎「谁长期维护、按什么规则维护」。RealSense 是全球 ROS 生态里最普及的深度相机，被工业视觉厂商收购后驱动的维护承诺需要重新评估（本周 librealsense2 2.59.1 / realsense2_camera 4.59.1 刚在四条线上发布，短期维护仍在进行）[16]；Inorbit 把机器人运维（observability）映射到 ISO 标准，是「标准先行于生态」的路径；Open-RMF 把例行会议开进 Intrinsic 办公室，配合 ROSCon 上 Intrinsic Core 的「新一代 ROS 发行版」定位，厂商在社区治理中的**实体存在**在加强，而官方把工作组写进治理页则是把这层关系制度化 [7][29][30]。

**影响层面：** 生态格局 / 治理机制 / 硬件驱动

**下一步盯什么：** RealSense 驱动在收购后的维护与许可证姿态；Open-RMF 与 Intrinsic 的职责边界；Official Working Group 的名单与章程文本。

## 工程化观察

1. **非 Ubuntu 平台正在补齐**：本周 rosdistro 的非 bloom 提交集中在平台规则——`pipx` rosdep 规则、`libcrypt-dev`、RHEL 的 `libdc1394-dev`/`libftdi1-dev`、NixOS 的 `libgit2`/`libquazip1-qt5-dev`，以及 **Fedora 44 加入 Rolling 支持平台** [16]。配合上期 PMC 的 ARM64 RPM 请求，可以看出「平台支持面」是当前基础设施投入的主线之一。
2. **发行元数据开始有缓存层**：rosdistro 合入「在 release tag 创建时发布持久分布缓存」（#50112）[45]，属于 buildfarm/索引侧的可用性工程，对镜像与离线环境的消费体验有直接影响。
3. **厂商往官方命名空间收拢**：KUKA 驱动迁移到官方 `kuka-ros`（#54429），Orbbec 相机 `orbbec_camera_v2` 2.10.6 三线发布 [16]。与「vendor 发行版」趋势互补：厂商既做发行版，也把驱动收回自有命名空间。
4. **构建系统向现代 CMake 目标导出收敛**：rclcpp 删除冗余的旧式 `ament_export_*`（这些包已使用 `ament_export_targets()`）[32]，rcl 统一语言标准配置，Nav2 削减 include 并加 Semgrep 规则 [27]——三者合并看，是一次跨仓库的「构建债」清理。
5. **安全修复与发布的错配仍在扩大**：Fast-DDS 三周 7 个编号、14+ 个修复提交，release 侧仍是 v2.14.7（9/8）[5]，rosdistro 侧无 fastrtps bloom [16]。修复能力与交付能力之间存在明显时滞，下游需要把「自行 backport」列入预案。
6. **快照缺口**：10/5 sync 后 snapshots.ros.org 未产生新快照（Jazzy 2026-09-11、Lyrical 2026-09-18、Humble 2026-09-14）[6]。上期把快照视为「回归测试闭环」的判断本周不成立，需要观察是流程时滞还是机制变更。

## 前沿议题

1. **声明式节点接口（NoDL）**：ROSCon 演讲「The Legible Node」的会后帖给出 NoDL v2 文档样例——publishers / subscriptions / parameters / QoS / service_servers 全部静态声明，并公开招募 rosgraph-wg 工作组参与者 [46]。若节点接口从运行时自省变成静态声明，配置校验、静态分析、生成式工具链都会获得新的立足点，也直接支撑「薄节点」架构。
2. **商用/闭源组件的分发边界**：社区在问「专有 ROS 2 组件一般怎么分发」，讨论给出的答案集中在两条——Transitive 的 npm 式「能力包」（可携带预编译二进制），以及用 Pixi 环境隔离系统 ROS 以规避 sync 漂移 [47]。这与 Isaac ROS 5.0 走 Pixi [48]、EasyNav 提供 Pixi 路径互相呼应：**环境隔离正在成为分发问题的默认答案** [2][26]。
3. **参数默认值变更需要独立审计通道**：knoblog 从 git 历史里抽出参数/增益/阈值默认值的 old → new 变更（Nav2 实例：`inflation_radius` 0.55 → 0.7、`time_before_collision` 2.0 → 1.2），指出这类改动从不进 changelog，却直接改变机器人行为 [42]。与本周 Nav2 的 staleness 加固放在一起看，参数语义的变更管理是下一个被工程化的对象。
4. **「AI 在控制回路之外」的三种基础设施**：Robot Brain（任务经验记忆，闭核 + ROS 2 参考桥）、DialoStack（语音对话但 LLM 不参与控制）、Kyvern（签名的可验证「为什么这么做」记录）[43][44][49]——三者在同一周出现，且都刻意把 AI 组件放在控制回路之外，指向「机器人行为的可解释/可追溯」这一正在成形的子领域。
5. **仿真器的可编程性向 Python 与数据侧让路**：gz-sim 将 ECS 组件与 ECM 操作暴露给 Python [38]，Uranus 探索数据驱动的仿真路线 [50]。仿真正在从「配置驱动的世界」变为「数据与脚本驱动的世界」。
