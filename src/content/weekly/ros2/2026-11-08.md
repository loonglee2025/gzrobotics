## 总判断

本周是两个方向同时加速的一周，而它们指向同一个矛盾：**能力在往前推，接口在往回砍**。

往前推的那一半，是上周还「验收单写满缺陷」的 buffer 后端第一次以产品形态落地。StereoLabs 发布 ZED ROS 2 Wrapper 5.6，直接以 `rosidl::Buffer` + CUDA 后端发布 `sensor_msgs/Image` 与 `PointCloud2`，用标准话题、无自定义类型、自动 CPU 回退，在 Jetson AGX Thor 上把点云端到端延迟降了最多 61%、延迟标准差降到约三分之一 [1]。这条通道自 10 月起就一直在填缺陷，本周上期点名的最后三个洞（`#953` 等 buffer 通道 DataWriter、`#965` 序列化 take 行为、`#963` 序列化长度）全部闭合 [2][3][4][5][6]——**上期那份缺陷名单，本周清空**。但同一周，`rosidl` 侧的另一条线亮起红灯：REP-0157 与 `rosidl::Buffer` 各自定义了一套「内存在哪里」的模型，PMC 成员在 11/4 专门会议前直接写道「我希望最终只有一个内存模型，而不是两个」 [7][8][9]。

往回砍的那一半更明确。Rolling 本周移除内置 topic statistics（约 2400 行，编译从 6.32 s 降到 4.91 s，约 −22%）[10]，并且是**不给弃用期**的直接移除；同时 rcutils/rcl/rclcpp/rclpy/rmw/rosidl/geometry2/rviz 八个仓库同步摘除 `ament_cppcheck`（这个工具自 2022 年起实质停用）[11]；`rclcpp` 还清掉了两个「从来编不过」的 API 与若干未用成员 [12][13]。11/3 的 PMC 纪要里，下一版路线图的第一优先级写的是 **build times 与 code cleanup**，其后才是 rclpy 改进与日志系统 [14]。把删除清单和路线图放在一起看，结论很清楚：**Rolling 进入了一个减法周期，削减的理由是「没人用」，而不是「有替代」**。

第三条线是**服务/请求-响应路径**成为缺陷集中区，且失败方式从「丢帧」变成「卡死或崩溃」。`rmw_zenoh` 修了一个可以让服务器进程直接退出的缺陷：畸形服务请求声明了超出上界的定长序列，生成的 typesupport 里 `resize()` 抛 `std::length_error`，而 `TypeSupport` 只捕获了 Fast CDR 的异常、`take_request`/`take_response` 自己没有 catch，异常就穿出 rmw API 终止了进程 [15][16]。`rmw_fastrtps` 修的是相反方向的静默：服务端只等 100 ms 的 `max_blocking_time`，没匹配上就把响应丢掉并打一行「client will not receive response」，客户端永远等下去；更糟的是 `endpoint_erase_if_exists` 没有通知条件变量，客户端走了也唤不醒等待 [17]。而 Connext 那边，PMC 上确认同一 participant 内的本地匹配**不保证**在 publish 前完成，最长可到 16 ms，而 Fast DDS、Cyclone DDS、Zenoh 都在订阅创建返回前完成匹配 [14][18]。三个实现，三种不同的失败方式——上期报告的「同一 API 两种行为」，本期升到了服务层。

发行与安全层面，`ros2_control` 在 Lyrical 上正式标记为 stable，并给出一份很长的破坏性变更清单，其中「Handle / export API 移除」意味着所有硬件插件要重编、并改为把手柄值所有权交给框架 [19]。Fast-DDS 本周合入两个新的 GHSA 修复（参与者权限授予过期后不解绑、DN 比较时转义字符处理错误），但**最新 release 仍是 v2.14.7（2026-09-08），这是连续第六期下游拿不到补丁**；两个新 GHSA 至今仍是 404，未公开 [20][21]。Kilted 的 EOL 日期在 PMC 上被明确为 **11 月 30 日**，Lyrical 的 sync 仍被约 15 个回归包卡住 [14]。

上期七个待跟踪项，本周闭环四个：`rmw_fastrtps#953`、`#947` 一族的序列化 take 问题、`ros2_control` 的 Lyrical stable、以及 `ros2/ros2#1887` 之外新增的一条——committer 投票因参与度不足被**重启**，并新增一名候选人 [14]。仍未闭环的还是那两项：Fast-DDS 发版，与 Lyrical sync。

## 本周关键信号

### 1. 零拷贝第一次以「产品功能」出现，同时暴露出两套内存模型的路线冲突

**发生了什么：** StereoLabs 发布 ZED ROS 2 Wrapper v5.6，新增对 ROS 2 Lyrical 的 `rosidl::Buffer` 消息字段支持，默认启用 `general.buffer_backend = cuda` [1]。要点在于它**没有另起一套数据类型**：发布的仍是 `sensor_msgs/msg/Image`、`sensor_msgs/msg/PointCloud2` 等标准消息，只是 `data` 字段带上了 CUDA 后端；订阅端只要在 `SubscriptionOptions` 里写 `acceptable_buffer_backends = "cuda"`，就能在回调里通过 `get_backend_type() == "cuda"` 判断并直接用 GPU 指针，不接受的订阅者（RViz2、`ros2 bag`、Python 节点、另一台机器上的节点）自动收到 CPU 数据，发布端无需知道谁在听。官方数字（Jetson AGX Thor，ZED 2i，Isaac ROS 5 裸机，publish 到订阅端 GPU 可取用）：紧凑点云延迟降 10%，全分辨率 14.7 MB 点云降 **61%**，点云延迟标准差降约 **3 倍** [1]。

同一条通道的技术债，本周基本收口：`#953` 让 `wait_for_all_acked` 也等 buffer 通道的 DataWriter（修 `#952`）[2]；`#966` 与 `#1097` 让 buffer 后端收到的消息做序列化 take 时**显式失败**而不是忙等死循环或返回描述符字节（修 `#965` 的两个实现分歧）[3][4]；`#964`/`#1092` 让 `rmw_serialize` 返回真正的写入长度而不是尺寸估算（修 `#963`）[5][6]。

**为什么值得关注：** 这是 buffer 后端第一次跨过「实验特性」的门槛——判断标准不是它有没有 issue，而是**有没有一个商业产品把它当作默认路径、且能对不接受它的订阅者优雅降级**。ZED 的自动 CPU 回退恰好是上期报告担心的地方（加速路径与基础路径语义不一致），而它选择的做法是「以订阅端声明为准」：能力协商发生在订阅侧，而不是让发布端猜。这个设计取向值得记住，因为它同时回答了 REP-0157 的一个开放问题——视图是否需要知道宿主是否加速。

但也有一处必须写清的边界：**进程内（IPC）订阅只能收到 CPU 数据**，要拿 GPU buffer 必须关掉 IPC [1]。这意味着「同进程零拷贝」与「跨进程 GPU 零拷贝」目前是互斥的，而这两者恰恰在同一个节点里同时存在（相机节点 + 处理节点被合进同一个 component container 时）。

同期的路线冲突更为关键。PMC 成员在 11/4 专门会议的预告帖下提了四个问题，第二个直接指向上期报告的主题：REP-0157 的 `rosidl_memory_t.attributes` 与 buffer 方案的 `BufferMemory`（`rosidl#990`）都在描述「内存住在哪」，而 buffer 那套**已经落到 rolling 和 Lyrical**（`rosidl#941`/`#944` 的 `rosidl_buffer`/`rosidl_buffer_backend` 与后端注册表、`rosidl_python#250`、`rmw_fastrtps#867`；后端实现仓库 `rosidl_buffer_backends` 已含 CUDA 与 Qualcomm 两套）[7][8][22]。同一帖里还有两个硬事实：参考实现不含测试约 **45k 行，其中只有约 8k 是生成器代码**，其余是 C/C++/Python 的容器运行时与 XCDR 库；以及原型把新类型放在 `sensor_msgs::msg::experimental::Image` 这种并行命名空间下，「怎么从 `experimental::` 走到默认」尚无答案 [8]。

**影响层面：** 消息层规范 / 零拷贝数据面 / 异构计算 / 客户端库 API 演进节奏

**下一步盯什么：** 11/4 会议的纪要。预告帖写着「Notes from the meeting will be posted in this thread afterwards」，但**截至 11 月 9 日该帖没有纪要**，11/3 的 PMC 纪要里也没有 REP-0157 条目 [8][14]——这是一处必须如实标注的空白，不要根据会议存在就推断结论。下一次相关会议是 **11 月 11 日的 Accelerated Memory Transport WG** [14]。另外要盯 REP-0157 是否接受「先只做 C++」「主体留在树外做实验包」这类分期方案，以及 `xcdr_buffers` 能否改用 Fast CDR 而不是自带 reader/writer。

### 2. 服务路径成为缺陷集中区：一个畸形请求能杀进程，一次超时能永久卡住客户端

**发生了什么：** 三件事，分属三个实现，全是请求-响应语义。

`rmw_zenoh#1095`（Rahul-cs50 提交，ahcorde 协同）修的是**远程可触发的进程终止**：服务请求或响应声明了一个超出上界的定长序列时，生成的 typesupport 用 `BoundedVector::resize()` 分配，抛出 `std::length_error("Exceeded upper bound")`；而 `TypeSupport::deserialize_ros_message()` 与 `_with_endpoint()` 只捕获 `eprosima::fastcdr::exception::Exception`，`ServiceData::take_request()` 与 `ClientData::take_response()` 又没有自己的 catch，于是异常**穿出 rmw API，进程终止**。修法是在两个 deserialize 函数里补 `catch (const std::exception &)`，返回 false 并设置错误信息，服务与客户端 take 路径随后返回 `RMW_RET_ERROR`，rclcpp 的 executor 记一条日志继续 spin；因为修在 `TypeSupport` 而不是各调用点，`rmw_deserialize()` 这条同样会漏出 `std::length_error` 的路径也一并覆盖了 [15][16]。

`rmw_fastrtps#956`（Michael Carroll）修的是静默丢弃：`send_response` 等响应 writer 与客户端的 response reader 匹配，但只等 writer 的 `max_blocking_time`（默认 100 ms），超时就丢掉响应并打「client will not receive response」，客户端就此永久等待；同时 `endpoint_erase_if_exists` 没有通知条件变量，所以即使客户端已经离开，等待也不会被唤醒。修法是延长到最多 10 秒，并在 reader 匹配或客户端端点消失时立即唤醒 [17]。

第三件来自治理层而非代码：11/3 的 PMC 会议议程记录了一条语义分歧——**同一 participant 内创建一个 publisher 和一个 subscription 后立刻 publish，消息是否一定到达？** `rmw_connextdds` 不保证发布前完成本地匹配，本地匹配最长耗时 16 ms；而 Fast DDS、Cyclone DDS、Zenoh 都在订阅创建返回前完成匹配 [14][18]。

**为什么值得关注：** 这三条合起来说明一件上期没写透的事：**发布-订阅路径的错误表现为「丢」，服务路径的错误表现为「卡」或「死」**。丢一帧在传感器流里通常可容忍（下一帧就来），但服务调用是一次性的：响应被丢掉一次，调用方就永远停在那里，而 100 ms 这个默认值在负载抖动、同机多 participant、或容器里 CPU 被限流时并不宽裕。`rmw_zenoh` 那条更严重——它把「畸形输入」的后果从「拒绝」变成了「进程退出」，而服务端恰恰是暴露给不受信调用方最直接的入口（多机器人系统里任何一个节点都能发请求）。值得注意的是修复方向：三条都在**把失败显式化到 API 边界**（返回 `RMW_RET_ERROR`、等待可被唤醒、把匹配语义写进规范化的期望），而不是「让它更快」。

第三件事的价值在于它是一条**可测性**问题而不是实现问题：如果三个 RMW 对「同节点自发布订阅能否立即收到」给出不同答案，那么任何依赖这一点的测试都是 flaky 的，而 flaky 测试本周已经以 `rclpy#1719`（async node/service/client 测试超时 120 秒，重新打开，Lyrical 的 backport 缺失）的形式出现在 buildfarm 问题列表里 [14]。

**影响层面：** 中间件可靠性 / 输入校验边界 / 跨 RMW 语义一致性 / 测试稳定性

**下一步盯什么：** `rmw_zenoh#1094` 只报了 Zenoh，但**同一段生成代码（`BoundedVector::resize()` 抛标准异常）在 `rmw_fastrtps_cpp`、`rmw_cyclonedds_cpp` 上是否存在同样的逃逸**，本周没有对应报告——这是最值得主动验证的一项。其次是 `#956` 的 10 秒上限在真实故障下是否足够（一个从未匹配的客户端会让服务端阻塞 10 秒？还是会被端点消失唤醒）；以及 Connext 的匹配语义最终是「改实现」还是「改文档」。

### 3. Rolling 的删减季：topic statistics 直接移除、cppcheck 全线摘除、死 API 考古

**发生了什么：** 三组删除，同一周。

**topic statistics 从 `rclcpp` 移除**，11/3 由 ahcorde 正式公告，涉及 10 月 5 日合入的五个 PR：`rclcpp#3203`（移除 `rclcpp`、`rclcpp_lifecycle`、`rclcpp_components` 中的实现）、`ros2#1878`（从 `ros2.repos` 移除 `libstatistics_collector`）、`demos#812`（移除 demo 包）、`examples#476`（移除示例）、`ros2_documentation#7245`（移除教程与概念页）[10][23]。移除面很具体：`NodeOptions::enable_topic_statistics()`、`SubscriptionOptions::topic_stats_options` 整个 `TopicStatisticsOptions`、`rclcpp::TopicStatisticsState`、`rclcpp::topic_statistics::SubscriptionTopicStatistics`、`NodeBaseInterface::get_enable_topic_statistics_default()` 与 `NodeBase` 构造参数、以及加载 component 时的 `enable_topic_statistics` 额外参数；`/statistics` 话题不再有任何发布者。`statistics_msgs` 本身**保留**（在 `rcl_interfaces` 里），所以只订阅那些消息的工具还能编。理由是三条：用的人极少；`tracetools`/`ros2_tracing` 能给出同样的速率/周期/延迟数据而不给每个订阅加代码与开销；`rclcpp` 不再依赖 `libstatistics_collector` 与 `statistics_msgs`，单发布单订阅节点的编译从 **6.32 s 降到 4.91 s（约 22%，Ryzen 9900X）**，整体移除约 **2400 行**。只影响 Rolling 与 Makoa Mata-mata（2027-05-23）及以后，Humble/Jazzy/Kilted/Lyrical 不变 [10]。

**`ament_cppcheck` 全线摘除。** clalancette 在 `rclcpp#3398` 里写明：`ament_cppcheck` 自 2022 年起因为 2.x 版本扫描时间过长被禁用，「四年过去我们似乎也没怀念它」，于是彻底停用；这属于一个更大的系列，目标是把它从 `ament_lint_auto` 里摘掉、最终删除该模块 [11]。本周 rcutils、rcl、rclcpp、rclpy、rmw、rosidl、geometry2、rviz 八个仓库在同一天完成同一改动。

**死 API 考古。** `rclcpp#3348` 删掉一个「声明还在、定义在 #1017 里已随旧 `IntraProcessMessage` 类型一起删除」的函数——任何调用都会链接失败；`rclcpp#3349` 修了一个**从不编译**的重载：`create_generic_service(NodeT, ...)` 把 QoS 传给 `const rclcpp::QoS&` 参数，没有这种转换，因为 `Node::create_generic_service()` 不走这个重载，所以四年没人发现；同一 PR 还删了 `src/rclcpp/create_generic_service.cpp`（从未进入构建，且已编不过当前 `GenericService` 构造函数）[12][13]。加上上周的未用成员清理与 flaky 测试删除，`rclcpp` 本周的删除量明显大于新增量。

**为什么值得关注：** 把三件事并置，能看出一个方向性判断：**Rolling 正在用「删除」换编译时间与维护面，而理由统一是「没有真实用户」**。这与上期「构建时间被当成一等工程问题」是同一条线，只是从「加 PCH、让 ccache 命中」变成了「把不需要的东西拿掉——那是最有效的优化」。22% 的单节点编译时间来自删掉一个大多数人都没开过的统计功能，这个数字会对所有下游项目生效，而它的代价是：任何在生产里依赖 `/statistics` 的系统，在升级到 Makoa 时会**静默失去数据源**（话题仍然合法、只是没人发）。

风险也说清楚：**这次移除没有弃用期**。公告里 tomoyafujita 提了两点异议——是否应该先走弃用周期，以及长期统计钩子是否该放在 `rcl` 层以便 `rclpy`、服务与 action 共享同一机制；维护者的回答是「功能用户太少、且 Makoa 周期刚开始，还有足够时间反应」，并请仍在用的人在帖内回复 [10]。这是可以理解但需要被记录的决策：**判断「没人用」的依据是最近的 bug 报告数量，而不是任何使用量统计**——而这类统计恰好在本周被删掉了，形成一个有意思的循环。

**影响层面：** 客户端库 API / 编译性能 / CI 与静态分析工具链 / 发行版迁移成本

**下一步盯什么：** `ament_cppcheck` 从 `ament_lint_auto` 移除后，`ament_lint_auto` 的默认集合是否变短（下游 CI 会静默少跑一项检查）；是否有生产用户按公告要求在 topic statistics 帖子里回复（如果有，可能触发一个树外的替代包）；以及同一「删除」逻辑会不会延伸到 `rclcpp` 的其他低频特性。

### 4. `ros2_control` 在 Lyrical 标记 stable：破坏性变更集中在「接口所有权」

**发生了什么：** christophfroehlich 于 11/6 发布 Lyrical Luth 的变更说明，`ros2_control`、`ros2_controllers`、`control_toolbox`、`realtime_tools` 均已标记 stable/released，并明确提示先读「Breaking / behaviour changes」再升级 [19]。破坏性部分按影响面排序：

- **Handle / export API 移除**（`ros2_control#3610`）：硬件组件的 `export_state_interfaces()` / `export_command_interfaces()` 不存在了，框架改为从 `<ros2_control>` 标签自己创建接口，硬件侧改用 `set_state`/`get_state`、`set_command`/`get_command` 取值；`StateInterface`/`CommandInterface` **不能再从 `double*` 构造**；chainable controller 的 `on_export_state_interfaces()`/`on_export_reference_interfaces()` 换成返回 `shared_ptr` 的 `on_export_*_interfaces_list()` [19]。
- **`switch_controller` 默认变为 `strict`**；`configure_controller` 只接受 `unconfigured` 控制器，`spawner` 会跳过已配置的，要用 `--reconfigure`；控制器管理器的 ROS 参数不再转发给控制器；一个控制器失败会**停掉整条 chain**；更新率会四舍五入到可达速率 [19]。
- **`ros2_controllers` 侧**：`joint_trajectory_controller` 的 `constraints.goal_time` 默认改为 `10.0` s 且语义变化（负值=无限等待、`0.0`=无宽限期），`action_execution_timeout` 移除；`joint_state_broadcaster` **不再发布 `dynamic_joint_states`**（改用 `state_interfaces_broadcaster` 或 `gpio_controllers`）；`JointGroupPosition/Velocity/EffortController` 弃用，改用带 `interface_name` 的 `forward_command_controller`；diff_drive/mecanum/omni_wheel 的 `tf_frame_prefix_enable` 弃用、diff_drive 的 `publish_rate` 移除 [19]。

新增侧同样值得记：handle 除 `double`/`bool` 外支持 `float32` 与 `int8/16/32`、`uint8/16/32`；新增 `INDIVIDUAL_BEST_EFFORT` 与 `REGEX` 两种接口声明方式；`battery_state_broadcaster`、`state_interfaces_broadcaster`、`magnetometer_broadcaster` 三个新控制器；`joint_trajectory_controller` 恢复了 ROS 1 的轨迹替换（新目标拼进正在执行的轨迹而不是替换）、`max_deceleration_on_cancel` 取消时减速、以及 `positions_upsampling.enable`——把低速率的位置指令块**上采样成平滑样条**；`realtime_tools` 新增 `LockFreePooledSPSCQueue` [19]。

本周对应提交也印证这条线在收口：`ros2_control` 于 11/2 打出 **6.13.0**，`ros2_controllers` 于 11/4 打出 **6.10.1**，其间 `#2705` 修了 `joint_trajectory_controller` 的内存访问崩溃（6.10.1 的内容）[24]；`gz_ros2_control` 同周发布 **4.0.2**。

**为什么值得关注：** 这份清单里真正昂贵的只有第一条。`export_*_interfaces()` 被删、`StateInterface` 不能再从 `double*` 构造，意味着**手柄开始拥有自己的值**——这是控制栈最底层的一次所有权迁移，所有硬件插件（厂商 HAL）都必须改并重编，且改法不能靠机械替换（原来是指向驱动的裸数组，现在值由框架持有，写回路径变成 `set_command`）。相对而言，`switch_controller` 变 strict、`goal_time` 语义变化这些是行为变更，能靠参数与测试兜住；但所有权变更会同时影响实时性假设（多一层间接）与「驱动内部状态与 command 值是否仍是同一块内存」的推理。

两处细节指向更远的方向。一是 `joint_state_broadcaster` 停止发布 `dynamic_joint_states`：这个「任意命名的接口集合」曾经是 ros2_control 里最灵活也最难静态检查的出口，废掉它并让 `state_interfaces_broadcaster` 承担，意味着**接口命名从运行时约定转向声明式**，与 `INDIVIDUAL_BEST_EFFORT`/`REGEX` 的引入是同一逻辑。二是 `positions_upsampling`：把低速率的位置块插值成平滑轨迹，这个需求的来源几乎只能是**学习策略（VLA/扩散策略）以 10–30 Hz 输出 action chunk**，而控制回路仍在 100 Hz 以上——控制栈开始在核心控制器里为这类输出模式留接口，而不是让每个团队自己在树外写一个桥。

**影响层面：** 控制栈 / 硬件插件 HAL / 工业迁移成本 / 学习策略接入

**下一步盯什么：** Handle API 移除后的社区反馈（迁移指南是否够用、是否有厂商直接选择停在 Kilted/Jazzy）；`goal_time` 默认 10 s 对现有产线的影响（原来靠 `action_execution_timeout` 的配置现在必须重写）；`positions_upsampling` 的插值在加速度连续上是否满足（spline 的类型很关键）；以及 `dynamic_joint_states` 的移除会不会打断 MoveIt 侧仍在读它的旧配置。

### 5. 仿真侧的实时因子与平台收缩：kinematic 模式从 30% 到 90%，macOS 上两代 Gazebo 提前退场

**发生了什么：** Gazebo PMC 11/2 的纪要里有一条容易被忽略但影响很大的更新：kinematic 模式新增「可选禁用接触」的参数（`gz-physics#1139` / `gz-sim#4101`），**实时因子（RTF）从约 30% 提升到约 90%** [25][26]。这条属于本周 6 个 `gz-sim` 提交之一，同周还有 `#3086` 动态可分离关节插件（Intrinsic 的 Arjo Chakravarty 与 Ian Chen 协同）[27]、`#4115` 给 `JointTrajectoryController` 加命名空间支持、`#4171` 新增设置链路运动学属性的组件。

基础设施侧：`gz-sim#4085` 在 Ubuntu Resolute 的 CI 上把 **Zenoh 作为默认传输后端**做集成测试 [28]；C++20 迁移继续（`gz-cmake` 改用 `CMAKE_CXX_STANDARD` 给 cppcheck 而不是硬编码，上游 `ogre-next` 的 `GpuProgramParameters` C++20 编译 PR 在评审中）；Bazel 侧 `gz-sensors#658` 停止把 pre-release 提交到 BCR，只发稳定 tag [26]。

平台收缩：**Gazebo Harmonic 与 Fortress 将于 2027-01-10 停止 macOS 支持**。原因是两者依赖的 `freeimage` 与 `qt@5` 即将在 Homebrew 被禁用——`freeimage` 有多个未修 CVE，homebrew-core 定于 2027-01-10 禁用该 formula，`qt@5` 因 2025-05 已 EOL 定于 2027-05-19 禁用。Gazebo 的 Rotary 与 Jetty 已迁到 Qt6 并弃用 freeimage，但把 Qt6 迁移回推到 Harmonic/Fortress「成本高到不可行」；自己维护一份 `freeimage`/`qt@5` formula 又等于把一个带未修 CVE 的库继续分发。PMC 因此决定届时彻底停止这两个版本在 macOS 上的支持，Ubuntu 侧支持周期不变；依赖 freeimage 的 `ogre1.9` 已在 Rotary 移除，Jetty 上将于同一天移除 [29][26]。

**为什么值得关注：** RTF 30% → 90% 这个数字的性质不是「优化」，而是**用法边界的迁移**：RTF 只有 30% 时，Gazebo 只能用于离线验证与慢速回归；到 90% 时，仿真才可能进入「准实时在环」（HIL/SIL 的时间语义、控制器周期与仿真时间对齐才有意义）。而之所以能提到 90%，是因为允许在 kinematic 模式下关闭接触计算——也就是说，**这是用「物理精度」换「时间精度」的显式交易**，配置错了会得到「机器人穿过障碍物但帧率很好看」的仿真。这条路对做运动学规划/导航仿真的团队是正确的，对做接触丰富的操作仿真则完全不能用。

macOS 那条则是另一类提醒：**外部依赖的 EOL 时钟在替项目做支持决策**。Qt5 早在 2025-05 EOL，freeimage 的 CVE 一直没修，Homebrew 一禁用 formula，所有靠它构建的下游就同时失去构建能力——Gazebo 只是先遇到了。任何把 macOS 作为开发/演示平台的机器人项目，2027-01-10 之后都要么上 Jetty+，要么退回 Docker/Ubuntu。

**影响层面：** 仿真性能 / HIL-SIL 时间语义 / 跨平台支持矩阵 / 供应链 CVE 债务

**下一步盯什么：** kinematic 模式下禁用接触这个参数在默认值上是否安全（默认保持原行为是底线，需在文档里显式警告）；Zenoh 作为 Gazebo 默认传输在 CI 上跑通后，是否会成为 Jetty/Ionic 的发行默认；`gz-sim#4096`/`#4097` 两个 TimelinePublisher backport 何时进入 Ionic 与 Harmonic；以及 2027-01-10 前是否会有一次 macOS 用户的集中反馈。

### 6. 治理进入「参与度、合规、agent」三线并行：投票重投、许可证缺口、以及把 AGENTS.md 写进构建系统

**发生了什么：** 三处独立的治理动作，本周同时出现在会议纪要里。

**投票失效。** 11/3 的 PMC 纪要第一条就是：最近的 committer 投票**参与度不足**，ahcorde 将在 11/2 那周重启投票，每个候选人会附带更完整的「我是谁、为什么被提名」；章程把异步投票限制在一周内，多用表单（多个决策一起投），单项则用邮件 [14]。同一周新增一名候选人：Maurice Alexander Purnawan（`mini-1235`），scope 限定 `rclcpp` [14]。值得一提的是这位候选人正是本周 buffer 修复 `#953`、`#966`、`#1097` 的提交者/共同作者 [2][3][4]——**代码贡献先于身份，这在这条线上一直是常态**。

**许可证缺口。** rosdistro 侧在审 `#53263`（新增 `example_robot_descriptions`）时发现包内文件带 CC-BY-NC-ND-4.0 与 CC-BY-SA-4.0：前者禁止商用与演绎，不可接受；后者看似典型 copyleft，但**并非 OSI 认证许可**（CC-BY 与 CC0 可接受）。用 CMake 排除这些文件不够，因为源码 deb 仍会包含它们；下一步是尝试在 release 仓库打补丁，太冒险就只能要求从上游删除。纪要末尾一句是重点：**「OSRA 需要拿出 IP 与许可政策」** [30]。

**agent 与多仓链式贡献。** Gazebo PMC 讨论了「同时在多个仓库开一串 PR 而不先做设计讨论」该怎么处理（触发点是 `gz-sensors#690`）。纪要里的三条都很具体：review 带宽与 CI 负载（要欢迎贡献者，但要避免大堆同时开着的 PR/draft PR 把 buildfarm 打满）；**federated 仓库布局对现代 AI 辅助工作流是否构成摩擦**（讨论了 CodeRabbit——对开源免费、能跟踪多仓上下文——同时担心「多一层门槛」与「AI 生成的评审意见与实现细节漂移」）；用 `AGENTS.md` 引导贡献者的建议被提出，但因**跨目录污染与安全顾虑**，倾向 opt-in 机制（skills 或 pre-commit hooks）[26]。结论是暂不定政策，先改贡献指南（跨仓特性先讨论）并**阻止 draft PR 自动跑 CI** [26]。

同一周，`AGENTS.md` 出现在另一个位置：Bazel 的 ROS Central Registry（RCR）发布 `lyrical.2026-10-05.rcr.0`，贡献方式写着「把你的 agentic coding 工具指向 `AGENTS.md` 与 `.agent/skills` 目录，它们会解释如何准备 workspace、vendor 一个包、修源码并 roll up 一个补丁」，CI 检查是否引入破坏性变更 [31][32]。

**为什么值得关注：** 这三件事放在一起，说明治理的焦点已经从「是否允许 AI 参与」转到**「如何验收、如何署名、如何在稀缺的 review 带宽上定价」**。投票参与度不足是个更根本的信号：异步投票的失败说明维护者的注意力已经不够分配，而这恰好是「链式 PR 打满 CI」讨论的同一个约束——**真正的稀缺资源是 review 时间，不是代码量**。Gazebo 提出的「draft PR 不自动跑 CI」看似小事，实际是把 CI 成本从「无条件的公共品」改成「有条件的配额」，这会直接影响外部贡献者的感受。

许可证那条被低估了：ROS 生态十年来的默认假设是「代码是 BSD/Apache，数据是 CC」，而 `example_robot_descriptions` 这类「描述文件 + 网格资源」的包天然会带 CC 系列，其中 `-NC-ND` 与「非 OSI 认证」两个坑都是发布流程不会自动拦的。OSRA 至今没有 IP 与许可政策，意味着**这类冲突会以「某个包突然从 apt 消失」的形式逐个暴露**。

一致的是署名：本周多个关键修复带 AI 署名（`Claude Opus 5.5`、`Claude Code`、`Claude Fable 5.1` 各有出现），而导航栈的 PR 模板已经把它拆成两个独立问题——「这个 PR 是否包含 AI 生成的软件」与「这个 PR 的描述是否由 AI 生成」，后者为「No」、前者为「Yes and it was manually validated and tested」是本周里最诚实的一行表格 [33]。

**影响层面：** 社区治理 / 贡献流程与 CI 成本 / 供应链许可合规 / agent 工具接入

**下一步盯什么：** 重启后的 committer 投票是否达到参与门槛（如果再次不足，章程可能需要改）；OSRA 的 IP/许可政策是否成形，`rosdistro#53263` 最终怎么处理 CC 文件；Gazebo 的「draft PR 不跑 CI」是否落地，以及 CodeRabbit 这类跨仓评审工具是否被正式引入；`AGENTS.md` 在 RCR 里被 agent 实际使用的效果（是否出现「CI 挡住破坏性变更」以外的质量问题）。

## 工程化观察

**三个「校验器本身有 Bug」的案例，比被校验的参数更值得记。** 导航栈本周三个修复的属性高度一致：不是算错了代价，而是**对「非法输入」的处理逻辑本身写错**。`(name != min || name != max)` 恒为真（应为 `&&`），于是 AMCL 的两个激光测距参数一旦设回 -1 就永远被拒 [42]；`terminal_checking_interval` 被当作取模除数却没有下界检查，0 值直接 SIGFPE [43]；`wrap_around=false` 的循环在状态 switch 之前 break，把 SUCCESS 判成 FAILURE [41]。这三处的共同点是**错误路径没有被测过**——合法输入一切正常，只有边界值或回退路径才暴露。上期说的「无效输入得到有效数值」是运行时数据的问题，本周这三个是**配置层的问题**，而配置层更难测：没人会给 5000 个参数各写一个 0 值与负值用例。

**跨发行版读取 bag 的前向兼容，终于被当成正常场景处理。** `rosbag2#2554` 描述了一个很典型的事故：用更新版本录的 bag，元数据版本 9 改了 `offered_qos_profiles` 的格式，读取时报错——**整个 bag 对 `ros2 bag info` 与 `play` 都不可读，而实际上只有 QoS 信息受影响**。修法是版本更新时告警、QoS 段解析失败时告警并回退默认 QoS，`metadata.yaml` 与存储文件内的 QoS 都适用 [37]。这条对多机器人团队的实际意义是：录包机器与回放机器的发行版不一致是常态（车上 Jazzy、工位 Rolling），而原先的失败模式是「全有或全无」。

**成熟项目开始为「每周期都跑的函数」做常数项。** `ros2_control#3753` 的 PR 描述里有一张完整的基准表：`enforce_command_limits()` 每周期运行，原实现对每个 `(硬件, 关节)` 限幅器都要再扫一遍所有硬件（`find` 后 `operator[]`），复杂度 O(H²·J)；改为把外层已有的限幅器传进去后，16 硬件 × 2 关节从 ~28800 ns 降到 ~22200 ns（−23%），4×6 降 12%，而 1×7 在噪声范围内 [44]。同时作者还标明「剩余成本部分来自接口键分配，由 #3632 处理」——**把一个微优化拆成可独立评审的两步，并给出可复现的测量方法**，这是本周最值得抄的做法。同周 `#3755`（服务列表线性化）与 `#3756`（只解析一次）是同一波。

**时钟相关缺陷在两个方向同时出现。** `rclcpp#3362`：时刻回拨后 `Rate::sleep()` 正确地把下一次唤醒排到 `now + period`，却仍用**旧时间轴**推进 `last_interval_ += period_`，于是此后每次调用都看到 `now < last_interval_`，循环以「period + work」运行直到时钟追上来——**用循环 bag 时永不恢复** [35]。反方向的 `rcl#1356` 是测试容差问题：Windows 上 OS wait 以系统时钟 tick 计，可能提前一点返回（CI 上实测 99.4 ms），测试加了 16 ms 容差（Windows）与 1 ms（其他平台），同时仍能检出「本不该触发的 override timer 唤醒」[36]。两者放在一起是一条经验：**凡是把「时间」当契约的地方（Rate、超时、测试），要么显式定义时间轴变化时的语义，要么留出时钟粒度容差，两者缺一都会出现「只在特定平台/特定场景」的偶发缺陷**。

**工具链超前：OpenSSL 4.0 的 FTBFS 由发行版方修。** Fast-DDS 本周的 `4c06c893` 来自 Canonical：OpenSSL 4.0 更严格的类型检查打破了 `rfc2818_verification`（旧 Asio 经 `<asio/ssl.hpp>` 间接引入）与 PKI 代码把 `X509_get_subject_name()` 结果存进非 const 指针的做法 [40]。这类提交在周报里通常是噪音，但它说明一件事：**中间件对 TLS 的用法一直被上游的头文件包含关系「偶然」满足**，发行版一旦收紧，跨发行版的构建矩阵就会同时变红。

## 前沿议题

**1. 一个内存模型还是两个：REP-0157 与 `rosidl::Buffer` 必须收敛。** 这是本期最该带到下周的问题。两边都在改「生成的 C++ 类型里 `uint8[]` 长什么样」、都在给 `rmw_fastrtps` 加 loan/协商管道、都在描述内存位置（`rosidl_memory_t.attributes` 对 `BufferMemory`）[7][8]。而 buffer 那套已经发了产品、进了 Lyrical [1]，REP-0157 还在 45k 行原型的阶段 [8]。现实的时间线指向一个结论：**REP-0157 若要落地，最可能的形态不是「替换 buffer 方案」，而是「把 buffer 方案一般化」**——如果真是这样，那么「`uint8[]` 字段能不能就是一个 `rosidl::Buffer`，指向 loan 区域」这个问题的答案，比 REP 里任何一条格式规定都重要。

**2. 服务路径的输入校验应该在哪一层。** `rmw_zenoh#1094` 暴露的是「生成的 typesupport 抛标准异常、而接口层只 catch 第三方库异常」这个组合缺陷 [15][16]。正确的边界在哪一层值得讨论：在 `TypeSupport` 里 catch `std::exception` 是止血（本周的选择），但更彻底的做法是生成代码在越界时返回错误码而不是抛异常——而那会改到 `rosidl` 生成器的契约，属于 REP 级别的决定。

**3. 用「能力声明」取代「配置约定」。** Interop SIG 11/5 的议题是 Next Gen Open-RMF 的 Behavior/Capability Declarations：模块（交通管理、任务管理、执行、门/电梯管理）通过 manifest 声明自己的行为与能力，系统据此**校验用户选的组合是否适配其场景**，并**自动生成/配置集成测试与端到端测试的期望** [49]。这个思路值得所有做模块化系统的人抄：它把「这个模块能干什么」从文档变成了机器可读的契约，而测试期望由契约推导——**同样的形状正在 agent 工具链里出现（工具声明 + 由声明推导的校验）**，两条线迟早会撞上。

**4. ROS-free 核心 + ROS 作为集成层。** ManyForge 明确把架构倒过来：核心组件是 C++/Python 且**不依赖 ROS**，实时敏感部分永远是 C++，场景/碰撞/执行/停止的权威在框架自己，ROS 只做集成层（stock ros2_control/JTC 与厂商驱动通过 adapter 接入），并且 Mock、Sim、Real 行为一致，可以在 Mock 上编好程序直接跑 Isaac Sim 或真机 [50]。它的开发方式同样值得记：公开仓只用于部署，开发以一个（目前私有的）Specs 仓为权威，每次改动对照 Specs、独立评审、跑数千测试与 sanitizer/stress，并在 Mock、Isaac Sim 与真机上验证 [50]。**「规格为权威 + agent 大量参与 + 机器验收」** 这套组合，可能是 agent 时代大型机器人代码库的一种可行形态。

**5. 控制栈为低速率学习策略留接口。** `positions_upsampling` 把 positions-only 的 action chunk 上采样成平滑样条，明确写着「对运行在低速率的学习策略有用」[19]。这比任何 VLA demo 都更有指示性：**策略输出频率与控制回路频率的错配，正在从「每个团队自己写桥」变成核心控制器的配置项**。

**6. 开源硬件栈的完整度在提升。** MABEL（NYU + 多伦多）把一台 56 自由度双臂移动机器人整套开源：三轮回转底盘 + 垂直升降 + 俯仰躯干 + 3 自由度头部与双目，两条 7 自由度臂（衍生自 OpenArm）与两只 17 自由度手（衍生自 ORCA Hand），用单台 Apple Vision Pro 遥操作；硬件 CERN-OHL-S-2.0、软件 Apache-2.0、文档与照片 CC BY 4.0 [51]。同期 Intrinsic 把 Intrinsic Core 开源（含实时控制、运动规划与 CNC 机床上下料的参考方案，通过标准 workspace/消息/工具与 ROS 互操作）[39][52]。一边是「整机开放」，一边是「工业能力开放」，两条路的生态含义完全不同，但都在扩大 ROS 2 的实际用户面。
