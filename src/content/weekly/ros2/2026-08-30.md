## 总判断

本周 ROS 2 的主旋律是**「Nav2 正式登陆 Lyrical、可观测性工具从『外挂』走向『可能被核心吸收』、以及 ROS 构建/分发体系出现多条现代化路径」**。最值得关注的是三件事：其一，**Nav2 Lyrical 版本正式发布**（8/25），带来 `nav2_ros_common` 抽象层、MPPI 系列大更新、组合式 bringup 内的 IPC 零拷贝，并同步上线了**全新按发行版分版本的文档站**——这是 Lyrical 发布三个月后生态追赶的标志性节点；其二，**话题频率/节点活性测量成为社区焦点**：ros2_pulse（LD_PRELOAD tracetools shim，近零开销、覆盖 intra-process）与 ros2topic_hz（C++ 高精度 hz）相继出现，而 PMC 纪要显示官方正在讨论**删除现有 topic statistics 实现、改用 trace tools 路线**，mjcarroll 甚至表态「干脆把核心里的 hz 实现换掉」——观测性正从外围工具演变为核心框架议题；其三，**ROS 的安装/构建/CI 体系一周三连**：Conan 官方团队发布 ros-conan（把 ROS Kilted 变成普通 C++ 依赖）、PMC 成立 Bazel 工作组、社区沉淀出 Windows CI 的 Pixi 模式，共同指向「ROS 融入主流软件工程工具链」这一长期方向。此外，Open-RMF 下一代原型落地预约式目的地服务器与分层全局占用地图，LeRobot↔ROS 桥接在 ROBOTIS 侧继续深化（上周 SIG PAI 组织化的延续）。

## 本周关键信号

### 1. Nav2 Lyrical 版正式发布：nav2_ros_common、MPPI 大更新、组合内零拷贝、全新文档站

**发生了什么：** Steve Macenski 于 8/25 宣布 **Nav2 for Lyrical** 正式发布（对应 1.5.x 系列，1.5.1 于 8/12 因依赖问题重发），官方称之为「数个发行版以来最广的一次更新」：

- **新包 `nav2_ros_common`**：把 ROS API 抽象到公共位置，简化软件开发与 compliant node 编写，将持续演进
- **MPPI 一批新能力**：开环控制模式、动力学支持、非对称加速度限制、插件化运动模型、轨迹验证器、延迟补偿
- **`PauseResumeController` BT 节点**（@redvinaa）：导航暂停/恢复能力
- **Vector Object Server**（@Sushant-Chavan）：多边形/形状数据与 costmap 2D、costmap filters 集成
- **Adaptive Goal Checker**：粗/细双标准的目标达成判定
- **RPP 支持 Dynamic Window Pure Pursuit**：路径跟踪时考虑动力学限制
- **组合式 bringup 内支持 IPC，实现真正的零拷贝通信**
- **Inflation Layer 大幅加速**：新算法 + 可选 OpenMP + 非对称膨胀层（激励左/右侧通行）
- **Collision monitor**：开关、排除区、costmap 数据源
- 同步上线**全新 docs.nav2.org**：按发行版分版本的文档、教程与暗黑模式

**为什么值得关注：** Lyrical 发布约三个月后，Nav2 的落地标志着 Lyrical 生态追赶进入收获期（与上周 Kilted/Lyrical 大同步中 dwb 系入库一脉相承）。技术上两个点尤其值得注意：`nav2_ros_common` 是 Nav2 向「ROS API 抽象层」迈出的第一步，与社区 executor/rclcpp 演进（如 waitable API 对齐）形成呼应——未来若 rclcpp 接口变动，Nav2 的适配面将显著收窄；而「组合 bringup 内 IPC 零拷贝」则把上周 rosidl::Buffer/共享内存主线直接接进了导航栈的默认部署形态。赞助商名单（Dexory、Polymath、NVIDIA、AMD、StereoLabs、3Laws、Staer）也显示 Nav2 的产业化支持面在扩大。

**影响层面：** 生态层 / 导航栈 / 发行版生态成熟度

**下一步盯什么：** Nav2 1.5.x 在 Lyrical 的实际部署反馈；`nav2_ros_common` 抽象边界是否会反向影响 rclcpp API 设计；上周 MPPI 椭圆约束「改-回滚」后的最终形态是否进入 Lyrical 线；新文档站对旧文档链接的迁移完整性。

### 2. 话题测量与节点活性成为焦点：ros2_pulse、ros2topic_hz，以及官方「删旧换新」的 topic statistics 路线

**发生了什么：** 本周「准确测量话题频率」这个老痛点出现了两条社区方案与一个官方动向：

- **ros2_pulse（8/24）**：`LD_PRELOAD` shim 挂在 rclcpp 已有的 tracetools 插桩层上，统计每个话题（含 **intra-process**）频率与节点活性。作者先量化了现状的代价：`ros2 topic hz` 占 7% 单核、`ros2 topic echo` 占 31%；更糟的是把 hz 指向 intra-process 话题会让发布端开始序列化每条消息，被观测进程 CPU 上升 52%——「观测行为改变被观测对象」。ros2_pulse 热路径约 0.3 ns/消息，4900 msg/s 压测下约占 2% 负载 CPU，无需重编译、无 root、不产生 DDS 流量；支持期望频率告警、抖动统计、JSON Lines 输出对接 Prometheus/OTel，rosdistro PR（Humble/Jazzy/Kilted）已提交
- **ros2topic_hz（8/29，Bernd Pfrommer）**：C++ 版高精度 `ros2 topic hz` 替代，对高频/高带宽话题比原生 Python 实现更准（Zenoh 上验证）。christophebedard 与 mjcarroll 在帖内讨论「是否应该直接用这个替换核心里的 hz 实现」，mjcarroll 表态支持
- **官方动向（PMC 8/18 纪要，8/25 发布）**：ROSGraph WG 正在做**基于 trace tools 的 topic statistics 原型**（因 RMW 讨论不接受 shim 作为核心特性）；同时 jmachowinski 提交了**直接删除现有 topic statistics 实现的 PR**——现有实现「在玩具场景外基本无用」，emersonknapp 同意删除是正确方向，开放问题是 deprecation 周期与 Windows 平台覆盖

**为什么值得关注：** 这是连续第三周「可观测性」主线的升级（继 ros2probe 的 eBPF 被动抓包、ROS 2 Inspector 的静态分析之后）：社区用扎实的数据证明了**现有工具的探针效应是结构性的**（hz/echo 改变被测系统、Humble 上 intra-process 完全不可见），而官方也终于承认内置 topic statistics 名存实亡。值得注意的张力是：官方原型刻意走 trace tools 而非 shim 路线，而 ros2_pulse 恰好是 shim 路线且已可进 apt——「社区现货 vs 官方正统」的取舍值得持续观察。

**影响层面：** 工程化 / 可观测性 / 核心框架（topic statistics 存废）

**下一步盯什么：** jmachowinski 删除旧 topic statistics 的 PR 是否合入及是否需要 deprecation 周期；ROSGraph WG 原型与 ros2_pulse 的路线竞争/融合；ros2_pulse 的 rosdistro PR 何时进同步；`ros2 topic hz` 是否真的会被 C++ 实现替换。

### 3. ROS 构建/分发/CI 体系一周三连：Conan ros-conan、Bazel 工作组、Windows CI Pixi 模式

**发生了什么：** 三条独立的信号共同指向「ROS 与主流软件工程工具链融合」：

- **Conan 官方团队发布 ros-conan（8/27）**：conan-io 成员维护的 Conan recipes 集合，把 **ROS Kilted** 变成可声明的 C++ 依赖（`ros-kilted/2026.06.17`，core/base/desktop 三种 variant），支持 Linux/macOS/Windows。纯 CMake 项目 `find_package(rclcpp)` + 链接 `rclcpp::rclcpp` 即可，**无需 package.xml、ament_cmake、colcon 工作区**；不同项目可在同一台机器上使用不同 ROS 版本/发行版而互不冲突；CI 覆盖 gcc13/clang17/MSVC。Conan 团队将出席 ROSCon Toronto 现场收集反馈
- **PMC 成立 Bazel 工作组**：andrew_symington 将起草 charter 并牵头，目标 ROSCon 前成形，为 ROSCon 上的构建系统讨论提供锚点（上周 protoros2 已建立在 ros-central-registry/Bazel 之上）
- **Windows CI 的 Pixi 模式被系统性总结（8/29，Daisuke_Kato）**：实测发现 `action-ros-ci` 在 Windows 上**故意跳过 colcon test**，`setup-ros` + Lyrical 会出现「0 packages / 0 tests / 0 failures 的假绿」；可行的模式是「固定版本 Windows 二进制 + ROS 自带 pixi.toml 复现依赖环境 + 显式 colcon build/test」，ros2-rust 与 ros2_control_ci 已有同类实践。作者建议：无论哪种方案，**CI 应在预期测试未被发现时直接失败**

**为什么值得关注：** apt/colcon 之外的第二条分发路径第一次由**主流包管理器官方团队**（而非社区个人）维护，这是质变——它把 ROS 拉进了 ConanCenter 的依赖图，让 ROS 与 OpenCV/TensorFlow Lite 等库享受同一套 lockfile、缓存与冲突检测。Bazel WG 的组织化 + Gazebo PMC 本周也在协调 Bazel 维护交接（含 BCR 访问权），说明「多构建系统并存」正从试探走向建制。Windows CI 的「假绿」揭露则对所有依赖 GitHub Actions 做 Windows 验证的团队是直接警示。

**影响层面：** 工程化 / 构建与分发体系 / CI 基础设施

**下一步盯什么：** ros-conan 的社区反馈与是否扩展到 Jazzy/Lyrical；Bazel WG charter 内容及其与 ros-central-registry 的关系；`action-ros-ci` 是否恢复 Windows 测试执行；「0 测试即失败」是否进入官方 CI 模板。

### 4. Open-RMF 下一代原型落地两大件：预约式目的地服务器 + 分层全局占用地图（GSoC 2026）

**发生了什么：** GSoC 2026 项目（导师 arjo129）向 `open-rmf/next_gen_prototype` 合入两个大型 PR，补齐 next-gen 水平化架构的关键缺口：

- **预约式目的地服务器（PR #25，+9k 行）**：目标被占用时不再直接失败停车，而是把机器人引导至用户定义的 **parking zones** 排队等待；parking zones 可在 RMF Site Editor 图形化标注，附带 Web 仪表盘与三机器人分流/取消的 launch 测试。顺带修复了负坐标网格索引 bug（会导致两台机器人拿到重叠目标）
- **分层全局占用地图（PR #36，+7.9k 行）**：各机器人的传感器观测（clear/occupied 区域、带来源与有效期）上报中央 path server，全局地图按来源分离存储、冲突时保守处理（任一来源报占用即占用）；**栅格化在观测到达时做一次并复用，合成速度提升 16–18×**；地图变更可触发在途机器人重规划（阻塞 300ms 后请求新计划，新旧计划无缝切换）；同源 free-space 观测可清除自己此前的障碍报告，避免机器人互相留下「幽灵障碍」
- 节点用 **Rust（ros2_rust）** 编写，Python 负责 launch/demo/测试

**为什么值得关注：** 这是 Open-RMF「从单体栈走向水平化、可独立替换节点」路线图的实质性落地，而且质量不像是学生 demo：观测接口刻意不内置融合策略、幽灵障碍清理、阻塞去抖等细节都处理到了。对做多机/楼宇 fleets 的团队，next_gen_prototype 正在接近「可参考的架构蓝本」。Rust 作为实现语言也再次验证了 ros2_rust 在核心系统软件中的可用性。

**影响层面：** 生态层 / 多机调度 / 水平化架构 / Rust 客户端库

**下一步盯什么：** Rust Nav2 costmap 观测节点（生产化缺口）何时补上；PiBT 规划栅格分辨率可配置化；next-gen 架构与现役 Open-RMF 主线的迁移路径。

### 5. LeRobot↔ROS 桥接继续深化：ROBOTIS 在 OMY 上同基准对比四个下一代策略

**发生了什么：** ROBOTIS（Pyo）8/24 发布实验报告：用开源的 **lerobot-robot-ros2-zenoh SDK**，把 Hugging Face LeRobot 生态的新策略通过标准 ROS 2 接口直接接上真机。在 CYCLO Intelligence 采集的遥操作数据上、同数据集同任务设置下 benchmark 了四个近期策略：**GR00T N1.7、MolmoAct2、VLA-JEPA、FastWAM**——GR00T N1.7 整体表现最强最稳。该工作流覆盖 ROBOTIS 全线（OMY、AI Sapiens、AI Worker、AI Manipulator、ROBOTIS Hand）。同周相关信号：德国团队发布 **ROS2SmolVLA**（小型 VLA 模型接入工业级轻量 cobot）、Pyo 另发了 OMY 上 GraspNet+Gemini 的 pick-and-place demo。

**为什么值得关注：** 上周 OSRA 成立 SIG PAI 把 Physical AI 组织化，本周就出现了「厂商级」的同基准策略对比——LeRobot↔ROS 桥接正从「能跑」进入「可比、可迭代」阶段。zenoh 作为桥接传输的选择也值得记录（与 ROS 2 内部 rmw_zenoh 的推进同频）。「小模型部署」（SmolVLA）是本周另一个被官方周报点名的方向，呼应边缘侧算力约束下的实用化趋势。

**影响层面：** 战略层 / 具身智能基础设施 / 策略评测方法

**下一步盯什么：** SIG PAI 是否把这类 benchmark 方法纳入路线图（标准化数据集/任务）；lerobot-robot-ros2-zenoh 与 SIG PAI demo 仓库的整合可能；GR00T 之外的策略在更多硬件上的复现。

**影响层面：** 治理 / 平台支持基线 / 发行节奏

**下一步盯什么：** PMC 异步投票结果（ROSCon 前落定）；scoped access 的首批执行情况；Gazebo M 最终命名（9/17）；ROS 2 是否跟进 macOS Intel 退场声明；Rolling sync 自动化的落地形态。

## 核心框架更新

**工程意义：** 本周核心客户端库无功能性大改动，但 rclpy #1702 修复的是「重复 spin 时回调累积」这类隐蔽的正确性问题，长生命周期 Python 节点受益。PMC 侧「删除旧 topic statistics 实现」的 PR 已开，是下周核心框架最值得盯的变动。

**工程意义：** rosidl memoization 是本周核心库里最「划算」的改动：IDL 解析在大型消息包构建中是可见瓶颈，进程内缓存零风险换时间。`ros2 doctor` 的 multicast 选项与上周网络诊断工具链的趋势一致。

### rmw / rosbag2 / Fast-DDS
- **Fast-DDS：修复交错日志的 TSAN 告警（#6468，8/24）**。
- rmw、rosbag2 本周窗口内无新 commit。

## 工程化观察

1. **可观测性连续三周升温，并从外围逼近核心**：ros2probe（eBPF 抓包）→ ros2_pulse（tracetools shim）→ 官方讨论删除旧 topic statistics、改用 trace tools 原型。一条清晰的演进线：社区先用外部工具证明价值与量化痛点，官方随后认领方向。做机器人系统的团队现在就可以用 ros2_pulse/ros2probe 组合获得「无探针效应 + 覆盖 intra-process」的观测能力，同时盯官方原型的平台覆盖（尤其 Windows）。

2. **「第二条分发路径」由主流包管理器官方团队维护，是质变而非量变**：ros-conan 让 ROS 成为 Conan 依赖图中的普通节点，配合 Bazel WG 的组织化与 Gazebo 侧 Bazel 维护交接，ROS 的构建/分发体系正在从「apt + colcon 单轨」走向「多轨并存、各取所需」。对需要跨平台、多版本并存、或与大型 C++ 依赖（OpenCV/TFLite）统一管理的团队，评估窗口已经打开。

3. **Lyrical 生态追赶进入收获期**：Nav2 正式版 + 上周 104 新包同步 + MoveIt 2.15 入库，Lyrical 从「新发行版」变为「可认真评估迁移的发行版」。Nav2 的组合内零拷贝 IPC 也把「零拷贝主线」从类型系统讨论拉进了默认部署形态。

4. **Open-RMF 水平化架构开始产出可参考的蓝本**：预约式目的地服务器 + 分层全局占用地图两个大件落地，且工程质量（观测接口的策略中立、幽灵障碍清理、栅格化复用 16–18× 加速）超出原型预期。多机调度领域的架构选型应把 next_gen_prototype 纳入雷达。

5. **CI「假绿」是普遍风险，值得所有团队自查**：Windows 上 action-ros-ci 跳过测试、setup-ros 跑出 0 tests 的绿灯——「预期测试未被发现即失败」应该成为所有 ROS CI 的标配断言，与平台无关。

6. **具身智能从组织化走向可对比的工程实践**：SIG PAI（上周）→ ROBOTIS 同基准四策略对比 + ROS2SmolVLA（本周）。下一步看的是 benchmark 方法与数据管线的标准化是否被 SIG PAI 吸纳。

## 前沿议题

### 1. 官方 topic statistics 重构：trace tools 路线 vs shim 现货
ROSGraph WG 刻意绕开 shim（RMW 讨论不接受其作为核心特性）走 trace tools 原型，但 ros2_pulse 已经证明 shim 路线可产品化且即将进 apt。若两者长期并存，社区将面临「装官方半成品 vs 装社区现货」的分裂；更理想的结局是官方定义消息契约与摄取点抽象（纪要中已提到 swappable ingest point 的设计意图），让 shim/LTTng/eBPF 都成为可插拔后端。

### 2. ROS 作为「普通 C++ 依赖」的边界在哪
ros-conan 抹平了 ROS 与 ConanCenter 库的界限，但 ROS 的运行时模型（daemon 式的发现、RMW 选择、环境变量）并非纯链接期问题。当 ROS 可以被 per-project 共存安装，「系统级 ROS」与「项目级 ROS」的混用调试、以及 bloom/rosdistro 发布流与 Conan/Bazel 流的映射关系，会成为新的工程议题——Bazel WG 的 charter 值得期待。

### 3. 多机共享地图的策略中立接口能走多远
Open-RMF next-gen 的观测接口刻意不内置融合策略（按源分离、保守合成只是默认），这与 Nav2 costmap 的 layer 模型、以及学术界的多机器人地图融合形成有趣对照。问题：策略中立带来的灵活性，会不会在生产部署时反而成为「每个车队都要自己写融合策略」的负担？接口与默认实现的边界划分值得跟踪。

### 4. 执行器之争的新变量：asyncio 作者进入 committer 序列
Nadav Elkabets（rclpy asyncio executor）被提名为 committer，叠加前几周 EventsCBGExecutor 转默认、waitable API 对齐 Python 的讨论，「收敛到统一 executor 模型 vs 拥抱语言原生调度」的走向可能出现实质性变化——ROSCon（9/22）上这几乎必是话题。

## 可继续深挖的问题

1. **jmachowinski 删除旧 topic statistics 实现的 PR 会否合入？** 需要 deprecation 周期吗，Windows 平台覆盖如何解决——这决定了官方观测栈的重置时间表。

2. **ros2_pulse 的 rosdistro PR 何时进入 Humble/Jazzy/Kilted 同步？** 以及它与 ROSGraph WG 原型最终是竞争还是合并为「契约 + 可插拔后端」。

3. **ros-conan 会不会扩展到 Jazzy/Lyrical，并被工业团队实际采用？** Conan 团队在 ROSCon 的反馈收集结果值得关注；Bazel WG charter 是否会覆盖与 ros-central-registry 的统一。

4. **Nav2 `nav2_ros_common` 的抽象边界如何演进？** 它会不会成为 rclcpp API 变动时的「减震层」范本，被其他大型栈（MoveIt、ros2_control）效仿。

5. **Open-RMF next-gen 与现役主线的迁移路径是什么？** Rust 观测节点补齐后，水平化架构何时达到「可试点替换现役部署」的成熟度。

6. **SIG PAI 会否把 ROBOTIS 式的同基准策略对比纳入标准化路线图？** GR00T N1.7 领先的结果在更多硬件/任务上是否可复现。
