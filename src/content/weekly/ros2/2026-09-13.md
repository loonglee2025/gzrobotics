## 总判断

本周是 **ROSCon Global 2026（9/22–24 Toronto）前最后一个完整工作周**，整个社区的注意力已从「新功能」切换到「会前收口」。最值得优先关注的三件事：其一，**PMC 换届正式落地**——9/8 会议确认、9/9 公告 skye.galaxy（Polymath）、JM_ROS/jmachowinski（Cellumation）、andrew_symington（Intrinsic）三人入委，三人恰好分别代表 events executor、客户端库性能与 Bazel 构建三条技术主线，且都将在 ROSCon 演讲；其二，**M-turtle（2027.5）路线图首次浮出水面**，主题是「less is more」——删功能（topic statistics）、合并执行器（rclcpp/rclpy executor 去重）、RViz 去 Ogre、linter 移出单测——ROS 2 核心开始做减法，这是多年来方向性最强的信号；其三，**Jazzy 完成 9/11 sync（882 个包）**，结束了自 6/18 以来近三个月的 sync 空窗，而 Lyrical 与 Humble 双双因回归推迟到 ROSCon 前最后窗口。Nav2 本周集中合入六个线程安全修复，是上周 #6429 报告的直接后续。

## 本周关键信号

### 1. PMC 换届落地：三人入委，恰好对应三条技术主线

**发生了什么：** 继上周选票发出后，9/8 PMC 会议确认、9/9 由 mjcarroll 正式公告三名新委员（ROS PMC Minutes 57957 / New ROS PMC Members 57984）：

- **skye.galaxy**（Polymath Robotics）——Client Libraries WG 主力，主导 CBG events executor 落地 Lyrical 及基准测试，并推动其成为未来发行版默认；
- **JM_ROS / jmachowinski**（Cellumation）——同样深耕 Client Libraries WG，贡献新 events executor 实现与全栈性能改进；
- **andrew_symington**（Intrinsic）——ROS Central Registry（Bazel 构建规则集）实现者。

三人全部有 ROSCon 2026 演讲。Bazel 工作组则进一步明确**推迟到 ROSCon 之后**（上周口径是「等 andrew 入委后」，本周 andrew 已入委但 WG 仍后移）——mjcarroll 澄清了 yadunund 的疑虑：WG 目标是让各家的 Bazel 实践进同一个房间做知识共享，而非把 ROS Central Registry 定为官方背书方案。

**为什么值得关注：** 换届不是仪式性事件——新委员的技术背景直接预告了 PMC 未来一年的议程重心：执行器架构统一（见信号 2 的 M-turtle executor 去重）、性能、以及 Bazel/现代构建链路的组织化。上周预告的「scoped access committer」和 Bazel WG 都在按节奏推进，治理变革进入执行期。

**影响层面：** 治理 / 路线图制定权

**下一步盯什么：** ROSCon 上三人的演讲内容与 PMC 问答；scoped access committer 第二批名单；Bazel WG 在 ROSCon 后的启动形态。

### 2. M-turtle 路线图定调「less is more」：删 topic statistics、合并执行器、RViz 去 Ogre

**发生了什么：** 9/8 PMC 纪要首次披露 M-turtle（2027 年 5 月）路线图方向（mjcarroll 主述，明确「尚未承诺」，按惯例在 ROSCon 前后公开征集意见）。核心判断：**技术债已经积累到该还的时候了**。具体方向：

- **Executor 去重**（skye.galaxy 主动认领）：rclcpp 与 rclpy 的 executor 子系统存在大量合理重复，开放设计问题是保留各自行为怪癖还是做成「rclcpp + Python 绑定」，ROSCon 后出具体提案——「短发行周期正是做架构级清扫的好时机」；
- **RViz without Ogre**（clalancette）：暂无具体计划，ahcorde 看过新版 Ogre，但 Ubuntu 上游不打包意味着 vendor 包仍会存在；反方意见是先评估生态已有可视化方案再投入重构；
- **声明式工具链**（emersonknapp）：NoDL 进核心工作流、ROS graph monitor、用 tracing 原型而非 RMW shim 实现 topic statistics；
- **结构化参数**（jmachowinski），与 NoDL 参数 schema 协同；
- **linter 不应是单测**（mjcarroll）：用 pre-commit + clang-format/ruff 把格式检查从 CI 构建中剥离——skye.galaxy 补充说这「也给 AI 生成的贡献设了质量底线，它们经常没跑过本地测试就交上来」；
- 删除「不 work 的东西」，点名 topic statistics。

**为什么值得关注：** 这是 ROS 2 历史上少见的「以删为主」的发行版叙事，与连续数周观察到的主线完全同频：社区焦点从「功能可用」转向「可维护、快构建、快 CI」。对用户的直接含义：M-turtle 可能是 API/行为清扫窗口（topic statistics 这类被点名删除的功能，依赖者应尽早规划迁移）；executor 去重若落地，是 rclpy 行为向 rclcpp 对齐的十年一遇级变更。

**影响层面：** 核心框架路线图 / API 演进 / 构建与 CI

**下一步盯什么：** ROSCon 期间路线图的正式公开与社区反馈；executor 去重的具体提案（ROSCon 后）；被点名删除功能的弃用时间表。

### 4. Rolling 同步自动化方案细化：阈值随发行周期动态调整，预计 2027 年 1 月上线

**发生了什么：** 「Rethinking Rolling Syncs」帖（56842）本周更新，mjcarroll 把上周 PMC 提到的自动化方案补全为完整设计：

- **阈值不是固定的**：现在到明年初——宽松阈值 + 高频自动 sync；临近 M-turtle 发布——阈值收紧（更大验证批次、更严格依赖图要求），类似 REP 2002 下 Rolling 在稳定版前的保守化；M-turtle 发出后阈值再回落；
- **readiness 度量**：buildfarm 测试结果 + 包在依赖图中的位置——下游影响大的包门槛更高，低风险叶子包不再被无关问题卡住；
- **范围限定**：只影响 Rolling，Humble/Jazzy/Kilted 的 patch release 流程不变；维护者的 bloom 发布流程不变，变的是包进 testing 之后的事；
- **时间表**：具体启动由 M-turtle ROS Boss 与发布团队定，**预期 2027 年 1 月**；
- 开放问题：初始批次大小与依赖图截断值、紧急修复的手动加急通道。

**为什么值得关注：** 上周我们看到的是「80% 通过率阈值」这个单一数字，本周补上了完整的周期化设计——Rolling 的「松紧带」第一次被形式化为可公布的策略。这直接改变下游对 Rolling 的预期管理：依赖 Rolling 做集成的团队可以把「sync 频率」从不可控变量变成可查的时间表。

**影响层面：** 发布管理 / Rolling 生态

**下一步盯什么：** 发布时间表上公布的实际数值阈值；测试场部署后的首次自动 sync；手动加急通道是否设立。

### 5. SIG Physical AI 双周进展：Qualcomm buffer backend 已合并但「无人有硬件验证」，WG3 独立推理节点亮相

**发生了什么：** 9/8 PMC 纪要中 SIG PAI 各组更新：

- **WG1**：Qualcomm 的 `rosidl_buffer_backends` 实现已合并，Python Torch 转换待办；零拷贝 rosidl 基准测试进行中（上周的 1 kHz/1 ms proof of life 的延续）；**REP 158（OpenUSD 互操作）进入投票阶段**；HCDF 提案推迟到十月；
- **PMC 级讨论——硬件加速后端的 CI 怎么办**：结论相当坦率——**PMC 目前不打算为这些架构提供 CI runner**。ahcorde 澄清核心只提供机制、不带官方后端（与 image_transport 插件模式一致）；yadunund 指出该仓 vendor 了 PyTorch 等依赖、携带厂商特定消息，倾向把厂商实现移到厂商自己维护的组织；最终口径是「每个维护者用自己的硬件对自己的后端负责」，并公开喊话：**有 Qualcomm 硬件的社区成员请联系验证加速路径**；
- **WG2**：就是否继续基于 Rosetta 做推理出现开放问题（Rosetta 正向框架无关漂移）；白皮书将以 markdown PR 发到网站，调研结果将在 ROSCon 发布；
- **WG3**：新独立推理节点 `intrinsic-inference` 亮相（ROSCon talk 已提交），下次会议讨论采用；计划与 ros2_control 做架构讨论，可能启动「实时与推理隔离」的 compartmentalization 工作流；
- **WG4**：App 1（SO-101）迁移 Lyrical，App 2 是 AIC 插线缆 demo，App 3 在「人形（更有声量）vs 双臂移动底座（更稳、更贴近 ROS 现有能力）」之间选型，正寻求厂商伙伴。

**为什么值得关注：** 两件结构性的事。其一，「核心出机制、厂商出后端、各自管 CI」的模式被 PMC 正式确认——这是硬件加速生态的治理模板，避免核心 CI 被厂商硬件绑架，但代价是加速路径的质量保证依赖厂商自律，采用者需自行验证。其二，WG3 的「实时与推理隔离」工作流一旦启动，将直面 ROS 2 控制环与 AI 推理环的频率错配问题——与本周 GSoC 的 ros2_control 轨迹上采样项目（见生态节）恰好是同一件事的框架侧与工具侧。

**影响层面：** 战略层 / 具身智能基础设施 / 硬件加速

**下一步盯什么：** REP 158 投票结果（ROSCon 前）；Qualcomm 是否拿出自家硬件的验证证据；WG3 与 ros2_control 的架构讨论纪要；App 3 的选型决定。

### 6. Nav2 线程安全集中收口：一周六个 data race / 并发修复

**发生了什么：** 继上周 #6435（Costmap2D 并发访问）之后，本周 Nav2 合入 12 个 commit，其中至少六个是并发/竞态修复：#6471（costmap shutdown flag data race）、#6472（锁 costmap service 响应生成）、#6446（Costmap2D::costmap_ 并发，#6429 的 Bug 2）、#6447（NavFn planner costmap 并发，Bug 3）、#6486（feasible path costmap 访问竞态）、#6467（成批解决报告的 tsan 问题）。另有 #6445（BT 在 goal 未确认时 halted 后取消 goal）、#6465（VO planner 更高效的栅格化）、#6492（Lyrical+ 上 nav2_common 改用 osrf_pycommon 系统包）、#6487（集成测试改为管理 RCLCPP 生命周期、改善资源清理）。

**为什么值得关注：** 这不是零散修复，而是一次**由 tsan（ThreadSanitizer）驱动的系统性并发清扫**——#6429 显然是一份完整的竞态清单，维护者在逐条消灭。工程含义有两层：使用 Nav2 的产线系统应尽快跟进这些修复（并发 bug 的症状是偶发崩溃/错误代价，现场极难复现）；同时 #6487 说明 Nav2 自身集成测试的生命周期管理也在加固，测试基建的可靠性在提升。

**影响层面：** 生态项目 / 正确性与稳定性

**下一步盯什么：** #6429 清单是否清零；这些修复随哪次发行版 sync 进入官方源；tsan 是否进入 Nav2 CI 常态。

### 7. rclcpp 启用 ABI 兼容检查 CI + rosbag2 0.35.0 落地混合序列化回放

**发生了什么：** 两条上周预告的事项本周兑现：

- **rclcpp #3262「enable ABI compatibility action check」（9/11）**——tomoyafujita 的 ABI 自动检查原型（Discourse 57477）正式进入 rclcpp CI，「防止 backport 漏网破坏 ABI」从原型变成核心仓库的强制门禁；
- **rosbag2 0.35.0（9/13）**——内含 **#2476 混合序列化格式回放**正式合入：一个 bag 里不同序列化格式的话题可以一起回放；代价是 `SequentialReader` 删除两个虚函数（**Rolling 限定的 API break**），`SerializedBagMessage` 新增 `serialization_format` 字段；
- rclcpp 另有 #3256（畸形 set_parameters 请求不再打崩节点）、#3258（拥塞下的线程使用改进）两个健壮性修复；
- rclpy #1718 修复 EventsExecutor 在任务抛异常时 segfault——events executor 相关修复持续进入，与新 PMC 委员的主线呼应。

**为什么值得关注：** ABI 检查进 rclcpp CI 是上周「ROS 2 ABI 治理组合拳」判断的第一个实锤——「防出错」这一侧开始制度化，接下来看 cottsay 的 version compatibility flag（「错了也炸不了」侧）何时跟进。rosbag2 混合序列化回放则直接服务于 rosbag2 作为数据基建的长期方向（多格式 bag、RRD 存储插件等生态动向同频）。

**影响层面：** 核心框架 / CI 质量门 / 数据基建

**下一步盯什么：** ABI 检查推广到其他核心仓的节奏；version compatibility flag 方案的进展；rosbag2 0.35.0 进入各发行版 sync 的时间。

## 工程化观察

- **回归与升级风险**：Jazzy 882 包大 sync 是本周最大变更面，生产团队应先在测试环境验证；rclcpp #3243（参数范围收紧，上周）可能随本次 sync 暴露历史配置错误。rosbag2 #2476 的 SequentialReader API break 仍限 Rolling。Nav2 六个并发修复值得反向评估自家 fork 是否携带同款隐患。

## 前沿议题

1. **「AI 推理环 × 实时控制环」的频率错配成为显学**
   GSoC ros2_control 轨迹上采样工具链（20–50 Hz → 200 Hz 平滑）+ SIG PAI WG3 的 compartmentalization（实时与推理隔离）+ intrinsic-inference 独立推理节点——三个独立进展指向同一个架构问题：大模型推理的速度与实时控制的要求差一个数量级，ROS 2 正在长出系统性的桥接层。做具身智能落地的团队应跟踪 WG3 的架构讨论结果。

2. **可靠性方法论的互联网移植**
   ros2_fault_injection（混沌工程）+ ros2_shadow（影子部署/候选版本 diff）+ 上周的 ros2_medkit（故障管理闭环）——ROS 2 的运维工具箱正在从「ROS 原生」转向「借鉴成熟软件工程方法论」。这会抬高生产级 ROS 系统的测试标准。

3. **硬件加速的治理模板确立**
   「核心出机制、厂商出后端、各自管 CI」——Qualcomm buffer backend 案例确立的模式，未来 NVIDIA/其他厂商的加速路径大概率沿用。采用加速后端的团队需要把「厂商验证证据」列入技术选型清单。

4. **Open Source Safety Consortium**
   安全论证（safety case）与代码一起开源，是功能安全领域少见的开放尝试。ROSCon 前后值得跟踪其成员扩展与方法论产出。
