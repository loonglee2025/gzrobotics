## 总判断

本周最值得记录的不是某个新特性，而是一条贯穿三个项目的工程口径变化：**ROS 2 生态开始系统性地把「静默失败」改成显式报错**。同一周里，`rmw_fastrtps` 把「未知 backend 名被悄悄丢掉、于是退化成 CPU 订阅」改为直接让订阅创建失败，并追加了一个「buffer-aware 发布失败必须返回错误」的 PR；Fast-DDS 修掉了 UDP 发送超时因 `tv_usec` 未归一化而设不上、且返回值未检查导致超时被静默留空的问题；Gazebo 侧则要求 `gz-transport` 在「环境变量选了 Zenoh 但没编进去」时显式失败，而不是静默回落 ZeroMQ [1][2][3][4]。加上 Gazebo PMC 这天处理的自动合并事故——一个 Fortress 回移在只有 DCO 检查的情况下自动合入失败构建、事后必须 revert——这三件事指向同一条纪律：**降级路径必须可被观测，合并门禁必须挡住失败**。

第二条主线是**发行机制层面的改制**。10/13 的 ROS PMC 纪要首次明确：「Rolling 的分布级 tagging 已正式停用」，并且正在做 Rolling 的自动 sync [5]。本周 rosdistro 出现 232 次提交、202 条发行提交、74 个包（rolling 独占 58 个），但**没有任何 sync 公告**——这与上期「Humble 10/12 sync 有正式 tag、有公告」的形态完全不同。同时上期遗留的边界本周被证实：`snapshots.ros.org` 根目录根本没有 `rolling/` 与 `kilted/` 两个子目录 [6]，不是路径变更，而是 Rolling/Kilted 这一代不发固定快照。

第三条是核心库的**清账周**。`rclcpp` 一周 17 次提交（8 个缺陷修复 + 7 个死代码清理），全部落在竞态、泄漏、析构顺序与未初始化读上；`rclpy` 修了 `ScopedWith` 析构段错误；其中 `#3280` 把 loaned message 的所有权交还方式改成 `shared_ptr` 自定义删除器 [7][8][9][10][11][12]——这是上期「零拷贝数据面」那条线的直接续篇，也是过去用 loaned message 的团队最容易踩到的那类隐形缺陷。

上期两个未闭环问题本周关掉一半：**ROS PMC 纪要 10/6 与 10/13 两期同时在 10/20 补出**，上期判断的「已知延迟而非停摆」成立；但 Fast-DDS 的九个 GHSA 编号**仍然是 404、最新 release 仍是 v2.14.7（09-08）**，下游一条修好的安全版本都还没拿到，这条线已连续第四期没有闭环 [13][5]。另外 `webots_ros2#1059` 的 Handle API 迁移连续第二周停在 open [14]。

## 本周关键信号

### 1. 「静默失败」被系统性改造成显式错误：中间件与仿真的同一套纪律

**发生了什么：** `rmw_fastrtps` 一周合入两个 buffer-aware 相关修复：`#946` 让订阅创建在 `acceptable_buffer_backends` 出现未知名字时直接失败（提交正文写得很直白：以前是「静默丢弃，于是打错一个字段名就得到一个只有 CPU 的订阅」，现在按 `rmw_subscription_options_t` 的文档语义报错，与 `rmw_zenoh_cpp` 对齐）；`#944` 让 loaned 与 dynamic take 路径也遵守 `ignore_local_publications` [1][15]。同时队列里还有 `#958`（buffer-aware 发布失败要返回错误，而非继续）与 `#955`（buffer-aware 路径之前先校验 `rmw_take_with_info` 参数）两个 open PR，方向一致 [2][16]。Fast-DDS 侧四个提交全部是「失败被吞掉」类问题的下游修正：`#6558` 把微秒数直接塞进 `struct timeval::tv_usec` 而不归一化到 [0, 999999]，导致一秒及以上的发送超时 `setsockopt(SO_SNDTIMEO)` 返回 `EINVAL`、**且返回值没检查，超时实际上从未生效**；`#6557` 修「`expired()` 与 `lock()` 之间代理被释放、registry 交出空池」的竞态；`#6573` 修 registry 对每个话题名永久留条目、使「话题名带 GUID」的进程无界增长；`#6579` 改进默认 TCP 配置（socket 自动调优、send/重连竞态）[3][17][18][19]。仿真侧，Gazebo PMC 明确 `gz-transport` 应在环境变量选了 Zenoh 但未编译支持时**显式失败**，而不是静默回落 ZeroMQ [4]。

**为什么值得关注：** 这四类问题有一个共同形态——**系统在错误状态下继续运行，且不告诉任何人**。打错一个 backend 名得到 CPU 订阅、超时设不上就是无限等待、Zenoh 没编进去就跑 ZeroMQ，在实验室里都能「跑通」，到产线上才变成难复现的性能与超时事故。把它们逐个翻成显式错误，是 ROS 2 从「框架」变成「平台」必须做的一步，也直接呼应上期的判断：buffer-aware 路径「静默回落 CPU」缺少可观测性——本周的 `#946` 就是对这个缺口的正面回应。

**影响层面：** RMW 分层 / 中间件可靠性 / 生产环境可观测性

**下一步盯什么：** `#958`/`#955`/`#953`（`wait_for_all_acked` 要等 buffer 通道的 DataWriter）、`#960`（participant 初始化期间的 buffer 发现）能否本周内合入；`rmw_zenoh_cpp` 与 `rmw_fastrtps_cpp` 在「显式失败」语义上是否继续保持一致。

### 2. core 库清账周：`rclcpp` 17 次提交全在生命周期与竞态上，loaned message 所有权改写

**发生了什么：** `rclcpp` 本周 17 次提交，8 个是缺陷修复：`#3280` 用 `shared_ptr` 自定义删除器把 loan 交还路径重写（提交里能看到两轮 review 收敛——先去掉额外互斥量、再给析构加 try-catch）；`#3319` 调整组件容器里 executor 与 class loader 的声明顺序，让 executor 先于组件库卸载被销毁（此前 `EventsCBGExecutor` 会在 Ctrl-C 时崩溃）；`#3350` 修用最小构造函数创建的 executor 在析构时崩溃；`#3288`/`#3361` 分别修 `EventsCBGExecutor::has_ready_entities` 与 `IntraProcessManager::lowest_available_capacity` 的数据竞争；`#3358` 修 `wait_for_message` 的关闭回调泄漏；`#3357` 修 `ParameterEventHandler` 跳过紧邻过期 handle 的回调；`#3359` 修 lifecycle `ChangeState` 服务的未初始化读 [7][8][9][10][11]。另一半是清理（移除未用的 typesupport、`NotNull` 助手、测试消息、`stop_sleeping_` 标志等），且 `#3341` 把 ABI 判定的 backport candidate 标签补进主干。`rclpy` 两个提交里，`#1745` 把回调所有权移进 `CbEntry`、让排队事件按 key 查找，从而在持 GIL 的情况下释放 `ScopedWith` 捕获，修掉析构段错误；另一个是构建告警清理 [12]。`rmw_implementation` 补了两个针对性测试：loaned message 下的 `ignore_local_publications`、以及 wait set 实体变化后的 publisher matched 事件。

**为什么值得关注：** 这批提交单看都是小修，合起来是一次「**用竞态做审计**」的窗口期：析构顺序、弱引用失效窗口、回调捕获生命周期——这些正是上期 `#3315`（已移除定时器的 use-after-free）、`#3278`（异常逃逸析构）那条线的延续。对业务侧最直接的一条是 `#3280`：loaned message 的归还语义过去依赖隐式所有权转移，一旦消息在回调外被持有就会出问题；改成自定义删除器后，返还时机由引用计数决定，`unique_ptr` 风格的直觉行为才真正成立。对正在往零拷贝/加速 buffer 迁移的团队，这是先决条件。

**影响层面：** 客户端库 / 内存与生命周期语义 / 组件容器稳定性

**下一步盯什么：** `#3280` 是否回移到 Humble/Jazzy（loaned message 在 Jazzy 上仍有大量使用者）；`EventsCBGExecutor` 在这个季度内的竞态修复是否收敛（已是第三次相关提交）；`rmw_implementation` 新增的 matched 事件测试是否暴露出 Fast DDS 侧的真实缺陷。

### 3. Rolling 发行机制改制：分布级 tagging 停用，一周 74 个包 release 却零 sync 公告

**发生了什么：** 10/13 的 ROS PMC 纪要里，Rolling 维护者明确记录两条：**「Rolling 的分布级 tagging 已正式停用」**，以及正在推进 **Rolling 的自动 sync**[5]。本周 rosdistro 数据与之呼应又留白：232 次提交中 202 条是发行提交（190 条带 `[bloom]`），覆盖 **74 个包**，分布为 rolling 59、lyrical 41、jazzy 37、kilted 35、humble 30——是上期（91 次提交、30 个包）的两倍以上。但**本周没有任何 sync 公告**，`snapshots.ros.org` 上本周也没有新增快照（最新仍是 jazzy/2026-10-05、lyrical/2026-10-05、humble/2026-10-12）[6]。同期 rosdistro 自身的工具链在换代：autorelease 与 validation 工作流从 Python 3.8 迁到 **3.12**，rosdep 的「legacy Python 2 键」清理走到 **Stage 5（100%）**，并新增 Conda channel URL 支持 [20]。

**为什么值得关注：** 过去判断「某发行版有没有前进」靠两件事：sync 公告与快照目录。本周这两把尺子同时失效——**tagging 停用意味着 Rolling 不再有可指认的同步点，snapshot 目录缺失意味着 Rolling/Kilted 无法做固定版本回归**。对上期那个结论（「用固定快照做可复现回归重新可用」）必须做修正：这句话只对 Humble/Jazzy/Lyrical 成立，Rolling/Kilted 从来就没有快照目录。对生产团队的实操含义是：**若需要可复现基线，不要选 Rolling**；若一定要跟 Rolling，就得自己 pin apt 快照或用容器镜像。

**影响层面：** 发行节奏 / 可复现性 / CI 与回归基线

**下一步盯什么：** 「自动 sync」的落地形态（是否有公告、是否仍生成 tag、频率）；`rolling/` 与 `kilted/` 快照目录是否会被补上；74 个包的 release 洪峰是否在下一个 sync 里集中到 apt。

### 4. PlanSys2 4.0.0：上期「迁到 Kairos 与 STN」的信号变成可安装的版本

**发生了什么：** 10/21 发布 **PlanSys2 4.0.0**，作者自己总结为两件事：一是**可靠性**——「任意启动顺序、进程崩溃后重启并恢复状态、丢消息、网络延迟、高负载、API 误用、恶意输入」都要能处理，测试手段包括 sanitizer、fuzzing 以及在 **Fast DDS / Cyclone DDS / Zenoh** 三种中间件上的压力基准；二是**PDDL 覆盖从 1.2 到 PDDL+**——STRIPS、类型、条件效果、派生谓词、数值 fluent、durative action、timed initial literal、PDDL3 preference/constraint、object fluent，直到 PDDL+ 的 process 与 event。默认规划器换成 Kairos，默认执行器换成 STN 行为树 builder（保留动作间并发与时间约束）。关键细节：**4.0.0 是 Humble / Jazzy / Kilted / Lyrical 四条发行线的同一个版本号**，rosdistro 里 `ros2_planning_system: 4.0.0-1` 已于 10/22 同时 bloom 进四条线，`kairos` 本周另有 8 次发行提交 [21][5][22]。

**为什么值得关注：** 上期报告写过「PlanSys2 转向 Kairos 与 STN」——当时还只是仓库层面的动作，本周它变成了一条可以在四条发行线上装同一个版本号的发行事实，这在 ROS 2 生态里不常见（多数包要对着发行版分叉）。对做任务规划的团队，两条含义：其一，PDDL+ 与 durative action 的**忠实执行**过去是这个栈最薄弱的一环，现在由 STN builder 兜住；其二，「跨 Fast DDS/Cyclone/Zenoh 的鲁棒性测试」这个说法本身值得借鉴——多数规划/调度类包只测一种中间件。

**影响层面：** 任务规划与执行 / 多发行版一致性 / LLM 任务规划的基线

**下一步盯什么：** 4.0.0 在各发行线实际进 apt 的时间；Kairos 的 PDDL 支持矩阵与基准是否被其它规划器作者引用；`ros2_planning_system_examples` 里 PDDL+ 示例（greenhouse/watering）是否成为教学默认。

### 5. Gazebo PMC 10/19：一次自动合并事故换来分支保护加固，同时决定往轻量 2D 物理探路

**发生了什么：** 本周 Gazebo PMC 纪要里有四件值与工程相关的事。**（a）合并门禁事故**：Fortress 回移 `gz-sim#4076` 在构建失败的情况下被 GitHub **auto-merge** 合入，原因是该分支只要求 DCO 检查；随后必须 revert（`#4079`），并正在通过 `terraform_github_repos#10` 更新分支保护，强制要求 Jenkins 与 GitHub Actions 检查 [23][24][25]。**（b）Fuel 服务器过载宕机**：周末因爬虫并行下载模型导致内存耗尽，服务已重启，后端在改成不把完整模型载入内存，并更新部署机制。**（c）轻量 2D 物理**：讨论用 Box2D 作为物理引擎插件，支撑「数百台机器人、只需要碰撞与基本运动学」的大规模平面仿真；对比对象是现有的 TPE（Trivial Physics Engine），后者目前**不支持关节**，将做更细的比较再定。**（d）Bullet-Featherstone kinematic mode 全套合入 Rotary**：位置限位、动/静 link 切换、带 CoM 偏移的 kinematic 基座速度、混合模式下的力扭矩传感器、root joint 位置速度共五个 PR 全部进主线，验证后回移 [4]。此外：runtime-typed `EntityComponentManager` 批量查询已合入并暴露给 Python；Ogre 1.12 迁移拆成 stacked PR，自定义地形 shader 因上游类被移除而暂时无解，PMC 同意「找不到快修就先不带该功能合并」；正在评估**用 Rust + Bevy 重写 gzweb**；macOS Tahoe 的 `ogre1.9` 因 AGL 在 macOS 26 被移除而需要社区补丁；并讨论 **Pixi 在 macOS 成熟后可能淘汰 Homebrew bottle**（保留 tap）[4]。

**为什么值得关注：** 三条判断：其一，**「自动合并」在只有 DCO 检查的分支上等同于没有门禁**，这次是 ROS 2 生态里少见的、公开复盘的 CI 治理事故，对任何开了 auto-merge 的仓库都是直接警告；其二，方案级取舍开始围绕「规模」而不是「精度」展开——Box2D/TPE 这条线瞄准的是数百机器人的平面场景，与上期的「多机器人仿真社区会议」是同一个需求；其三，`EntityComponentManager` 批量查询 + Python 暴露，说明 Gazebo 正在把「仿真即数据源」当成一等用途（强化学习/数据生成侧的直接受益）。

**影响层面：** 仿真生态 / CI 治理 / 大规模多机器人仿真 / 开发环境可获取性

**下一步盯什么：** `terraform_github_repos#10` 落地后，各 gz-* 仓的必需检查清单；Box2D vs TPE 的结论会不会变成一个官方 plugin；Ogre 1.12 合并时是否真的丢掉自定义地形 shader（对用高度图的团队是硬伤）；Pixi 与 Homebrew 的替代关系（衔接上期的 2027-01-10 Homebrew 断供日期）。

**为什么值得关注：** 治理信号这四周第一次从「静默」转为**有排期的具体议题**。三条最值得记：其一，**macOS 的定位正在被重新定义**——「Pixi 长期策略 + 明确平台边界」意味着未来 macOS 可能是「有官方支持的开发者体验，但不承诺全部发行版」；与 Gazebo PMC 讨论淘汰 Homebrew bottle 是同一股风。其二，`AGENTS.md` 标准化贡献规则在全仓推广，是 AI 参与贡献后的必然产物（本周 `rclcpp#3319` 的提交里就带 `Assisted-by: Claude Code` 标签，`rmw_fastrtps#946` 带 `Co-authored-by: Claude Opus 5.5`）——**ROS 2 正在正式化「AI 辅助提交」的署名与规则**。其三，buildfarm 的 27 个陈旧 issue 与多个发行线级 flaky，说明测试基础设施的维护带宽是当前瓶颈，而不是缺功能。

**影响层面：** 治理与流程 / 平台支持边界 / 贡献规范 / CI 稳定性

**下一步盯什么：** TGC 的 ROS 代表投票与 M-turtle ROSboss 投票（两者绑定同批发出）；committer 培训与 PMC summit 是否成行；Pixi 策略的时间表；`AGENTS.md` 是否真的进入各仓；`perf_test` 的 Cyclone 侧根因。

### 7. gz_ros2_control：上期 RFC 没关闭，但重构已经按 RFC 的意图做完了

**发生了什么：** `gz_ros2_control` 本周 **9 次提交**，主线是把「不可测的大函数」拆成「可单测的部件」：`#985` 抽出插件 SDF 解析与关节过滤，`#987` 抽出 controller 更新门控，`#989` 让插件加载失败**直接导致启动失败**（而不是带着空组件跑）、并补 `GZResourceManager` 测试；另有 `#986` 修插件 SDF 解析边界情形与「关节无名字」时的崩溃、`#990` 在 launch 测试结束时优雅停 Gazebo、`#991` 为 IMU 与力扭矩传感器路径补单测、`#992` 值初始化 `HardwareInfo` [27][28][29]。而上期点名的 RFC `#964`（重组集成测试架构：从「进程/话题存在」升级到「校验关节位置/速度/力矩的实际响应」）**状态仍是 open、最后更新停在 9/27** [30]。同期 `ros2_controllers` 两个修复值得记：`#2697` 修 tricycle controller 在激活时接口重新绑定，`#2701` 修 admittance controller 与 gpio_controllers 的用户文档 [31][32]。

**为什么值得关注：** 这是一个**「RFC 未关闭但实质已落地」**的典型样本：判读社区动向时只跟 issue 状态会漏掉真实进度。把 SDF 解析、更新门控、资源管理逐个抽成 helper 并配单测，正是 RFC 里「可验证、可组合」的前提动作；`#989` 的「加载失败即启动失败」又回到本期第一条主线——**不许静默降级**。对用 gz_ros2_control 做真机/仿真一致性验证的团队，这批提交提高了「仿真里过的测试在真机上有意义」的概率。

**影响层面：** 硬件抽象 / 仿真桥 / 测试架构

**下一步盯什么：** RFC `#964` 是否在重构完成后正式关闭，以及关闭时是否有「响应级断言」的示例；`gz_ros2_control` 与 `ros2_control` 6.13（本周仍无，rolling/lyrical 停在 6.12.0）的版本对齐。

## 工程化观察

1. **「降级必须可见」正在成为跨项目的验收标准。** 本周至少四处独立改动朝同一方向：`rmw_fastrtps#946`（未知 backend 报错）、`#958`（buffer 发布失败返回错误）、Fast-DDS `#6558`（超时设不上不再静默）、`gz_ros2_control#989`（插件加载失败即启动失败）、`gz-transport`（Zenoh 未编译却选中要显式失败）。写代码评审清单时可以直接加一条：**这条失败路径上，用户会看到什么？**

2. **可复现性的尺子要分发行版看。** `snapshots.ros.org` 根目录只有 groovy/noetic … jazzy/lyrical/humble，**没有 rolling 与 kilted**；加上 Rolling 分布级 tagging 停用，Rolling 事实上已从「可指认快照」模型转向「连续滚动」。需要基线的产线应把 Jazzy/Lyrical/Humble 作为锚点，Rolling 只做前瞻验证。

3. **自动合并是门禁问题的放大器。** `gz-sim#4076` 这类事故的根因不在 auto-merge 本身，而在「必需检查只有 DCO」。评审任何仓库的合并策略时，先看 required checks 列表，再看 auto-merge 开关。

4. **AI 辅助提交在 ROS 2 主干已进入「署名 + 规则化」阶段。** 本周主干提交里出现 `Assisted-by: Claude Code`、`Co-authored-by: Claude Opus 5.5`，同时 PMC 在推 `AGENTS.md` 统一贡献规则。把这条写进团队的 contributor guide 比争论要不要用更实际。

5. **`rclcpp` 连续三周在做竞态与生命周期审计**，且集中在 executor / intra-process / 组件容器三处。若你的系统在这三处有自定义扩展（自定义 executor、组件热卸载、进程内通信），值得跟一遍这批 PR 的 diff，而不是等下一个发行版。

## 前沿议题

- **执行资源的显式化（C++26 `std::execution`）**：社区帖提出 ROS 2 executor 线程不应「顺手承接任意计算」，主张用 senders/receivers + scheduler 把「计算在哪里执行」变成架构决策——通信与协同回调保留专属容量，昂贵的感知/规划派到独立执行资源，并强调要遵守真实的时间与安全层级（车队协同不得干扰车辆控制）。作者明确不替代 executor，而是问 `rclcpp` 是否该暴露与 `std::execution` 兼容的 scheduler 抽象 [47]。这条与本周 `EventsCBGExecutor`/`IntraProcessManager` 的竞态修复是同一问题的两面。
- **`image_transport` / `point_cloud_transport` API 统一**：社区发起把两者 API 对齐、C++/Python 一致，目标是「把 `rclcpp::Publisher` 换成 `image_transport::Publisher` 只需最小改动」，并补齐 connect callback 等能力，**赶在 Makoa 代码冻结（2027-05）之前**；11 月中收集意见后开工 [48]。上期引用过 Makoa 发行说明，这条是它的具体施工面。
- **大规模平面仿真的物理后端**：Box2D vs TPE（TPE 尚无关节支持），目标数百机器人、只需碰撞与基本运动学。
- **gzweb 的 Rust/Bevy 重写评估**：性能、真实感与现代 SDFormat 支持是三个动机。
- **mypy 回归阻塞构建**：`rclpy#1707` 的 154 个生成代码导致的 mypy 回归，是「类型标注进入生成链路」的典型代价，值得关注其解决方案（生成侧修复还是 mypy 配置隔离）。
